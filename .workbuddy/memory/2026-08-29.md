## 5. 外部建议代码评审（用户提供他人给的「按钮悬停放大+音效」「等距角色呼吸」方案）
**实测验证（Godot 4.7.2 真机）**：
- `Node.find_node()` **已被移除** → `root.has_method("find_node")=false`，`find_child()=true`。建议代码里的 `get_tree().root.find_node("AudioUI",true,false)` 运行时必崩（Nonexistent function），且 check-only 因 `root` 返回类型宽松**解析期不报错，是隐性炸弹**。
- `TIME` 未定义 → `Parse Error: Identifier "TIME" not declared`。呼吸脚本 `iso_character_breath.gd` 直接加载失败。**这正是不少 "Parse error" 的字面来源**。

**建议方案的优点（采纳）**：① 用 `scale` 而非 `custom_minimum_size` 做悬停放大——不干扰容器布局，核心正确；② 组件化挂载（方案A）优于集中绑定（方案B），组合优于继承；③ Tween + `kill()` 防冲突；④ 禁用态守卫 + `@export` 调参；⑤ 呼吸"脚钉死地面、禁止整体 Y 位移"对等距 2.5D 是正确直觉。

**建议方案的缺点（不可直接抄）**：
- `find_node` 已移除（上）；`TIME` 未定义（上）；Control `scale` 绕 **pivot_offset 默认 (0,0)** 缩放 → 按钮往右下长而非中心放大，右下角按钮会溢出（建议方案完全没提 pivot）；`_process` 轮询 disabled 属反模式；单个 AudioStreamPlayer 会被后一个音切断前一个（快速划过多个按钮爆音）；`@export = preload("可能不存在的路径")` 在 preload 语义下会让整个脚本加载失败而非静默；方案B 自己没写 `kill()`，与方案A 自相矛盾。

- 绕过已有的 `AudioManager`（已有 SFX 总线 + `play_sfx()`），失去音量/总线控制。
- 只考虑鼠标 hover，忽略两个现实：安卓触屏无 hover（需 pressed 态）；本工程 MenuItem 是**键盘导航**（`FOCUS_NONE` + `_unhandled_input`），hover 动画音效完全不会触发。

**定案的三层解耦架构（用户已采纳方向）**：

## 6. 重大发现：画面技术路线的「文档决策」与「代码现实」不一致
用户提出质疑："我定项时记得是 2.5D 锁视角不能转视角，为什么说是 3D 场景 + Sprite3D？"——核查后证实用户直觉正确，确实存在不一致。

**概念澄清**：「2.5D 锁视角不可转」是**目标**；「3D 场景 + Sprite3D」与「纯 2D + Y-sort」都是实现该目标的**手段**。视角能否旋转**只取决于相机**（Camera2D/Camera3D 固定角度即可锁死），与用 2D 还是 3D 场景**无关**。二者不矛盾。

**实测代码现状（Godot 4.7.2 grep 取证）**：
- `TownScene.tscn` 根节点 = **Node2D**；`BattleScene.tscn` 根节点 = **Control**（战斗是 UI 界面，非场景）
- 相机 = **Camera2D**（`TownScene.gd:68`，挂在玩家节点下）
- 玩家 = `Node2D` + **蓝色 32×32 ColorRect 占位**（`TownScene.gd:61-67`）
- NPC = `Node2D` + Sprite2D（有立绘时）或**黄色占位方块**（`TownScene.gd:74-98`）
- 背景 = 单张 2000×2000 纯色 ColorRect
- **全工程零 3D 节点**：Node3D / Sprite3D / Camera3D / MeshInstance3D / Vector3 全部搜不到
- `scenes/actors/` 下 player / enemy / npc / interactable **四个目录全空**，角色系统尚未实现
- **未启用 ysort**（`TownScene.gd` 无 `ysort_enabled`），等距视角下角色前后遮挡会错乱，需要补

**结论**：现在正是技术路线决策的**黄金窗口**——角色系统一行未写，改动代价最低；一旦立绘、移动动画、碰撞做完再换路线，返工成本会高一个数量级。
**我的建议**：继续走**纯 2D**。理由：① 代码已如此，改 3D 要重写移动/相机/碰撞；② 用户是新手，3D 场景搭建（正交投影、Sprite3D 朝向、材质光照）门槛明显更高；③ 回合制 + 自动战斗不吃 3D 的红利（3D 价值主要在即时动作、真实遮挡、光影）；④ 战斗本来就是 UI 界面做的，与 3D 无关。**但必须补 `ysort_enabled`**。

## #148 战斗逻辑层架构设计（可视化战斗）· 审视 + 方案

**产出**：`docs/战斗逻辑层架构设计.md`（v1.0，战斗域重构唯一执行基线）

**现状诊断（7 个硬伤）**：
1. 回合流程编排写在表现层 `BattleScene._on_action_pressed()`（攻击→敌人回合→判胜负→结算手动串）
2. 战斗一帧跑完（自动战斗是 `while` 死循环）→ 动画没机会播
3. **`enemies.json` 的 `speed` 字段从未被任何代码读取** → 无行动顺序
4. `randf()` 内联在 `CombatCharacter.take_damage()` / `AbilityService` → 不可复现不可测
5. 伤害公式 `max(1, amount - int(defense*0.5))` 硬编码 → 违背数据驱动
6. `StatusEffect` + `active_effects` 是死代码，从不 tick
7. 表现层只能读 `CombatState.entries: Array[String]` → 拿不到结构化事件

**目标架构（四层 + 一条事件流）**：
① 输入层（CombatCommand，玩家/AI）→ ② 逻辑域 CombatCore（纯 RefCounted，零 Node/零 randf/零 Tween；含 TurnScheduler / DamageResolver / EffectSystem / CombatBrain）→ ③ **CombatEvent 队列（唯一层间契约，可序列化）** → ④ 表现域 CombatDirector（await 逐个播）+ CombatView（只做血条飘字）。队列空 → 请求下一回合。

**四条铁律（新增，已写进文档）**：
1. 逻辑域不认识 Node 也不认识时间（无 await/Tween/delta）
2. **战斗内事件不走 EventBus**（高频有序流，走总线污染全局且顺序不可控）→ 用**函数返回值**传；只有 combat_started/ended/finished 这类跨模块通知发 EventBus
3. 表现层**只读事件不读 CombatState**（事件自带 `target_hp_after`）
4. 随机源必须注入（CombatCore 持 RandomNumberGenerator，seed 可外部指定 → 同 seed 同指令 = 同结果）

**关键设计决策**：
- 新增 `combat_event.gd`（RefCounted class + to_dict/from_dict）：代码里类型安全（避 untyped 遍历 Cannot infer type），存档时转 Dictionary 不违反「内存统一 Dictionary」纪律
