# 跨模块 BUG 修复机制（专治"修了好久"）

> 生成：2026-09-02
> 背景：用户指出一个真实痛点——一个 UI 层小 BUG 修了很久；并质疑"模块内部关上门"机制，
> 理由是"它暴露不出来别的模块和这个模块可能会关联出现的 BUG"。本机制即为此而生。
> 结论先行：**封装（关门）降的是"内部爆炸"的耦合，但查不出"跨模块接缝 BUG"；后者才是拖很久的真凶，要靠"接缝透明 + 修 BUG 协议"解决。门照关，但要补缝。**

---

## 0. 先认账：你的批评是对的

"模块内部关上门"（只露公开方法、内部私有）做的是一件事：**防止模块 A 内部出错传染给模块 B**——这是降耦合，有价值。

但它**解决不了、甚至遮住**另一类 BUG：**跨模块接缝 BUG**。
- 例子：UI 显示的数据来自某个服务；UI 变化由某个 EventBus 信号触发；两个模块靠一份契约对接。
- 这类 BUG **不在任何模块"内部"**，而在两个模块的**边界（缝）**。门一关，你反而看不到"谁的数据喂给了 UI、哪个信号触发了 UI、payload 对不对" → 更难查。

我们 handoff 板当前 open 的 UI BUG 几乎全是接缝 BUG（真实信号名作证）：
`notify_quest_track_changed`（任务窗发信号、HUD 订阅未闭环）、`inventory_add_overflow`（满包丢物信号无人订阅）、`player_hp_changed`（信号参数不匹配致 TownScene 掉血即崩）、"响应式锚点覆盖其余弹窗""列表刷新子节点"。
→ 痛点就在**缝**，不在内部。所以"再多加封装"治不了你的病。

---

## 1. 门和"查关联 BUG"不矛盾：门照关，缝要透明

- **门照关**：模块内部仍私有（保留降耦合、防内部爆炸的好处）。
- **但接缝必须全透明 + 有测试**：公开接口、EventBus 信号、契约，全部**可见、可查、有集成测试**。
- "内部私有"与"边界可观测"是**互补**，不是二选一。不要因为怕暴露关联 BUG 就拆掉门（那会回到高耦合）；也不要因为装了门就以为 BUG 查得出来（门挡的是内部，不是缝）。

---

## 2. 跨模块 BUG 修复协议（5 步，铁律）

> **铁律 0（最重要）：没稳定复现 + 没失败测试，不准说"修好了"。**
> "看起来好了" = 没修好。这正是一个 BUG 拖好几天的根因——没有把 BUG 钉死，改完不知道真没真好，过两天又冒。

**① 复现 + 钉死（写失败测试 / 最小复现步骤）**
先造一个最小复现：操作步骤，或直接写一个 failing 单测断言"期望行为"。测试红 = BUG 在；修到绿 = 真修好。UI BUG 可用 `tests/ui/` smoke + 一个针对该交互的断言。

**② 沿接缝定位（封装暴露不了的地方，靠这一步）**
UI BUG 几乎都在"UI ↔ 服务"的缝上，顺三条线查：
1. UI 显示的数据，从哪个服务的哪个公开方法 / 哪个 JSON 来？
2. 触发 UI 变化的 EventBus 信号，是谁发的？payload 对不对？
3. 契约总表里这个接口/信号的定义，调用方和实现方现在还对得上吗？（`tools/gen_contract.gd`）

**③ 判"内部 BUG" vs "跨模块 BUG"**
- 纯 UI 内部（布局/锚点/信号连错/节点复用）→ UI 窗口自己修。
- 数据源或信号来自服务 → **这是跨模块 BUG，走 handoff 派给责任窗口**；UI 窗口别自己去改服务内部（也改不动，门是关的）。

**④ 加"接缝集成测试"防回归**
修完后补一个测试，直接验"缝"：**发信号 / 调方法 → 断言另一端收到正确结果**。
这样以后模块 A 改了输出、模块 B 没跟上，下次测试立刻红，不用等玩家发现。
（我们目前只有 `gen_contract.gd` 的**签名**检查，缺**行为**集成测试——这是真缺口。）

**⑤ 双闸门 + 关单**
全量 GATE2 过 → handoff issue 标 `closed` → changelog 该行「关联」注明 **根因 / 回归自 `<commit>`**。

## 3. 让"关联 BUG"暴露出来的两个工具（建议建）

**A. EventBus 信号流日志（调试版）**
在 `EventBus.emit` 包一层：记录 `信号名 + 参数 + 时间`。出 BUG 时一眼看到"谁发了什么、谁听了、参数对不对"。专治"最松解耦=控制流隐形"的坑（信号是隐式耦合，grep 不到调用链）。

**B. 信号地图（文档/自动生成）**
从 EventBus 信号清单生成：每个信号 **谁发 / 谁听 / payload 结构**。改信号前先查地图，避免"发了没人听"或"听了但字段对不上"。
（内部仍可关；缝全透明。）

## 6. 静默拦截 BUG 专项（无报错，但行为就是错）

> 生成：2026-09-02（用户真实案例：能进游戏、但开始界面卡死、全程零报错，修了很久）
> 本质：**事件被某个控件吃了**，不是逻辑错。GATE1（解析/编译错误）永远抓不到，只能靠"鼠标拾取"暴露。

### 6.1 这类 BUG 长什么样
- 能进游戏、能跑、全程**零报错**；
- 鼠标自动卡在某个按钮上移不开（hover 被吞）；
- 点下去永远不触发回调；
- 只有"恰好没这种拦截子节点"的按钮正常（如普通 `Button` 没装饰子节点）。

### 6.2 头号坑：mouse_filter 枚举写反（反直觉）
Godot 的 `mouse_filter`：
| 值 | 枚举 | 含义 |
|---|---|---|
| `0` | `STOP` | **拦截，吃掉点击**（这是**默认值**，也是直觉反的） |
| `1` | `PASS` | 放过，事件落到下层 |
| `2` | `IGNORE` | 忽略，点击穿透 |

本意让装饰子节点（`Label`/`TextureRect`/`ColorRect` 这类盖在按钮中心的）"点击穿透"，却**错写成 `0`**（以为 0=无/穿透，实际 0=STOP=拦截）。于是 `label_main`（文字标签，正好盖在按钮中心）变成拦截型，把按钮本体的 `mouse_entered`/`button_up` 全吞了 → 自动悬停 + 点不动 + 零报错。

**铁律**：想让子控件"点击穿透"，必须写 `2` 或 `Control.MOUSE_FILTER_IGNORE`，**绝不可写 `0`**（那是 STOP=拦截）。

### 6.3 两道自动守卫（已落地，2026-09-02）—— 把铁律变成会报红的测试
以后这类回归一出现就拦在合并前，不再靠人肉排查：

- **GATE0（静态扫描，提交前跑）**：`python tools/lint_mouse_filter.py --tier default`
  - 扫所有 `.tscn`，找出"按钮下的**可见**装饰子节点且 `mouse_filter = STOP(0)`"。
  - `visible = false` 的节点自动排除（不可见不吃输入，非 BUG，避免误报）。
  - 默认层只报**显式 `= 0`**（= 有人写 0 想穿透，典型手误，零误报）；`--tier strict` 用于定期审计（含默认 STOP 的潜在隐患）。
  - 退出码：有高危发现 = 1，可接 CI 阻断。
- **GATE2（运行时结构断言，已接入 `run_all`）**：`tests/unit/test_ui_mouse_filter.gd`
  - 加载 `screens.json` 全部界面，`instantiate()`（不需场景树布局、同步执行）后遍历节点树，断言"**任意 BaseButton 的可见 Control 子节点不得为 STOP(0)**"。
  - 与静态扫描互补：静态查提交期、运行时查加载期；`.tscn` 声明树里的装饰节点全覆盖。（动态 `_build_ui()` 里手加的装饰子节点，记得显式设 `IGNORE(2)` 才同防。）
  - 当前 54 套件 / 0 ✗ 已含此测试。

### 6.4 出 BUG 先查"拾取"别查"逻辑"
遇到"不报错但某个按钮点不了 / 鼠标卡住" → **别翻逻辑，直接查鼠标拾取**：
1. `python tools/lint_mouse_filter.py --tier strict` 扫一遍，看有没有按钮装饰子节点仍是 STOP；
2. 或复刻无头拾取：取可疑界面每个按钮中心 `get_viewport().gui_find_control_at_pos(center)`，若落点不是按钮自身、而是某个 STOP 子节点 → 就是它吞的；
3. 修：把那个子节点 `mouse_filter` 改成 `2`（`replace_all` 一次改全同类型处）。

### 6.5 门禁非绿 = 禁止继续（本次顺带教训）
修复期间发现 `BattleScene.gd` 的 `_on_auto_pressed` 因缩进错（`eid` 在 `for` 循环外使用）早已**解析失败**，导致 GATE2 整条战斗图标测试编译失败——但红门禁一直没被处理，印证"多 AI 各自改、红了没人管"。
**铁律补充**：GATE1 / GATE2 一旦非绿（有 SCRIPT/PARSE/COMPILE ERROR 或 ✗），**立即修、禁止带着红门禁继续开发或合并**；红门禁是"别人刚改崩"的最强信号，优先级高于任何新功能。
