# 背包业务模块设计评审与一线大厂实现方案

> 评审角色：项目经理 × 程序员 × 架构师三视角
> 评审范围：`services/inventory/**` 及其全部上下游（shop / forge / alchemy / equipment / combat / quest / defeat_handler / InventoryScreen / SaveManager）
> 评审基线：2026-08-29 工程快照（Phase 2 系统填充中）

---

## 一、总评（TL;DR）

**架构骨架是对的，能打 75 分**：三栏分类、堆叠、负重、存档接口、EventBus 通知、配置驱动、不持有 Node——该有的分层意识都有，且是全工程少数带单测的服务。

**但当前实现存在 4 个会直接造成玩家资产损失的 P0 级 bug**（付钱不发货、扣料不掉产出、换装丢装备、实例 ID 撞车），**1 个功能级缺口**（丹药配置了 heal_hp，但全工程没有任何"使用物品"的入口——玩家有药吃不了），以及一批 P1/P2 的架构债。

一句话结论：**先止血（P0 一天内可修完），再补使用/事务两大能力，最后再做 UI 网格化。**

## 三、问题清单（按大厂 P0-P2 分级）

### P0：玩家资产损失类（必须立即修）

**P0-1 商店买入：钱扣了、货没到。**
`shop_service.gd:68-69` 先 `ps.spend_money(total)` 再 `inv.add_item(...)`，且**忽略 add_item 返回值**。背包满时 `add_item` 部分失败返回 false，钱已扣，货没进包，无回滚、无提示。
→ 一线做法：**先预检 `can_add`，再扣钱，再入包**；或整个交易做成事务（见 §4.3）。

**P0-2 锻造/炼药：材料扣了、产出丢了。**
`forge_service.gd:41-54`、`alchemy_service.gd:20-27` 都是先全量扣材料、后 `add_item` 产出。产出时背包满（主栏满）→ 产出静默消失。锻造主栏产物尤其容易触发（30 格）。

**P0-3 装备换装：原装备凭空蒸发。**
`equipment_service.gd:45-54` `unequip()` 先 `equipped.erase(slot)` 再 `add_item(item_id, 1, "unequip")`。背包满时 add 失败返回 false 被忽略——**装备从世界上消失**。
`equip()`（第 32-37 行）同槽已有装备时先调 unequip，把上述路径也带崩。装备逻辑还调用了 `GameManager.inventory_service`，属于服务层横向直调，重构时一并收口。

**P0-4 instance_id 用 `Time.get_ticks_msec()` 生成，同毫秒必撞。**
`inventory_service.gd:49`：`"%s_%d" % [item_id, ticks_msec]`。战斗掉落、批量入包时同一毫秒创建多个同 id 物品 → **instance_id 重复**。`get_instance_by_id` 永远返回第一个匹配——装备系统可能拿错实例。这颗雷等"按实例操作"的功能一多必炸。
→ 一线做法：全局自增序号 + 存档 max_id 恢复；或 `instance_id = "%s_%d_%d" % [item_id, ticks_msec, 自增计数]` 保底。

### P1：功能缺口 / 设计偏差

**P1-1 没有"使用物品"（use_item）路径。**
pills.json 配了 `heal_hp / heal_mp`，ItemEnums 定义了 `CONSUMABLE`，但全工程 grep 不到任何 use/consume item 的业务代码。**玩家现阶段无法吃药**，战斗中更没有用药策略（回合制 CRPG 里这是核心资源循环）。这是背包作为"资源枢纽"的最大功能缺口。

**P1-2 负重是假负重。**
`PlayerState.strength` 注释写"影响攻击/负重"，但 `BASE_MAX_WEIGHT=50` 是常量，从未与力量挂钩；`add_item` 不检查超重；超重无任何惩罚（跑不动/无法奔跑/属性惩罚都没有）。当前负重只是 UI 上一个数字。

**P1-3 装备存档丢实例维度。**
`EquipmentService.save()` 只存 `slot -> item_id`。装备被"抽离"背包时实例已删除，耐久（字段已预留从未使用）、来源、未来词缀全部丢失；unequip 又 `add_item` 生成全新实例。**装备从未真正拥有过实例身份**，与背包的实例模型割裂。

**P1-4 双轨数据模型，枚举是死代码。**
`ItemData`（Resource schema）+ `ItemEnums` 全套枚举定义了，运行时却全部用 JSON 裸字符串（`type: "material"`、`rarity: "common"`），只有 equipment.json 手写 `"flags": 64`。两套模型必然漂移：枚举加一项 JSON 不会跟，字符串打错字运行时静默落入 `main_slots` 兜底分支。

**P1-5 删除类操作无事务边界。**
`remove_item_by_id` 逐实例扣减，中途没有任何失败可能所以暂时安全，但 `forge` 的"多材料校验→逐个扣除"两步之间无原子性（单线程下靠调用方自觉）。一旦新增"批量合成/一次吃多个"需求就会写出扣一半失败的代码。**缺 `try_consume(items: Array) -> bool` 原子扣料接口**——锻造/炼药/未来商店回购全都需要。

### P2：打磨项（排期做，不救火）

| # | 问题 | 位置 | 说明 |
|---|---|---|---|
| P2-1 | UI 是只读聚合列表 | InventoryScreen.gd:73-92 | 按名字聚合计数，丢失实例；无使用/装备/丢弃/排序/拆分/拖拽；`item_slot`、`tooltip` 组件目录是**空的** |
| P2-2 | UI 全量重建刷新 | `_refresh()` | 事件一来 queue_free 全部重建；30 格无所谓，网格化后必须改脏刷新 |
| P2-3 | 缺 `inventory_full` / 容量查询 API | — | 调用方无法预检，只能靠返回值猜；事件里也没有"哪些没装下"的溢出信息 |
| P2-4 | 团灭丢物规则硬编码 | `lose_some_non_rare_items` | `rarity=="common"` 写死在代码，违背本工程"数值全进 JSON"铁律，应做成难度表字段 |
| P2-5 | 读档信任存档 weight | `load()` 第 239 行 | 改配置后旧档负重错，应 load 后 `_recalculate_weight()` |
| P2-6 | 自身 signal 双发冗余 | Service 内 3 个 signal | 没有任何连接者，与 EventBus 转发重复，留一套即可 |

| P2-8 | `can_forge` 未乘 count | forge_service.gd:77 | 与 `forge()` 的 `* count` 不一致，未来批量合成时 UI 预检会误判 |
| P2-9 | 存档槽位顺序不保真 | `_serialize_bag` | 跳空槽存、find(null) 塞回，顺序会重排；当前可接受，做拖拽后必须存 `{idx: inst}` |

## 四、一线大厂的背包业务实现逻辑（目标设计）

以下方案**严格贴合本工程现有分层铁律**（services 无 Node、数值进 JSON、跨模块走 EventBus、GDScript 4.x 红线），不是空中楼阁。

### 4.1 领域模型：定义与实例彻底分离

```
ItemDef（静态，ConfigManager 持有）        ItemInstance（动态，InventoryService 持有）
├─ id / name / type / rarity             ├─ instance_id（全局唯一，发号器生成）
├─ max_stack / weight / price            ├─ item_id（回指定义）
├─ flags: 位标志(可卖/可弃/可堆/消耗/装备)  ├─ count / durability / max_durability
└─ use_effect / equip_slot / bonus_*     ├─ acquired_source / acquired_time
                                         └─ affixes[](未来词缀预留)
```

落地动作：
- **JSON 全部补上 `flags` 字段**，代码里所有"能不能卖/能不能丢/能不能堆"判断一律走 `ItemEnums.ItemFlag` 位标志，字符串 type 只决定进哪个栏位。
- `ItemData` Resource 若半年内不用编辑器 .tres 工作流，**删掉或降级为文档**，别维护两套。
- 新增 `ItemFlags` 辅助静态类：`is_stackable(def)` / `is_sellable(def)` / `is_consumable(def)`，禁止散落 `data.get("flags", 0) & 16` 这种裸判断。

### 4.2 服务 API 契约（读写分离 + 全操作带原因）

```gdscript
# ---- 查询（Query，随时可调，无副作用）----
get_item_count(item_id) -> int
get_free_capacity(bag_type) -> int           # 还能塞几个（按 max_stack 折算）
get_weight_ratio() -> float                  # 0.0~1.0+，UI 进度条与超重判定共用
can_add(item_id, count) -> bool              # P0-1/P0-2 的预检依据
can_consume(defs: Array) -> bool             # 批量材料预检

# ---- 写入（Command，全带 source 原因枚举）----
add_item(item_id, count, source) -> AddResult   # {added, overflow}，不再只回 bool
add_items(list: Array, source) -> AddResult     # 事务批量：要么全进，要么一条不加
try_consume(list: Array, source) -> bool        # 原子扣料：校验+扣除不可分割
remove_instance(iid, source) -> bool
move_instance(iid, to_idx) / split_stack(iid, n) / sort_bag(bag_type)
use_item(iid, context) -> UseResult             # 见 4.4
drop_item(iid, count) -> bool                   # 走 flags DISCARDABLE 检查
```

关键规则：
- **所有写操作必须带 `source`**（`"shop_buy"` / `"forge:recipe_id"` / `"drop:enemy_id"` / `"quest:q_001"` / `"player_use"`），现有代码已有雏形，补齐枚举防止裸字符串漂移。
- **add 事件携带溢出量**：`inventory_add_overflow(item_id, lost_count)`，商店/锻造 UI 据此弹"背包已满，损失 X"——比静默丢失好一百倍。

### 4.3 事务化：P0 三连的根治方案

大厂做法是**先冻结校验、后原子提交、失败整体回滚**。对单线程 Godot 不需要真的 undo 栈，"预检→执行"两段式就够了：

```gdscript
# shop_service.buy() 重写示意
var need: AddResult = inv.query_add(item_id, count)     # 纯计算，不落盘
if need.added < count:
    return FAIL_BAG_FULL                                 # 钱分文不动
if not ps.spend_money(total):
    return FAIL_NO_MONEY
inv.add_item(item_id, count, "shop_buy")                 # 预检过，这里必成功
```

同样模式复制到：
- `forge/alchemy`：`can_consume` + `query_add(output)` 双预检 → 扣料 → 产出；
- `equipment.equip/unequip`：换装 = **一次事务**（卸下产物与装上新装备在同一批预检里算空间，而不是先 erase 再 pray）。

进阶（Phase 3 再做）：引入 `InventoryTransaction` 对象收集 pending_ops，`commit()` 时统一应用并批量发一次 `inventory_changed(reason)`——UI 一次刷新而不是 N 次。

### 4.4 使用物品（use_item）——本阶段最值得补的功能

```
ItemDef.use_effect = { "kind": "heal", "hp": 50, "mp": 0, "combat_only": false }
```

- 背包新增 `use_item(iid, context) -> UseResult`：校验 flags 的 CONSUMABLE → 扣 1 个 → 按配置调 `PlayerState.heal()/consume_mp()` → 发 `item_used(item_id, effect)` 事件。
- **战斗内**：BattleScene 行动菜单加"物品"页签，列出 CONSUMABLE 且 `combat_only` 允许的实例，使用消耗一次行动机会——回合制 CRPG 的资源策略感立刻成立。
- 效果种类未来扩 `buff` / `cure` / `exp`，用 `kind` 分发，**不要**给每个丹药写一个 if。

### 4.5 实例 ID 发号器（P0-4 根治）

```gdscript
# InventoryService 内
var _next_iid: int = 1
func _new_instance_id(item_id: String) -> String:
    var id := "%s#%d" % [item_id, _next_iid]
    _next_iid += 1
    return id
```
- `_next_iid` 进存档（save 里多存一个 `next_iid`），读档恢复，永不重复。
- 顺手把 `ItemInstance.serialize` 加 `ver` 字段，为将来存档迁移留钩子（大厂存档必带 schema_version）。

### 4.6 负重做真（低成本方案）

- `difficulty_table.json` 或 `world_config.json` 加 `weight_per_strength: 2.0`；`max_weight = BASE + strength × 系数`。
- `add_item` 入包前查 `get_weight_ratio()`，超重时**允许塞入但触发状态**（移动减速/无法奔跑），或直接拒绝——二选一，写进 GDD 由策划定，代码只读配置。
- `inventory_weight_changed` 的第二个参数从常量改为动态 max。

### 4.7 UI 渲染契约（Phase 2 后半段）

- 补齐空目录里的 **ItemSlot 组件**（格子：图标 + 数量角标 + 稀有度描边 + new 角标 + tooltip 挂点），背包 = `GridContainer(30)` × 3 页签，这是装备/商店/锻造面板将来共用的底座。
- 刷新走**脏标记**：Service 里已有的 `_dirty` 提升为公开 `is_dirty()/clear_dirty()`，UI 只在打开时和收到事件后增量刷变化的槽位，不整体重建。
- 聚合列表保留为"材料箱"快捷视图，主背包必须逐实例显示（同一武器两把要能分别装备/卖出）。

### 4.8 测试策略（边界用例矩阵）

在现有 `test_inventory_service.gd` 基础上补：

| 用例 | 断言 |
|---|---|
| 背包满时 add | added<count、overflow 事件、原物不动 |
| 满包时 buy/forge/unequip | 钱不动 / 材料不动 / 装备不消失（P0 回归） |
| 同毫秒批量入包 100 件 | instance_id 全局唯一 |
| try_consume 中途不足 | 全量不扣 |
| 存读 roundtrip 含 next_iid | 恢复后新 iid 不冲突 |
| 堆叠边界（0 / max_stack / max_stack+1） | 计数精确、空槽回收 |
| 超重入包 | 按配置拒绝或放行+状态 |
| 团灭丢物 | 只丢主栏 common、quest 材料栏不动 |

## 六、值得保留的优点（评审不是只挑刺）

1. `ISaveable` 注册制存档 + `test_save_roundtrip` 已跑通，底子比多数独立项目好。
2. 三栏自动归类 + `_bag_for_item` 单点决定归属，未来加"仓库/坐骑包"只需加分支。
3. 配置容错层（`_is_valid_entry` + 引用校验 + 错误落盘 `config_errors.log`）是大厂级思路。
4. 团灭丢物的 while 索引遍历注释写清了为什么不用 for-in——这种"踩坑即文档"的习惯请保持。
5. 全链路 `source` 字段预留（drop/quest/forge/unequip），为审计和成就系统打了好底子。
