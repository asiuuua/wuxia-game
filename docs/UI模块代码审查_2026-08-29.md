## 二、真正做得好的地方（不偏袒也要承认）

- **单一编排闸口**：`UIManager` 收口 6 层 CanvasLayer、屏幕栈、弹窗生命周期（经 `EventBus.popup_close_requested`，弹窗自己绝不自毁）——解耦干净。
- **数据驱动到位**：加界面只动 `screens.json`；加菜单项只动 `menu_config.json`；改手感只动 `ui_anim.json`；配色集中在 `ui_theme.gd`。**零代码改动即可扩展**。
- **基类 DRY**：`BaseScreen`（铺满+安全区+键盘导航+取消+顶层守卫）与 `PopupBase`（`make_glass_panel`+`request_close`）消除大量样板。
- **组件化高质**：`UIFeedback`（pivot 居中缩放/tween kill/键盘焦点三处真实修复）、`MenuItem`（FOCUS_NONE 防焦点悬挂的根因注释）、`IconRegistry`、`UICenterUtils`（修 Godot 4.7.2 `PRESET_CENTER` 坑）都是工业级封装。
- **HUD 四面板**：纯展示、只订阅事件、`_exit_tree` 断信号；任务栏可拖拽+落点持久化（含脏存档守卫）。
- **测试覆盖厚**：`test_hud_panels / popup_lifecycle / screen_centering / menu_config_driven / ui_center_utils / icon_registry / inventory_smoke / m5~m8_smoke` 等，远超多数同体量项目。

## 三、缺陷清单（按严重度，均附文件定位）

### P1（会真实触发、影响核心体验）
- ~~**`GameMenuScreen.gd` 无 ESC 关闭**~~ → 已修：在 `PopupBase` 加统一 `ui_cancel→request_close`（`close_on_cancel` 范式，默认开），GameMenu 及全部未自管 ESC 的 PopupBase 子类（Shop/Attributes/Sect/Alchemy/Forge/Abilities/BondRomance）自动获得 ESC 关闭，与既有 `Inventory/Equipment` 行为一致；`EscMenu` 继承 `BaseScreen` 且 `close_on_cancel=false`，不受影响。
- ~~**`ConfirmDialog.gd` 确认回调双重执行**~~ → 已修：原 `_closing` 只守 `_close()`，但 `_confirm_callback.call()` 在 `pressed` 与 `_unhandled_input(ui_accept)` 两条路径各跑一次（确认钮聚焦时按 Enter 同时触发两者）。改为 `_closing` 守卫前置到 `_on_confirm/_on_cancel` 入口，回调与信号只触发一次。

### P2（边界/竞态/一致性）
- ~~**`CelebrationOverlay.gd` 异步竞态**~~ → 已修：`_apply_media` 经 `ResourceManager.acquire_async`，原 `_on_media_ready` 未判容器有效性即 `add_child`；若 CG 在加载完成前被关/跳过，回调把节点挂到已 `queue_free` 的 `_media_box` 上 → 崩溃或泄漏。新增 `_is_closing` 标志 + `is_instance_valid(self/_media_box)` + `path != _media_path` 过期丢弃三重 guard，关闭/跳过/_exit_tree 置位。
- **`BondRomanceScreen.gd` 调试按钮进生产**：207 行"测试：拉满所有好感"、215 行"满好感(测试)"直接调 `romance_service.debug_max_affection`。玩家在姻缘界面可见可点 → 一键满好感，属未完成收口（建议 `$debug` 开关或发布前删除）。
- **`DialogOverlay.gd` 固定像素 + 越权逻辑**：面板 `position=Vector2(80,400)`、`size=(880,200)`（77-78 行）不居中、不随分辨率、不套安全区，非 1080p/竖屏安卓会错位或出屏；且直接调 `GameManager.quest_service.accept()`、`EventBus.cmd_start_combat.emit()`、`UIManager.close_screen(self)`（243-265 行），违背"UI 只渲染/emit，逻辑归服务"铁律，是"上帝叠加层"。

### P3（规范违反/小隐患）
- **主题铁律被多处违反**：`ui_theme.gd` 明令"禁止散落 `Color(...)` 字面量"，但 `DialogOverlay`(93/109)、`ConfirmDialog`(132 行 `_apply_glass_button_style` 的 `Color(0.05,0.06,0.09,0.90)`)、`CelebrationOverlay`(51/63/80)、`Tooltip._rarity_color`(78-84) 共 5+ 处裸写颜色——根因是 `UIPalette` 缺"遮罩/对话/CG 边框/稀有度"等条目，规范未强制、执行不一致。
- **`Tooltip.gd` 裁剪**：Tooltip 作为 `InventoryScreen` 子节点，被背包面板裁剪/层级限制，贴边物品提示会被切。
- **`InventoryScreen.gd:206` 拆分**：`int(count)/2` 在物品被并发移除后 `get_instance_by_id(iid)` 返回 null → `.count` 崩溃（概率低）。
- **`EquipmentScreen.gd` 双刷新**：`equip()` 后既显式 `refresh()` 又经 `EventBus.equipment_changed` 再 `refresh()`，非幂等；装备钮未挂 `UIFeedback`（与其余 UI 不一致）。

## 四、六角色点评要点

- **架构师**：`UIManager` 约 390 行、集层初始化/注册表/开关/缓存/Toast/溢出/动作路由/安全区于一身，**单点故障且难单测隔离**；最大分叉是 `BaseScreen` 有 `close_on_cancel` 而 `PopupBase` 没有——ESC 处理应下沉到 `PopupBase` 基类统一（本轮已补，消除各屏手写遗漏）。`CelebrationOverlay` 直引 `core/resource_manager` 破了 UI→core 的层界。
- **前端**：视觉语言统一（玻璃+金边+居中），但**全模块固定像素、无 viewport 缩放适配**，DialogOverlay 甚至不用居中锚点；徽标逻辑在 `top_right_menu_panel` 与 `GameMenuScreen` 里都硬编码成"姻缘"语义，加第二个带徽标项就接不上。
- **性能**：缓存弹窗（`cache:true`）、背包脏刷新复用槽位、CG 关闭 `evict` 归还引用——都正确。但 `UIFeedback` 每次悬停读 `ConfigManager` 动效令牌（需确认是否缓存解析结果，否则每次 hover 解析 JSON）；Toast 每次 `new Label+StyleBox+tween` 无池化；列表类屏（装备/背包/结缘）`refresh()` 仍 `queue_free` 重建子节点，未池化。
- **运维**：加界面/菜单/动画只改表是巨大红利；但铁律未强制、UI 主题色散落、`UIManager` 单点故障使任何 UI 回归都可能波及全模块。
