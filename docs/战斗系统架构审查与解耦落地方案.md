## 2. 对照你的方案：哪些逻辑是对的（举证）

### ✅ 完全一致 / 方向正确的点

1. **等轴测换算**
   你的 `logic_to_screen`：
   ```gdscript
   sx = (logic_x - logic_y) * tile_w * 0.5
   sy = (logic_x + logic_y) * tile_h * 0.5
   ```
   现有 `BattleGrid.grid_to_world_iso`：
   ```gdscript
   return Vector2((pos.x - pos.y) * tile_w * 0.5, (pos.x + pos.y) * tile_h * 0.5)
   ```
   **逐字符一致**。菱形布局、2:1 比例、斜 45° 效果已落地。✅

2. **逻辑与画面分离**
   你的架构分层表（Resource / Manager / Unit / View）与现有四层（Resource 配置 / CombatService+Core / CombatCharacter / BattleGridNode+BattleEntity）一一对应，且现有更彻底（逻辑层零 Node）。✅

3. **曼哈顿距离做射程**
   你的 `get_manhattan_distance` 与现有 `is_target_in_range` 都用 `abs(dx)+abs(dy)`。✅

4. **朝向基于逻辑坐标差值**
   你的 `calc_facing(from,target)` 只算 `delta=target-from`，与地图尺寸无关——现有逻辑也从未把屏幕尺寸塞进朝向计算（方位由 `grid_pos` 决定）。✅ 你补的「斜视角只是视觉偏转、逻辑仍是上下左右 4 向」是**正确且重要**的提醒。

5. **镜头自动适配**
   你给的 `auto_fit_camera` 思路（算四角→算 zoom）是对现有「固定 `bf.position` 居中」的有益升级，尤其大地图（22×18）会超出视口，必须加 zoom。✅ 建议采纳。

### ⚠️ 你方案稿里的技术坑（落地前必须修正）

| 坑 | 方案稿写法 | 问题 | 正确做法 |
|---|---|---|---|
| TileData 不能 `@export` | `class_name TileData extends RefCounted` + `@export var tile_grid:Array[Array[TileData]]` | **RefCounted 无法被 `.tres` 序列化/导出**，`@export` 在 RefCounted 上不生效 | 继承 `Resource` 而非 `RefCounted`；或直接用 `Dictionary` 描述每格（现有就这么做，更省事） |
| BattleManager 是 Node2D | `extends Node2D` + 全局态 `current_map`/`unit_list` | 违反「业务层不持有 Node」铁律；Autoload Node 在切场景时生命周期诡异 | 做成 `RefCounted` 或放进 `GameManager`，不挂场景树 |
| 全局 `current_map` 单例态 | 多场战斗串行时被覆盖 | 若未来支持「战斗内再触发战斗」会串数据 | 现有把状态封在 `CombatState` 里，更安全 |
| `queue_free_children` 清场 | 每场战斗 free 全部节点 | 大地图数百格 + 数十单位，同步 free 会卡帧；且不如池化 | 现有 `CombatEntityPool` 复用已经更优，保留 |
| 坐标换算写死 tile 尺寸 | `tile_w=128,tile_h=64` 写死 | 换美术比例要改代码 | 现有 `tile_width/tile_height` 是属性，可调 |

**结论**：你的方案「思想全对，代码稿需按现有工程纪律改写」。建议以现有 `BattleGrid` + `CombatService` 为基座，而不是另起 `BattleManager`。

## 4. 现有架构优点 / 缺点

### 优点（必须保留，别动）
- 逻辑层 100% `RefCounted`，切场景零残留、可 headless 单测（你方案想达到但没达到）。
- `CombatEvent` 事件流 + `CombatEventRenderer` 统一演出，逻辑与表现彻底分离。
- 对象池（`CombatEntityPool`）+ 飘字池，复用而非 new/free。
- 确定性随机 `SeededRNG`，可复现、可存档、可单测（梦幻西游服务端权威思想的单机版）。
- 网格逻辑全纯函数，与尺寸无关（你方案核心诉求已满足）。

### 缺点（落地要补）
1. **单玩家单位**：`state.player` 是单一引用，无法表现「主角的同伴同场」。多 NPC 同场景的「友方多单位」不支持。
2. **grid 内嵌在 battle 配置**：每场战斗一份，但「同一底图所有遭遇共用一套地形」需手动在多个 battle 里复制 grid，易漂移。应提为独立「战棋布局资源」。
3. **绘制未批处理**：`BattleGridNode._draw` 每次高亮变化 `queue_redraw` 重画**全部格子**；几十单位 + 几十特效时绘制开销随格子数线性增长（大地图尤甚）。
4. **场景卸载同步释放**：`_exit_tree` 同步 `clear()` 池，人数多/特效多时可能掉一帧。
5. **无地形高度**：等轴测下高度差能极大增强「斜 45°」立体感（参考图里的桥/台），目前只有平面障碍。

## 5. 落地扩展方案（针对你的真实需求）

### 5.1 任意底图复用战斗逻辑：加「底图 → 战棋布局」映射层
不要改 `CombatCore`/`BattleGrid`（它们已尺寸无关）。在**配置层**加一层：

```
data/configs/maps/<底图id>.json
{
  "tactical_layout": "res://data/configs/battles/grids/courtyard_12x10.json"
}
```
`cmd_start_combat` 解析时：先查底图布局，再合并到 battle 的 `grid` 配置。
**效果**：竹林底图所有小怪自动共用同一套 12×10 斜 45° 布局；换底图只换一份 JSON，战斗代码零改。

### 5.2 多 NPC 同场景出
- **多敌人（敌方）**：已支持（`enemy_ids` + `deployment` 逐敌定位）。把遇怪点配置成多个 `enemy_id` 即可。
- **多玩家单位（组队）**：需把 `state.player` 从单引用升级为 `state.player_party: Array[CombatCharacter]`，`CombatCore` 的 `player_basic/player_skill` 增加 `actor_id` 参数。这是**唯一需要动逻辑内核**的改造，建议单独排期。
- **同屏多独立 NPC 实体**：世界地图（TownScene）上多个 NPC 各自带 `battle_id`，走近任一个触发对应战斗——现有 `GameManager.start_battle` 已支持，无需改。

### 5.3 数十特效极致帧率
现有池化已就位，再补三招：
1. **绘制批处理**：`BattleGridNode` 改用 `MultiMeshInstance2D`（一个 draw call 画全部同色格），高亮变化只改 `instance_color`，不重画几何。
2. **限制 redraw 频率**：高亮更新合并到一帧（`set_deferred`/accumulate），避免一次移动触发多次全图重绘。
3. **特效预算**：飘字池设上限（如 64），超出 oldest 复用；粒子/打击特效用 `GPUParticles2D` 而非逐个 Node。
4. **CanvasGroup / 合批**：单位血条用 `CanvasItem` 合批材质，减少 state change。

### 5.4 进入/卸载场景不卡顿
1. **分帧释放**：`_exit_tree` 不再同步 `clear()`，改为 `call_deferred` 把池清空分到 2~3 帧。
2. **预载 UI**：战斗场景 `.tscn` 提前 `preload`，遇怪瞬间只切换不编译。
3. **保留池常驻**：`CombatEntityPool` 跨战斗保留（已在 `_exit_tree` 只 `clear` 空闲项，已接近最优），避免反复 new。
4. **资源回收**：`GameManager.start_battle` 已调 `ResourceManager.reclaim_all()`，保留。

### 5.5 朝向 / 坐标标准化（采纳你的提醒）
加 `enum FACING {UP,DOWN,LEFT,RIGHT}` 到 `CombatCharacter`，`move_unit` 时按 `delta` 算朝向存枚举；
视图层 `BattleEntity` 拿到枚举切贴图。逻辑层永远不知道屏幕，斜 45° 映射只在视图做。
**这正好补上现有「单位没有朝向」的空缺**（现有 `grid_pos` 只记坐标，没记面朝）。

### 7.5 胜负判定修正 + 组队闭环（2026-08-30 补）

> 用户实测「图二战棋教头」队伍反馈：**胜负判定当时只看主角**，友方 NPC 未计入玩家方。已修正。

**Bug 根因**
1. `CombatService.get_result()` 旧逻辑：`if _state.player.is_dead: return DEFEAT` —— 完全忽略友方 NPC。
2. 友方 NPC 从未被注入玩家方：`start_combat` 只建 `player` 与 `enemies`，`player_party`/`allies` 一直为空，故 `is_over()`（虽已写对）也只看到主角。

**修正（同时满足三条铁律）**
- `get_result()`：敌方全灭→胜利；否则 `is_player_side_wiped()`→失败；否则胜利。
  - 友方 NPC 单独阵亡 ≠ 失败 ✅
  - 主角阵亡但友方 NPC 存活 ≠ 失败 ✅
  - 主角 + 全部友方 NPC 同时阵亡 = 失败 ✅
- `CombatState.is_player_side_wiped()`：主角 + `player_party` + `allies` 全部阵亡才算；单玩家退化为只看主角。
- `is_over()`：同步纳入 `allies`。
- `start_combat._build_player_side(battle, ps, edm, state)`：把 **战斗配置 `allies`**（数据模板复用 `enemies.json`，无模板则用主角属性 0.7~0.8 倍兜底）与 **`player_state.companion_ids`（存档同伴）** 注入 `player_party`（`is_player=true`）。
  - 这样友方 NPC 自动：进入玩家方 → 被敌人 AI 集火、纳入回合序列（7.3.2）、被玩家操控（7.3.1）、计入胜负与结算快照。
- `finalize._build_snapshots()`：玩家方友军一并纳入，供任务系统判定。

**验证**：新增 `test_defeat_rule.gd`（5 项全绿）+ `battles.json` 测试战斗 `tactical_ally_inject`；双闸门 **40 套件 0 失败**。

**让友方 NPC 在某场战斗登场**：在该战斗配置加 `"allies": ["npc_id"]`（npc_id 在 `enemies.json` 有战斗属性即复用，否则用主角兜底属性）；或设置 `player_state.companion_ids`。两者都会被注入玩家方并落入 7.3.1/7.3.2 的全部链路。
