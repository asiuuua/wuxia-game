# 无立场裁定：两套 P4–P7 工业化实现谁在实际落实上更胜

> 立场声明：本文件刻意不以任一实现方利益为中心，全部结论以**磁盘上双方真实源码**为唯一依据。
> 左版 = `D:\武侠游戏`（静态 class_name / acquire 系列 API，已推 Gitee `master`）
> 右版 = `D:/wuxia-game-fresh`（Autoload / load_cached 系列 API）

---

## 一、对方给的 4 条"硬伤"逐条核验

### 指控 1：`class_name ResourceManager` 与 autoload 名 `ResourceManager` 同名 → 两套进同一工程符号冲突、跑不起来
**核验结果：误植（作为"我方独立工程的缺陷"是假的）；但作为"两版合并的 blocker"是真实的、且是双方面责任。**

- 左版 `project.godot`（autoload 段 22–40 行）：**无任何 `ResourceManager` 注册**。`resource_manager.gd:13` 的 `class_name ResourceManager` 是纯静态类，无 Autoload。→ 左版**独立工程零冲突**。
- 右版 `autoload/resource_manager.gd:13` 注释明确写："autoload 脚本不写 class_name（与单例名 ResourceManager 冲突，遵循 ConfigManager 模式）"。→ 右版**刻意规避**了 class_name，仅以 Autoload 单例名 `ResourceManager` 存在，独立工程也零冲突。
- **真相**：冲突只发生在"把两版塞进同一个工程"时——左版的静态 `class_name ResourceManager` 与右版的 Autoload 单例 `ResourceManager` 撞名 → Godot 报重复全局名。**这是两版都叫 "ResourceManager" 导致的合并 blocker，不是左版单方面的缺陷**。对方把它表述为"对方（静态版）的冲突"，是归因错位。

### 指控 2：`reclaim_all()` 反向侵入子系统（直接调 `PortraitCacheManager.clear()` + `CombatEntityPool.clear()`）→ 违反单向依赖
**核验结果：属实但被夸大（是 intra-layer 耦合，非跨层硬违规）。**

- 左版 `resource_manager.gd:141-142` 确实调用了这两个 `.clear()`。
- 但 `PortraitCacheManager`（`core/portrait_cache_manager.gd:12`）与 `CombatEntityPool`（`core/combat_entity_pool.gd:11`）**都位于 `core/` 层**，与 `ResourceManager` 同层。项目"单向依赖"铁律约束的是**跨层顺序**（autoload→core→data→services→scenes），`core→core` 属同层内部引用，不构成该铁律所指的"地基→业务子系统"反向侵入。
- 性质：一个"统一回收总闸"的便利耦合，可维护但非致命。风险等级：低。

### 指控 3：`force_reclaim_all()` 连 refcount>0 都清 → 误调即正在用的资源瞬间消失（footgun）
**核验结果：API 确实存在，但是"死代码"——全工程无任何调用点，不构成实际风险。**

- 左版 `resource_manager.gd:146-150` 定义了 `force_reclaim_all()`。
- 全仓 grep `force_reclaim_all`：**仅定义 + 文档提及，零调用**（不在任何运行路径中）。
- 性质：一个显式命名为 `force_` 的"核选项"，存在但未接线。属于设计上的潜在 footgun，但**非活跃 bug**。

### 指控 4：静态空闲表跨引擎会话常驻（`CombatEntityPool._free_entities` 是 static var）→ 忘 release 则实体脱离树仍被静态数组引用、跨场景累积泄漏
**核验结果：被夸大（有界 + 不会无限累积）。**

- 左版 `combat_entity_pool.gd:17` 确为 `static var _free_entities: Array[BattleEntity]`。
- 但有 `MAX_ENTITIES=64` 硬上限 + `_trim_entities()` 超额即 `queue_free`（`combat_entity_pool.gd:75-78`）。静态空闲表**长度恒定 ≤64**，不可能无界增长。
- 关键机制澄清：**静态数组只收"已 release"的脱离树实例**。若某路径"忘了 release_entity"，该实体仍挂在战斗场景树上（作为子节点），随场景释放一起被释放——**它根本不会进入静态数组**，因此"脱离树却被静态数组引用"的场景在实际代码里不会发生。忘 release 的后果仅是"该实例不被复用、下次 new 一个新的"（轻微低效），而非内存泄漏。
- 性质：理论担忧，工程上不显现。风险等级：低。

**小结：4 条指控中，作为"左版独立工程的硬伤"——0 条完全成立；作为"合并 blocker / 设计气味"——部分成立但均被对方夸大。**

## 二、对方自称优势（含其自身隐患）的核验

| 对方自称 | 核验 | 备注 |
|---|---|---|
| "process_frame 泵的常规连接，标准做法" | **属实** | 右版 `autoload/resource_manager.gd:189-202` 的 `_ready` 里 `get_tree().process_frame.connect(_on_process_frame)`。两版都有泵，左版是静态 `_ensure_pump`（Engine.get_main_loop()），右版是 Autoload `_ready`。**两版等价**。 |
| "release 保留条目供 TTL 清扫（已修过 bug）" | **属实** | 右版 `release()`（:89）仅减计数，归零后由 `reclaim_idle`/`evict` 清。其 `evict()`（:99）关闭界面时立即释放——**这一点右版确实比左版（release 后等 5s TTL）更及时**。 |
| "PoolManager 单例持有飘字引用但有界（max_size 上限）" | **部分属实，但藏自身 footgun** | `object_pool.gd:11` 默认 `_max_size=50` 有界 ✓；但 `acquire()`（:37-40）在 `not _auto_expand 且 active>0` 时会 `_active.pop_front()` **偷一个在用节点** reset 复用 → 飘字/特效串台 bug（默认 `auto_expand=true` 不触发，但属潜在错误路径）。且 `ObjectPool` 是 `RefCounted` 持有 `_parent: Node` 引用，父节点释放后易成悬空引用。 |
| "无命名冲突、无跨模块侵入、无 footgun API" | **不成立** | 命名冲突在合并场景存在（见指控1，右版 Autoload 名正是冲突源之一）；"无跨模块侵入"——Autoload 本身就是被全工程依赖的跨模块单例；"无 footgun"——其 `ObjectPool` 偷活跃节点即 footgun。 |

**对方评估中的事实错误（必须指出）：**
- 对方称"对方 CG 泄漏（它没漏）"——**与事实相反**。左版 `CelebrationOverlay` 原 `acquire_async` 后从不 `release`，引用计数永不归零，CG 大媒体常驻，已修复于 `c2b0d03`。即左版**确实漏过、已修**；右版用 `evict()` 关闭时释放，**右版本身不漏**。对方说"它没漏"指左版没漏，是错的。
- 对方的"后期稳定性我方更胜"结论，建立在"命名/架构/footgun 三处硬伤"之上——但三处要么误植、要么夸大、要么是死代码，其结论缺乏代码支撑。

## 三、你要求的 6 个维度实测对比

### ① 超长文本（1M+ 对话行）
**结论：平手（继承 P1 分片，两版一致）。**
- 两版 `dialogue_service.gd` **逐字相同**；分片逻辑在 `ConfigManager.get_dialog`（KB 级索引 + 内容按需懒加载），属共享地基，忽略行尾 CR 后两版一致。
- 左版多一处 P5 超集：每行 `voice` 字段（数据驱动语音），右版无。→ 左版**轻微胜出**（功能超集，非性能差异）。

### ② 多对话（并发/密集渲染）
**结论：平手。**
- 条件预检缓存（`_cond_cache`，1s TTL）、编译后对话缓存（`_parsed_cache`）两版完全相同。多对话推进/选项渲染的求值开销一致。

### ③ 多 NPC 调用（数百 NPC 独立/分支/条件剧情）
**结论：平手（继承 P3 隔离 + 条件缓存，共享）。**
- P3 隔离、cond 缓存均为共享地基，两版一致。无差异。

### ④ 战斗弹窗的卸载 / 实体复用
**结论：左版更完整。**
- **左版**：`BattleScene:104/110` + `tactical_battle_scene:92` 经 `CombatEntityPool.acquire_hud/acquire_entity` 取用；战斗结束 `_release_all_huds()`（:345→347/352）与 `_release_all()`（:456→460）**归还实体与 HUD 回池**；池有界 64、`clear()` 在场景切换统一释放。→ **实体 + HUD 双双复用，多场战斗内存恒定**。
- **右版**：`BattleEntity.new()`/`UnitHud.new()` **直接 new（无复用）**（BattleScene:57/108、tactical:106）；`PoolManager` **仅用于飘字 pop_text**（`tactical_battle_scene:88/96` register/unregister）。→ 实体/HUD 每场 new/free 抖动，多场战斗 GC 压力大；仅飘字复用。
- 这意味着你的"大批量敌人、多场战斗实体复用、零内存泄漏"目标，**左版落实更彻底**。

### ⑤ 性能的极致优化（加载不卡帧）
**结论：左版在"加载"维度决定性胜出；右版在"关闭释放"维度略优。**
- **左版 CG/媒体加载**：`acquire_async` → `StreamingMediaLoader.request` → `ResourceLoader.load_threaded_request`（**后台线程**）→ `process_frame` 泵回调。主线程**零阻塞**，大视频/立绘流式不卡帧。✅ 命中"CG视频流式加载"目标。
- **右版 CG/媒体加载**：`CelebrationOverlay._apply_media` 走 `ResourceManager.load_cached()` → `resource_manager.gd:79` 的 `res = load(path)`（**主线程同步阻塞**）。大 CG 视频/贴图加载会**直接卡帧掉帧**（注释说"超大音频可改用 stream_resource"，但 CG 界面本身没用）。❌ 流式目标落空。
- **关闭释放**：右版 `evict()` 立即释放 ✅；左版 `release` 后等 TTL（~5s）才由 `reclaim_idle`/`reclaim_all` 释放（已修泄漏，但有时间窗）。右版此处更及时。

### ⑥ 后期稳定性
**结论：左版实际运行时风险更小；右版"架构洁癖"主张被自身违规抵消。**

左版真实风险（均已评估，均低）：
- `force_reclaim_all` footgun → **死代码，零调用**。
- 静态池跨会话常驻 → **有界 64，不累积**。
- `reclaim_all` 耦合 → **core→core 同层，可接受**。
- CG 释放有 5s 时间窗（已修泄漏）→ 轻微。
- **零新增 Autoload** → 全局单例少，生命周期简单。

右版真实风险（对方未提）：
- **新增 2 个 Autoload**（`ResourceManager` + `PoolManager`）→ 直接违反项目"不增新 Autoload"铁律；Autoload 生命周期复杂、全局可达，反而增加耦合面。
- `ObjectPool.acquire` 偷活跃节点（auto_expand=false 路径）→ 飘字/特效串台潜在 bug。
- `ObjectPool` 为 `RefCounted` 持有 `_parent` Node 引用 → 父节点释放后悬空引用风险。
- **CG 主线程阻塞加载** → 大资源下帧率抖动、输入延迟，是真实运行时不稳定源。

**裁定：右版声称"后期稳定性我方更胜"，但代码显示其有 2 处铁律违规 + 阻塞加载 + 池 footgun，而左版的"硬伤"均被夸大或死代码。就"实际运行时长期稳定"，左版风险更小。**

## 四、诚实总裁定论

**谁在实际落实上更胜：左版（`D:\武侠游戏` / 静态 acquire）总体更优**，主要凭三点硬落实：
1. **真·异步流式加载**（后台线程，不卡帧）——直接命中你"CG视频/大图加载"的扩容硬需求；右版此处是同步阻塞，目标落空。
2. **战斗实体 + HUD 全量池化并接线**（acquire/release 闭环，有界 64）——直接命中"多场战斗实体复用、零泄漏"；右版仅飘字池化，实体/HUD 仍每场 new/free。
3. **零新增 Autoload**——遵守项目铁律，全局单例少，生命周期更简单；右版反加 2 个 Autoload 违反铁律。

**但必须如实承认左版的相对弱势（右版更优或左版该改之处）：**
- 右版 `evict()` 关闭即释放，比左版"release 后等 TTL"更及时——左版可在 `CelebrationOverlay` 关闭时直接调 `ResourceManager` 的等效 `evict`/立即清，消除 5s 时间窗。
- 右版**每场景 register/unregister 的池生命周期**比左版"全会话静态池"作用域更精准（左版静态池跨场景常驻，虽不漏但作用域偏粗）。
- 左版 `reclaim_all` 耦合、`force_reclaim_all` 死代码 footgun 是真实气味，应清理（删死代码 / 把耦合降级为事件订阅）。
- 右版 `ResourceManager` API 更丰富（pin/unpin/evict/acquire_sync 别名），可用性更好。

**对对方评估的纠偏：**
- 4 条"硬伤"作为左版独立缺陷均不成立；作为合并 blocker 是双方面责任。
- "CG 没漏"是事实错误（左版漏过、已修；右版本身不漏）。
- "后期稳定性我方更胜"结论缺乏代码支撑，其自身有 2 处铁律违规 + 阻塞加载 + 池 footgun。

**最终建议**：维持 `D:\武侠游戏` 为权威（已推 Gitee）。但应吸收右版两点长处：① 给 `ResourceManager` 增加 `evict()` 即时释放接口并在 CG 关闭路径调用（消除 5s 窗）；② 清理 `force_reclaim_all` 死代码、将 `reclaim_all` 对子系统的直接调用改为事件订阅，彻底消除耦合气味。右版 `backup-fresh-fork-pre-auth` 分支保留备查，其 `pin/unpin`、`evict` 接口设计值得借鉴。
