## 0. 结论先行（给决策者）

**不建议「不计成本推倒重写」。** 两个理由：

1. **规范本身禁止**。第 8 节「AI 不是架构师」、第 16 节 STOP 规则、第 23A 节闭环、第 204 节「ASK BEFORE CORE CHANGE」——架构级变更必须走 ACR→评审→ADR→分批迁移。直接重写属于 STOP-012（需求与架构冲突）与 STOP-015（架构文档与实际代码不一致）。
2. **第 171 节明确**：旧工程已有的「编译门禁、单测门禁、工程规范、引用校验、结构保护」**应升级，而不是丢弃**。本项目现有 **9 道门禁 + 73 个测试文件**，推倒重写会一次性摧毁这层安全网。

**建议方案**：**绞杀者式（Strangler Fig）分批迁移**——新能力按规范建，旧模块逐个迁移，全程保持门禁绿、游戏可运行。

**最高 ROI 切入点（强烈建议优先）**：规范 **0-C 章 Execution / Transaction / Rollback**。
理由：本项目历史上反复出现「扣钱不发货 / 扣料丢产出 / 换装丢装备」类 P0 资产损失缺陷（见 `docs/` 相关事故复盘与 `godot-asset-safe-fix` 工作流）。这类缺陷的根因正是**缺少事务原子性**。0-C 的 Transaction + Mutation Journal + Rollback 是对症的特效药，收益立竿见影，且可作为**新增链路**落地，不必改动任何既有模块。

## 1. Reason（变更理由）

- 用户指定 V1.2 为「最新执行标准」，要求以其为准绳。
- 当前架构（`autoload → core → data → services → scenes`）与 V1.2 要求的分层架构存在**系统性差距**，涉及 Core/Save/Public Contract，属 L5。
- 项目正处于可运行的稳定态（9 门禁），是进行架构治理的**最佳窗口**——再晚则迁移成本指数上升。

## 4. Proposed Change（建议变更）

**采用「绞杀者式分批迁移」，而非推倒重写。** 核心原则：

1. **新能力一律按规范建**，旧模块保持可运行。
2. **先建测量（扫描器），再动结构**——没有测量就没有治理。
3. **一次一个 Vertical Slice**，每个 Slice 独立验收。
4. **门禁全程保持绿**，任何一步失败即回滚该步。

### 目标架构（第 0-A.2 Architecture Graph）

```
Presentation
    ↓
Application（Use Case / Transaction Orchestration）
    ↓
Execution / Transaction Runtime   ← 【最高优先级】
    ↓
Domain
    ↓
Kernel

Infrastructure 通过 Contract / Port 提供技术能力
Content 提供 Definition / Schema / Pack / Index
```

## 5. Alternative Solutions（备选方案对比）

| 方案 | 描述 | 优点 | 致命缺点 | 结论 |
|---|---|---|---|---|
| **A. 推倒重写** | 一次性按规范重建全部 | 架构纯净 | 摧毁 73 测试 + 9 门禁；游戏数周不可运行；单人开发几乎必然烂尾；**违反规范 171 节** | ❌ **否决** |
| **B. 绞杀者分批迁移** | 新能力按规范建，旧模块逐个迁 | 全程可运行、风险可控、可随时停 | 工期长；中期存在新旧并存 | ✅ **推荐** |
| **C. 只做规范子集** | 仅采纳高 ROI 部分（Enforcement + Transaction） | 见效最快、风险最低 | 架构不彻底 | ⚠️ **建议作为 B 的前两阶段** |
| **D. 维持现状** | 不采纳 | 零成本 | 持续违反宪法；P0 资产损失缺陷会复发 | ❌ 否决 |

**推荐路径：先执行 C（Phase 0-2），验证收益后再决定是否继续 B（Phase 3+）。** 每个 Phase 结束都是一个可安全停下的决策点。

## 6. Dependency Impact

- **受影响模块**：全部（22 个 service、38 个 core、15 个 autoload、56 个场景脚本）。
- **循环依赖风险**：GameManager 持有 17 个 Service，Service 又反向访问 GameManager/EventBus，已存在事实上的**星形耦合**。迁移必须先斩断这层（Phase 3）。
- **跨窗口协同**：需按第 168A 节建立 Shared Foundation Write Lease，现有 handoff 板升级即可。

## 7. Save Impact

- 当前 `SAVE_VERSION = "1.1.0"`，已有版本校验与迁移步骤（**优良基础**）。
- 迁移至 SaveDTO 三分法（第 6/25 节）时，**必须保持 v1.1.0 老档可读**，按第 32 节逐步迁移，每步配 Migration Test（第 86 节）。
- **红线**：任何阶段不得出现「旧存档不能用了」。

## 8. Content Impact

- 72 个 JSON 配置结构**基本可保留**，主要工作是把 `data/configs/` 升级为规范要求的 `content/definitions/ + schemas/ + indexes/` 并接入 Content Registry（第 65/66 节）。
- 内容 ID 引用完整性由现有 **GATE6 引用校验**守护，迁移期间不得放松。

## 9. Test Impact

- 现有 **73 个测试文件全部保留**，按第 172 节「Test Migration」逐模块迁移为行为测试（表达行为，不复制实现）。
- 新增测试类型：Architecture Test（第 83 节）、Contract Test（第 84 节）、Transaction Test（0-C.20）、Migration Test（第 86 节）。
- **禁止**为适配新代码而删除或改写旧测试（第 90 节：测试是裁判）。

## 10. Migration Plan（分批迁移计划）

> 每个 Phase 结束都是一个**可安全停下的决策点**，需跑全量门禁并记录证据。

### Phase 0 — 立宪与测量（**非破坏性 · 可立即开始**）
- 宪法纳入 `docs/constitution/` ✅（已完成）
- 产出三张图：Architecture Graph / Foundation Graph / Build Graph（0-A.1）
- **基线留证**：跑一次 `verify_all.py` 9 门禁，记录迁移前基线
- 建立 **7 个架构扫描器**（0-E.2），**先以 REPORT 模式运行**（只报不拦）
- 建立 Module Owner 登记表（第 5 节）
- **改动**：纯新增文件，零既有代码修改
- **风险**：**零**

### Phase 1 — Kernel 契约 + 测试基建（**非破坏性 · 增量**）
- 建 `domain/kernel/`：`Command` / `Query` / `Result` / `Error` / `Event` 强类型契约（0-B.16、0-B.4）
- Command/Query Handler 骨架 + 对应单元测试
- 门禁扩至 GATE10（架构依赖）/ GATE11（禁止 API），**REPORT 模式**
- **改动**：新增，不接入既有业务
- **风险**：**极低**

### Phase 2 — Execution / Transaction Runtime（**最高 ROI**）
- 实现 Transaction + Mutation Journal + Commit/Rollback（0-C.5~0-C.9）
- Command Scheduler（0-C.13）
- **以 VS-001 Merchant Purchase 验证**（0-F.2/0-F.3：必须故意测试 7 种失败路径）
- **直接收益**：根治「扣钱不发货 / 扣料丢产出」类 P0
- **风险**：低（新增链路，可选接入）

### Phase 3 — Composition Root 收敛（**最危险阶段**）
- 15 个 Autoload → `ApplicationRoot` 统一装配（第 72 节）
- GameManager  stripping：剥离场景切换/Loading/世界状态，只留装配职责（第 73 节）
- **必须逐 Service 迁移**，每迁一个跑一次全量门禁
- **风险**：**高**，需单独 ADR + Write Lease

### Phase 4 — 逐模块迁移（Strangler Fig）
按规范第 206 节主施工路线顺序，一次一个模块：
```
Actor/World/Time → Relationship/Faction → Item/Inventory/Equipment
→ Economy/Shop/Crafting → Combat → Quest/Dialogue → Bond/Romance/Marriage/Family
```
每个模块走：Design → Contract → Skeleton → Unit Test → Implementation → Integration（第 157 节）。

### Phase 5 — Infrastructure 抽离
- 建 Repository Contract + Adapter（第 27/116 节）
- 消除 Domain 层 21 处 FileAccess/JSON/ResourceLoader 违规
- **验收标准（第 100 节）**：替换持久化实现时 Domain = 0 修改

### Phase 6 — Enforcement 升级为 E4 拦截
- 扫描器从 REPORT 切为 BLOCK（0-E.1）
- 补齐 Vertical Slice VS-001~VS-005（0-F）
- Studio 工具升级（第 67 节）
