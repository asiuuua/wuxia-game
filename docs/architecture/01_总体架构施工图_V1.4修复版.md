## 3. 总体架构目标

最高架构目标不是「尽快把功能写出来」，而是：**在长期、大规模、多模块、多 AI、多内容持续增长的情况下，控制变化半径，使系统保持可验证、可替换、可迁移、可扩展。**

架构目标优先级：

1. 正确性
2. 边界清晰
3. 状态所有权明确
4. 可测试
5. 可验证
6. 可回滚
7. 可替换
8. 可扩展
9. 可维护
10. 可观测
11. 可迁移
12. 性能

**性能不能成为破坏前十一项的借口。**

## 6. Architecture Graph 冻结规则

**允许：**

- Presentation → Application
- Application → Execution
- Application → Domain Contracts（即 → Domain / Kernel，二者同层，见 §5 修复句）
- Execution → Domain
- Execution → Kernel
- Domain → Kernel
- Infrastructure → Contracts
- Content → Schema
- Tools → Content / Schema / Validation
- Tests → 被测试对象

**禁止：**

- Domain → Presentation
- Domain → SceneTree
- Domain → UI
- Domain → FileAccess
- Domain → JSON
- Domain → Database
- Domain → Godot Runtime API
- Actor → Storage
- Presentation → Domain State Mutation
- Content → Domain Implementation
- Gameplay Module → 另一个 Gameplay Module 的内部实现
- 任何模块 → 未注册公共 Contract

**所有规则必须进入 Architecture Enforcement。**

## 9. Layer 01：Kernel

Kernel 是整个工程最稳定的语义基础。

**Kernel 只保存：**

稳定身份、Value Object、Result、Error、Command、Query、Event、Condition Contract、Effect Contract、Rule Contract、Transaction Contract、Clock Contract、Random Contract、Repository Contract。

**Kernel 不保存：**

Godot Node、SceneTree、UI、JSON、SQLite、Save implementation、Content implementation、Gameplay-specific orchestration。

---

## 10. Kernel 的 GDScript 原则

Core GDScript 必须：强类型、明确返回类型、明确参数类型、Typed Array、明确跨模块公共类型。

**不以以下能力作为架构前提：**

- C#/Java 风格 Interface 模拟
- 假想 readonly
- 泛型体系
- Dictionary 万能传输
- Variant 万能传输

**Interface 是架构角色**，不要求强制 `IXXX`。

**readonly 不作为架构能力**，采用：

```
private backing field
        ↓
getter
        ↓
controlled mutation API
```

**泛型不是核心架构前提。** 优先 `NPCRepository` / `QuestRepository` / `ItemRepository`，而不是为了抽象建立 `IRepository<T>`。

## 11. Layer 02：Domain

Domain 是游戏世界规则的唯一核心。

**Domain 回答：世界应该如何运行？**

Domain 包含：Entity、Value Object、Runtime State、Rule、Condition、Effect、Domain Service、Domain Event、Module-specific Contract。

**Domain 不直接处理：** UI、Scene、Node、File、JSON、Database、Audio、Rendering、Input、Godot SceneTree。

## 14. Layer 03：Execution（V1.2 最重要升级）

Execution 是 **Command 真正改变 Domain State 的运行时执行层**。

- Execution 不是 Domain
- Execution 也不是 Application
- **Application 负责：这个用例要做什么**
- **Execution 负责：这个变化如何安全发生**

## 16. Transaction Runtime

必须明确区分：

**Transaction Contract**（属 Kernel / Contract）：Transaction ID、生命周期语义、Commit、Rollback、状态。

**Transaction Runtime**（属 Execution）：Begin、Prepare、Mutation Journal、Pending Event、Commit、Rollback、Recovery、Transaction Context、生命周期管理。

**禁止把所有职责塞入 `TransactionManager` 形成新的 God Object。**

> **V1.4 修复版（B7 消歧，对齐宪法 RULE 009/§98/B7）**：**Execution 属 Shared Foundation**（同 §98 的 Transaction Contract / Mutation Journal），享有同样治理——默认冻结、单一 Write Owner / Write Lease，普通 Gameplay AI 只消费不擅改（宪法 RULE 009）。Transaction Contract=契约（kernel）、Runtime=执行（Execution/Transactions；§16 区分的两分表述与宪法 §0-C/§16 一致）。

---

## 17. Mutation Journal

所有受事务管理的重要 Mutation 必须记录：

```
transaction_id
target_id
owner_module
state_key
before
after
sequence
undo_strategy
```

示例：

```
Mutation #1  target=PLAYER_001  state=gold       before=500  after=400
Mutation #2  target=PLAYER_001  state=inventory  before=[]   after=[ITEM_POTION]
```

Rollback：`Mutation #2 undo → Mutation #1 undo`

**必须按 Journal 的反向顺序恢复。禁止根据当前状态猜测如何补偿。**

---

## 18. Rollback Failure

若 Rollback 自身失败：`TRANSACTION_RECOVERY_REQUIRED`

必须记录：transaction_id、mutation_sequence、failed_undo、current_known_state、recovery_action。

**Rollback Failure 不能被 `catch → print(error) → 继续游戏` 掩盖。**

---

## 19. Event Commit Boundary

必须区分 Pending Event 与 Committed Event。

- 事务期间：Domain Mutation → Pending Event
- Commit 成功：Commit → Committed Event

**只有 Committed Event 才能驱动：** Presentation、Persistence、Projection、外部观察者、后续正式业务事实链。

---

## 20. Post-Commit Failure

Committed Event Handler 失败：**不回滚已提交的 Domain State**。

必须使用：Retry / Dead Letter / Projection Rebuild / Recovery Task。

**禁止：Event Handler Failure → Undo committed transaction**（此时事实已经成立）。

---

## 21. Command

Command 表示**意图**。

例：BuyItemCommand、AcceptQuestCommand、CompleteQuestCommand、EquipItemCommand、TalkToNPCCommand、AttackCommand、UseAbilityCommand、ProposeMarriageCommand、TravelCommand、AdvanceTimeCommand、CraftItemCommand。

**Command 必须：** 明确类型、明确输入、可记录、可测试、可排序、可重放。
**Command 不直接修改 UI。**

---

## 22. Query

Query 表示**当前是什么状态**。

例：GetPlayerStatusQuery、GetNPCQuery、GetQuestStatusQuery、GetInventoryQuery、GetRelationshipQuery、GetFactionStandingQuery、GetAvailableQuestsQuery、GetShopItemsQuery、GetCombatStateQuery。

**Query：只读、不改变 Domain State、不启动业务 Mutation。**

---

## 23. Event

Event 表示**已经发生的事实**。

例：QuestAcceptedEvent、QuestCompletedEvent、ItemAddedEvent、ItemRemovedEvent、MoneyChangedEvent、RelationshipChangedEvent、MarriageFormedEvent、ChildBornEvent、FactionStandingChangedEvent、CombatStartedEvent、CombatEndedEvent、TimeAdvancedEvent、WorldEventTriggeredEvent。

**绝对区分：Command = 我要做什么；Event = 已经发生什么。**

---

## 24. Condition / Effect / Rule

**Condition**（是否满足）：HasItemCondition、HasMoneyCondition、QuestCompletedCondition、RelationshipAboveCondition、FactionStandingCondition、TimeCondition、LocationCondition、LevelCondition、FlagCondition

**Effect**（施加什么变化）：AddItemEffect、RemoveItemEffect、ModifyMoneyEffect、ModifyRelationshipEffect、ChangeFactionStandingEffect、StartQuestEffect、CompleteQuestEffect、SetFlagEffect、AdvanceTimeEffect

**Rule**（业务规则）：BuyItemRule、MarriageEligibilityRule、EquipItemRule、TravelRule、CraftingRule、CombatActionRule、QuestCompletionRule

**Rule 不负责：** UI、Audio、Scene、Save、File、Godot Runtime。

---

## 25. Layer 04：Application

Application 负责 **Use Case Orchestration**。

例：BuyItemHandler、AcceptQuestHandler、CompleteQuestHandler、TravelHandler、MarriageHandler、CraftHandler、StartCombatHandler。

标准链路：

```
Command
 ↓
Handler
 ↓
Load required state
 ↓
Validate
 ↓
Invoke Domain
 ↓
Execution
 ↓
Commit
```

**Application 不拥有核心 Domain State。Application 不成为 `GameApplicationService` 这类全局 God Object。**

## 26. Application 与 Execution 的边界

| 层 | 回答 |
|---|---|
| Application | 我要完成购买这个用例 |
| Execution | 这个用例产生的状态变化如何原子执行 |
| Domain | 什么条件下购买合法 |
| Infrastructure | 数据如何被保存和读取 |
| Presentation | 如何让玩家看到购买结果 |

---

## 27. Layer 05：Infrastructure

Infrastructure 是**技术实现适配层**：Persistence、Database、Filesystem、Clock、Random、Localization、Audio、Assets、Platform、Logging。

**Infrastructure 实现 Contract / Port。** 例：GameClock、RandomProvider、NPCRepository、QuestRepository、SaveRepository。

**Domain 不知道具体实现来自：** JSON / SQLite / Binary / Memory / Remote / Mock。

---

## 28. Repository Boundary

Repository 是 **Contract**。例：NPCRepository、QuestRepository、ItemRepository、InventoryRepository、RelationshipRepository、FactionRepository。

Infrastructure 提供实现。**禁止 Domain → SQLite 或 Domain → JSON。**

---

## 29. Clock Boundary

游戏逻辑不得直接使用系统时间。**禁止 system time 作为游戏逻辑事实源。**

统一 `IGameClock / GameClock Contract`，支持：Real Clock、Fake Clock、Replay Clock、Test Clock。

> **V1.4 修复版（A5 `I` 前缀 + C3 装配，对齐宪法 §0-B.5/§79）**：`IGameClock` 的 `I` 前缀代表它是**具体类型服务契约**（不是泛型模板化仓库），允许使用，与 §27/§28 `NPCRepository`（无 I）不冲突——I 缀取舍按「是否面向多实现的具体契约」定。IGameClock / IRandomProvider 由 **Composition Root 统一实例化注入**，不作全局单例（宪法 §79/B8）；Replay 记录字段（Build/Content Version、RNG Seed、Command Sequence、Game Time）在 VS 或 13 号图落地，本图只定原则。

---

## 30. Random Boundary

Domain 禁止直接 `randf()` / `randi()` / `RandomNumberGenerator.new()`。

统一使用 Random Contract，支持：固定 Seed、测试、Replay、AI 行为复现、Combat 复现、Bug 调查。

Deterministic Replay 至少记录：Build Version、Content Version、Schema Version、RNG Seed、Command Sequence、Game Time、Relevant External Inputs、Checkpoints。

---

## 31. Layer 06：Presentation

Presentation 负责：Input、UI、Scene、Animation、Camera、Audio Trigger、Navigation、Visual Feedback、ViewModel。

标准：`Query → ViewModel → UI`；输入：`Input → Command → Application`。

**禁止：Button → player.gold -= 100**

---

## 32. Godot / GDScript Boundary

Godot 是 **Runtime / Presentation / Infrastructure / Tools 的技术环境**，不是 Domain 的业务事实源。

**Domain 默认禁止：** Node、Node2D、Node3D、Control、SceneTree、Resource、PackedScene、Input、RenderingServer、AudioServer、FileAccess、DirAccess、ProjectSettings。

> **V1.4 语境复校**：以上默认禁止项在「代码明确属于白名单 Adapter / Boundary（如 `*_adapter.gd`、`adapter/` 层）」时放行——即 RULE 001 允许的与 Godot 原生运行时深度协作出口（宪法 0-B.0 / 0-E.3）。Domain 核心业务仍不得在业务类内直接调用上述 API。

**Domain / Kernel 禁止：** `get_tree()`、`get_node()`。

**Application 默认也不依赖 SceneTree。** 只有明确授权的 Presentation / Adapter 层可使用 Godot Runtime API。

---

## 33. Node / Scene 的定位

Scene / Node 是 **Runtime Carrier**，不是 Business State Source of Truth。

例：`NPCState` 才是 NPC 的业务运行时状态；`NPCScene` 只是把状态 Materialize 为可交互对象。

---

## 34. Actor Architecture

Actor 是 **Runtime Entity Carrier**。Actor 不拥有整个游戏。

```
Actor
├── Identity
├── Stats
├── Progression Ref
├── Inventory Ref
├── Equipment Ref
├── Relationship Ref
├── Faction Ref
└── Status
```

**禁止 `ActorState` 吞掉** Quest / Relationship / Inventory / Economy / Faction / Family / Combat / World 等所有状态。

---

## 35. Actor Materialization

```
World Simulation State
        ↓
Materialize → Actor Runtime → Active
        ↓
Dematerialize → World Simulation State
        ↓
Rematerialize（状态必须一致）
```

**Actor Scene 不成为永久业务事实源。**

---

## 36. Player

Player 是特殊 Actor：

```
Player
├── Actor
├── PlayerProgression
├── PlayerPreferences
├── PlayerMeta
└── PlayerCampaignState
```

**禁止 `PlayerState` 塞入整个世界。**

> **V1.4 修复版（B1/B2 消歧，对齐宪法 §224/B3）**：Player 是 **Actor 的特殊实例**（承载身份 / 控制器 / 输入 Intent），**不设独立 player 模块**。各子状态写 Owner：`PlayerProgression`（经验/等级）→ **Progression**；可写领域状态如 **Gold→Economy Wallet、背包→Inventory**；`PlayerCampaignState`→ **Story/CampaignState**；`PlayerPreferences`/`PlayerMeta` 为玩家配置/元数据，由 Presentation/local 配置文件收口。Actor 内的 Progression/Inventory 为 **Ref（引用）不持有真源**，与「NPCState 只引用不复制其他模块状态」一致（见 §37 修复句）。

---

## 37. NPC

NPC 必须数据驱动。区分：NPCDefinition / NPCState / NPCSaveDTO / NPCActorRuntime。

**NPCState 保存：** 位置、生命、当前状态、当前任务状态、当前日程状态、Runtime Flags。
**NPC 不保存：** Node、Scene、Texture、UI、DialoguePanel。

> **V1.4 修复版（B8/B10 消歧，对齐宪法 §224/B3）**：`NPCState` 中的「当前任务状态 / 当前日程状态」应为**指向该模块状态的只读引用/句柄**，而非复制一份副状态；Quest 状态写 Owner=Quest、日程状态写 Owner=Schedule，NPCState 不重复持有真源（避免违反单一 Owner，见宪法 B7/B8 口径）。四维对齐：NPCDefinition=Definition、NPCState=Runtime State、NPCSaveDTO=Save DTO、NPCActorRuntime=Actor Runtime（§40 四维数据边界）。

---

## 38. State Ownership Architecture

每个 Runtime State 必须拥有唯一 Owner。基线：

| State | Owner |
|---|---|
| Actor | Actor Identity |
| NPC | NPC Identity / NPC Runtime State |
| World | World State |
| Schedule | Schedule State |
| Relationship | Relationship Edge / Score / Type |
| Romance | Romance Progress / Stage |
| Marriage | Marriage State |
| Family | Family State |
| Pregnancy | Pregnancy State |
| Children | Child Growth State |
| Faction | Faction State |
| Progression | XP / Level / Talent / Skill |
| Item | Item Definition / Instance Identity |
| Inventory | Container / Slot / Stack |
| Equipment | Equipment Slot / Loadout |
| Crafting | Crafting Transaction State |
| Economy | Currency / Wallet / Economic Transaction |
| Shop | Shop State / Shop Inventory |
| Ability | Ability State / Cooldown |
| Combat | Combat Session State |
| Quest | Quest State / Objective Progress |
| Dialogue | Dialogue Runtime State |
| Story | Story Arc / Chapter State |
| Content | Definition / Pack / Version / Index |
| Persistence | Save DTO / Save Version / Migration |
| Presentation | ViewModel / UI Local State |

> **V1.4 修复版（B3/B4消歧，Owner 表 vs §13 模块基线的统一）**：本表是**状态写 Owner** 的权威（每类 Runtime 状态唯一 Owner），可与 §13 模块基线并存但职权不同——§38 认状态、§13 认模块。`Shop`、`Pregnancy` 在本表是状态 Owner；模块归属按「Economy 域含 Shop、Family 域含 Pregnancy/Children」整套：**Shop 与 Merchant 归 Economy 域，Merchant 是 Shop 的参与方（交易者）非独立状态 Owner**。新增模块/状态必须先经 §38 的 Who-Owns/Reads/Mutates/Persists 问答，冲突时以本表为准。

---

## 39. State Ownership 禁止项

- 禁止 NPC + Quest 同时拥有 Quest State
- 禁止 Player / NPC / Relationship 同时复制同一份 Relationship State
- 禁止 Presentation 保存一份可写的业务 State
- 禁止 Node 拥有 Domain 的第二份事实状态

**任何新增 State 必须先回答：** Who Owns It? / Who Reads It? / Who Mutates It? / Who Persists It? —— **回答不了：STOP**

---

## 40. 四维数据边界（V1.2）

| 维度 | 描述 |
|---|---|
| Definition | 世界里有什么 |
| Runtime State | 世界当前是什么状态 |
| Execution State | 当前事务 / Command / Scheduler 正在做什么 |
| Save DTO | 如何持久化 |

**四者不能混成一个对象。**

---

## 41. Content Architecture

Content 是**世界的描述系统**，不是世界规则执行系统。

Content 包括：NPC、Quest、Item、Ability、Dialogue、Faction、Location、Recipe、Event、Story，均以 Definition 为核心。

> **V1.4 修复版（B9 层位消歧）**：Content 在依赖链上立于**下方数据/描述层**（同 §5 图：Raw→Schema→…→Runtime Consumption），是「数据侧」而非「业务侧层级」；它不直接依赖 Domain 实现（见 §43），经 Schema/Registry 供 Domain/Application 消费。Content 的层位=描述数据底座，非 Presentation/Application/Domain 的一员。

---

## 42. Content Pipeline

```
Raw Content → Schema Validation → ID Validation → Reference Validation
→ Condition Validation → Dependency Validation → Localization Validation
→ Balance Validation → Build → Index Generation → Content Package
→ Content Registry → Runtime
```

**禁止运行时才发现：** QUEST_000123 不存在 / NPC_000456 不存在 / Dialogue 引用不存在 Quest。

---

## 43. Content 与 Domain 的边界

**禁止：Content → 直接引用 Domain Implementation**

正确：

```
Content Authoring → Schema → Compiler / Validator → Validated Definition
→ Registry → Domain / Application Consumption
```

**Content 改变不应该迫使 Domain 重构。**

---

## 44. Content ID

正式 ID 必须机器验证：`NPC_000001`、`QUEST_000001`、`ITEM_000001`、`ABILITY_000001`、`DIALOGUE_000001`、`FACTION_000001`、`LOCATION_000001`、`EVENT_000001`、`STORY_000001`。

**正式 ID：永不复用。**

---

## 45. Content Registry

建立 `ContentRegistry` 负责：Load、Cache、Index、Version、Dependency、DLC、Mod、Validation、Unload。

**业务代码不得散布 `load("res://...")`。**

---

## 46. Content Index

必须建立：QuestByNPC、QuestByFaction、QuestByRegion、QuestByChapter、QuestByTag、DialogueByNPC、DialogueByQuest、ItemByCategory、ItemByTag、NPCByRegion、NPCByFaction、AbilityByActor。

**避免运行时大规模无索引扫描。**

---

## 47. Binding Architecture

Definition 不直接硬编码复杂对象关系。使用 QuestNPCBinding、QuestRegionBinding、QuestRewardBinding、QuestDialogueBinding，使 `NPC ↔ Quest`、`Quest ↔ Dialogue`、`Quest ↔ Reward` 保持可组合。

---

## 48. Relationship

Relationship 是通用关系图。核心：RelationshipGraph、RelationshipEdge、RelationshipType、RelationshipState、RelationshipRule。

可表达：Friendship、Respect、Trust、Hatred、Romance、Family、Master、Disciple、Sworn、Faction。

**Relationship 不负责：** Marriage、Pregnancy、Child Growth、Inheritance。

---

## 49. Marriage / Family

Marriage 是 Relationship 之上的 Gameplay Module。

```
Proposal → Eligibility → Marriage Transaction → MarriageFormedEvent
```

Family 接收 `MarriageFormedEvent` 后建立 FamilyUnit / Household / ParentChildRelation / Inheritance。

**Marriage 不吞并 Family。**

---

## 50. Quest

Quest 负责：QuestDefinition、QuestState、Objective、ObjectiveState、Progress、Branch。

奖励通过 **Effect** 执行：

```
QuestCompletedEvent → Reward Effect
→ AddItemEffect / ModifyMoneyEffect / ModifyRelationshipEffect / UnlockEffect
```

---

## 51. Dialogue

Dialogue 是 Runtime Graph：

```
DialogueGraph → DialogueNode → DialogueChoice → Condition → Command / Effect
```

**Dialogue 不直接修改** Relationship / Quest / Inventory / Faction，而是产生相应 Command / Effect。

---

## 52. Story

Story 位于 Quest 之上：

```
Story
└── Arc
    ├── Chapter
    ├── Quest
    ├── Dialogue
    ├── Event
    └── Scene
```

**Story 不重新定义 Condition / Command / Effect / Event，而组合已有能力。**

---

## 53. World

World 管理：Region、Location、Weather、Calendar、Time、World State、Spawn、Travel、World Event。

**World 不管理：** UI、Scene、NPC Panel、Combat UI。

---

## 54. Schedule

Schedule 独立存在：ScheduleDefinition、ScheduleState、ScheduleRule、ScheduleEntry。

时间推进：`TimeAdvancedEvent → Schedule Resolver → Schedule State → NPC / Shop / World Effects`

**Scheduler 不直接替代 Command Execution。**

---

## 55. Faction

Faction 独立于 NPC：FactionDefinition、FactionState、FactionMember、FactionRank、FactionRelation、FactionReputation、FactionRule、FactionPolicy、FactionResource。

**NPC 只保存 FactionMembership** —— 这样新增势力无需修改 NPC 核心结构。

---

## 56. Item

必须区分：ItemDefinition / ItemInstance / ItemStack。

```
ITEM_SWORD_001   → Attack=30, Weight=5
INSTANCE_xxxx    → Enhancement=+7, Durability=83, Owner=PLAYER_001
```

---

## 57. Inventory

Inventory 负责：Container、Slot、Stack、Add、Remove、Move、Capacity。

**不负责：** Equipment Rule、Shop Price、Crafting Rule、Quest Reward。

---

## 58. Equipment

Equipment 负责：Slot、Equip、Unequip、Loadout、Requirement、Modifier。

与 Inventory 通过 Command / Transaction / Event 协作。

---

## 59. Crafting

**不为 Forge / Alchemy / Cooking 分别建立三套核心系统。** 统一 Crafting Module，使用 RecipeDefinition、CraftingRule、CraftingEffect，类别：Forge / Alchemy / Cooking。

---

## 60. Economy / Shop

**Economy：** Money、Currency、Wallet、Price、Market、Economic Rule、Economic Transaction。

**Shop：** ShopDefinition、ShopState、ShopInventory、ShopEntry、ShopRule。

**Shop 不直接操作 Player Wallet。** 购买链路：

```
BuyItemCommand → Shop Validation → Economy Validation → Transaction
→ Money Mutation → Inventory Mutation → Commit → Purchase Events
```

---

## 61. Ability

Ability 数据驱动：AbilityDefinition、AbilityCost、AbilityTarget、AbilityCondition、AbilityEffect、AbilityCooldown、AbilityModifier。

新增武学 / 法术 / 暗器 / 阵法 / 毒术 / 轻功 / 内功，**原则上不需要重新设计 Ability 核心**。

---

## 62. Combat

Combat 与 World Actor 解耦。

战斗开始：`World Actor → Combatant Snapshot → Combat Session`
战斗结束：`Combat Result → World State Update → Committed Events`

**Combat 不依赖：** NPC Scene、Player Scene、Battle UI。

---

## 63. Combat AI

```
Player ──Input──→ Command ──┐
                            ↓
                   Combat Command Pipeline
                            ↑
AI ───Decision──→ Command ───┘
```

**AI 是 Command Producer，不是第二套 Combat Rule。**

---

## 64. Scheduler Architecture（V1.2 四层）

1. **Command Scheduler**
2. **Actor Scheduler**
3. **World Simulation Scheduler**
4. **Persistence Scheduler**

---

## 65. Command Scheduler

负责：Command Queue、Ordering、Priority、Deterministic Tie Break、Dispatch。

Command 元数据：command_id、sequence、source、actor_id、timestamp、game_tick、correlation_id、causation_id。

**排序必须确定。禁止依赖 Dictionary iteration / Node tree order / Thread scheduling。**

---

## 66. Actor Scheduler

Actor Tick 状态：REALTIME、ACTIVE、REDUCED、SIMULATION、SUSPENDED。

**Actor Tick 不得绕过 Command Execution：**

```
Actor Tick → Decision → Command → Execution
```

而不是 `Actor Tick → 直接修改 Domain State`。

---

## 67. World Simulation Scheduler

负责：World Time、Schedule、World Events、Background Simulation、Materialization / Dematerialization。

**World Simulation 产生的状态变化仍必须遵守 State Owner 和 Execution Boundary。**

---

## 68. Persistence Scheduler

负责：Save、Load、Snapshot、Journal Update、Migration、Durability。

**Persistence 不拥有 Domain State。**

---

## 69. Persistence Boundary

Save 不只是 SaveManager，而是正式架构边界：

```
Domain Transaction Commit → Committed Event
→ Persistence Snapshot / Journal → Durability Gate
```

具体边界可由 ADR 调整，但必须明确。

---

## 70. Save Architecture

Save 至少包含：save_version、game_version、content_version、timestamp、checksum。

然后：Player、World、Quest、NPC、Relationship、Faction、Inventory、Equipment、Progression、CustomModules。

**保存格式属于 Save Schema。不得直接把 Runtime Object 当 Save DTO。**

---

## 71. Save Migration

```
Save V1 → Migration V2 → Migration V3 → Current
```

**禁止假设旧 Save == 新 Save。** 任何 Save Schema 修改必须触发：Impact Analysis、Migration、Compatibility Test、Gate。

---

## 72. Event Log

可保留可选 Event Log（Event ID、Timestamp、Actor、Event Type、Payload），用于 Bug 调查、Debug、Replay、玩家日志、AI 分析、测试。

**Event Log 是否成为正式持久化事实源，必须由独立架构决策确定。**

---

## 73. Composition Root

Composition Root 是共享 Foundation，负责 Create / Inject / Register / Compose。

```
ApplicationRoot
 ↓
ContentRegistry → Repositories → Application Handlers
→ Execution Runtime → Event Handlers → Module Loader → Capabilities
```

**Composition Root 负责组装，不负责业务规则。禁止演变成 GameManager 2.0。**

---

## 74. Autoload

**原则：越少越好。** Autoload 不得成为默认的全局业务状态容器。

**禁止为了方便新增：** EventBus Autoload、GameManager Autoload、SaveManager Autoload、AudioManager Autoload、ConfigManager Autoload。

若确实需要新增 Autoload：

```
STOP → Shared Foundation Review → ACR / ADR → 批准后实施
```

---

## 75. Module Loader

Module Loader 属 Foundation：

```
Discover → Validate → Resolve Dependencies → Initialize
→ Activate → Run → Deactivate → Dispose
```

**Module Loader 不实现 Gameplay Rule。**

---

## 76. Module Manifest

模块可声明：id、version、dependencies、optional_dependencies、capabilities、content_requirements。

示例：`marriage` ── dependency: relationship ── optional: family

**依赖必须可机器验证。**

---

## 77. Capability Registry

Capability Registry 负责声明当前工程有哪些能力可用：COMBAT、CRAFTING、MARRIAGE、CHILDREN、POLITICS、HOUSING、FACTION、ROMANCE。

**业务代码禁止散布 `if service != null`**，统一使用 CapabilityRegistry。

**Capability 不承载业务逻辑。**

---

## 78. Definition / Runtime / Save / Capability 边界

**必须避免：Capability → 拥有整个 Module State**

正确：

| 概念 | 职责 |
|---|---|
| Capability | 能力是否存在 |
| Module | Module State |
| Content | Definition |
| Persistence | Save DTO |

---

## 79. Studio

Studio 不是 JSON 编辑器，而是 **Content Authoring System**。

包括：NPC Editor、Quest Editor、Dialogue Graph Editor、Story Editor、Item Editor、Ability Editor、Faction Editor、Relationship Editor、Schedule Editor、World Event Editor。

编辑器依赖 Schema / Definition / Validation / Registry，**不直接修改 Runtime State**。

---

## 80. Story Editor

Story Editor 使用 StoryGraph，节点类型：StoryNode、ConditionNode、ChoiceNode、CommandNode、EventNode、VariableNode、BranchNode、JoinNode。

**StoryDefinition 与 Story Runtime 二者分离。**

---

## 81. Debug Architecture

Debug 是正式能力，不是 `print("test")`。

可定义：DebugCommand、DebugQuery、DebugEvent、DebugSnapshot。

可查看：NPC State、Quest State、Faction、Relationship、World Time、Active Events、Combat State、Save State、Transaction State。

---

## 82. Logging

统一 Logger：TRACE、DEBUG、INFO、WARNING、ERROR、FATAL。

**禁止业务代码散布 `print("aaaa")` / `print("test")` / `print("why")`。**

关键日志必须具有：module、operation、correlation_id、causation_id、transaction_id、command_id。

---

## 83. Error Architecture

错误必须机器可识别。例：ERR_ITEM_NOT_FOUND、ERR_INSUFFICIENT_MONEY、ERR_INVALID_TARGET、ERR_QUEST_NOT_AVAILABLE、ERR_REQUIREMENT_NOT_MET、ERR_INVALID_STATE、ERR_MODULE_DEPENDENCY。

**禁止依赖中文错误字符串作为业务判断依据。**

Result 推荐：OperationResult、CommandResult、SaveResult、LoadResult、BuildResult、ValidationResult。

Error 至少包含：error_code、context；适用时：causation_id、correlation_id、transaction_id。

---

## 84. Definition / Runtime 不得混淆

**错误：** NPCDefinition 同时保存当前位置 / 当前血量 / 当前任务 / 当前关系
**正确：** NPCDefinition / NPCState / NPCSaveDTO

同样适用于：Quest、Item、Faction、Ability、Shop、Dialogue、Story。

---

## 85. Cross-Module Communication

模块之间**只能**通过：Command、Query、Event、Public Contract、Application API。

**禁止访问 `other_module/internal/`**

**禁止：** Quest → Relationship.private_state
**正确：** QuestCompletedEvent → Relationship Application / Handler → Relationship State Owner

---

## 86. Event Architecture

**不建立万能 EventBus。**

事件层次：

```
Domain Event → Application Handling → Presentation Notification
```

Presentation 可使用 **Signal** 用于 UI / Animation / Audio / Local lifecycle。

**跨业务事实必须使用 Typed Domain Event。禁止 Dictionary Event Bus。**

---

## 87. GDScript 类型策略

**Core：Strongly Typed First。**

**允许 Variant 的边界：** Raw Content、外部未知输入、Editor Metadata、Debug Metadata、Schema Parser Boundary

**默认禁止 Variant：** Domain State、Command Payload、Event Payload、Actor Runtime State、Save DTO、Cross-Module Core Contract

**Dictionary 默认仅用于：** Raw JSON、Authoring Data、Config、Temporary Tool Data、Extension Metadata

**禁止 Dictionary 成为 Universal Context / Runtime State / Command / Event Transport。**

---

## 88. GDScript Object 选择

**优先 RefCounted / Plain Class：** Command、Query、Result、Error、Domain State、Transaction、Domain Event、Actor Contract、Test Double

**Node 仅在确实需要** SceneTree / Lifecycle / Rendering / Input / Audio / Presentation 等引擎能力时使用。

---

## 89. Abstraction Rule

新建抽象必须满足至少一项：

1. 第二个实现即将存在
2. 明确 Test Double
3. 平台差异
4. 可替换 Strategy
5. 跨模块隔离

**否则优先 Concrete Class。禁止「以后可能有用」。**

---

## 90. State Mutation Rule

状态变化必须经过 Owner。

**禁止：** `inventory.items.append(...)`

**正确链路：**

```
Command → Inventory Application → Inventory Domain → Mutation
```

**State Owner 是唯一事实写入者。**

---

## 91. Architecture Enforcement

架构不能只写在 Markdown。必须建立：

```
Rule → Enforcement Method → Scanner / Test → Gate → Merge Block
```

执行级别（优先级 E4 > E3 > E2 > E1 > E0）：

- **E0** DOCUMENT
- **E1** REVIEW
- **E2** TEST
- **E3** STATIC CHECK
- **E4** BUILD BLOCK

**能自动检查的规则不得长期停留在 E0。**

---

## 92. Architecture Validators

至少建立：

- dependency_validator
- forbidden_api_validator
- module_scope_validator
- changed_file_scope_validator
- contract_drift_validator
- state_owner_validator
- naming_validator

---

## 93. Forbidden API

必须机器检查：FileAccess、DirAccess、JSON、ResourceLoader、SceneTree、get_tree、get_node、ProjectSettings、Random APIs、System Time APIs。

**依据模块分别限制。** 例如 Domain：JSON = BLOCK、FileAccess = BLOCK、SceneTree = BLOCK、Godot Node = BLOCK、Random Global API = BLOCK、System Time = BLOCK。

---

## 94. Contract Drift

Contract Registry 与实际代码比较：class_name、method signature、parameter、return type、event、command、query、error、schema。

发现 `Contract ≠ Implementation` → **CONTRACT DRIFT → 禁止直接 Merge。**

---

## 95. Changed File Enforcement

AI 实际修改文件必须与 Task Scope Lock 比较。Allowed Files 之外发生修改 → **SCOPE VIOLATION → 默认 BLOCK。**

---

## 96. State Ownership Enforcement

自动检测：多模块写同一 State、非 Owner Mutation、重复完整 State、Save State 无 Owner、Runtime State 无 Owner、Node 成为第二状态源。

发现 → **STATE OWNERSHIP VIOLATION → 禁止 Merge。**

---

## 97. Architecture Health

持续监控：Fan-in、Fan-out、Cross-module Imports、Dependency Depth、Cycles、Public API Count、Shared Foundation Change Frequency、Changed Files / Feature、Contract Drift、Schema Drift、Save Drift、God Object、Duplicate Infrastructure、Regression、Performance Regression、Context Staleness、Unowned State、Scope Violations、Enforcement Coverage、Transaction Recovery Incidents、Rollback Failure Count、Command Ordering Violations、Contract Change Lead Time。

---

## 98. Shared Foundation

以下默认属于 Shared Foundation：Kernel、Public Command、Public Query、Public Event、Transaction Contract、Mutation Journal、Composition Root、Module Loader、Capability Registry、Content Schema、Save Schema。

**Shared Foundation：单线程治理。不能多个 AI 同时修改。**

---

## 99. Write Lease

Shared Foundation 修改必须拥有：lease_id、owner、scope、reason、related_acr、related_adr、allowed_files、start_revision、release_condition。

**同一 Scope：同一时间只允许一个 Write Lease。**

---

## 100. Contract Freeze

Contract Freeze 后：

**AI 可以：** Consume、Implement、Test、Propose Change
**AI 不可以：** 私自修改、偷改参数、增加 Event、改 Save Schema、改 Content Schema

需要改变：

```
ACR → Impact Analysis → Decision → Version Bump
→ Migration / Compatibility → Tests → Gate
```

---

## 101. AI Architecture Boundary

AI 是 **Implementer**，不是 **Architecture Owner**。

**AI 不得私自：**

1. 修改架构
2. 新增 Autoload
3. 创建 Global Singleton
4. 修改公共 Contract
5. 修改 Save Schema
6. 修改 Database Schema
7. 扩大模块职责
8. 修改其他模块内部实现
9. 新增核心术语
10. 新建重复基础设施
11. 删除失败测试
12. 注释失败代码
13. 用 TODO 掩盖未完成逻辑
14. 创建万能 Manager
15. 创建万能 EventBus

---

## 102. AI 开工十问

1. 我修改哪个 Module？
2. Module 负责什么？
3. Module 不负责什么？
4. 我会修改哪个 State？
5. 谁是 State Owner？

8. Transaction Boundary 在哪里？
9. Failure / Rollback 如何处理？
10. Tests / Gates / Evidence 是什么？

**无法回答：STOP**

## 103. Task Scope Lock

**AI 不得顺便重构整个项目。**

READ BEFORE WRITE
UNDERSTAND BEFORE MODIFY
CONTRACT BEFORE IMPLEMENTATION
SCOPE BEFORE EDIT
OWNER BEFORE MUTATION

## 106. Legacy Architecture

Legacy 是 **Reference**，不是 **Architecture Authority**。

**允许 Legacy 用于：** 功能考古、Gameplay 行为发现、数据发现、Bug 发现、UI 行为参考、Migration

## 122. Blast Radius

架构健康的重要指标：**一个需求需要修改多少个「不相关文件」。**

| 理想 | 修改范围 |
|---|---|
| 新增武器 | Content |
| 新增任务 | Quest Definition + Dialogue |
| 修改商店价格 | Content Definition |
| 修改存储实现 | Infrastructure |
| 修改 UI | Presentation |

**若「修改一个武器 → 修改 14 个 Service」，说明架构开始腐化。**

## 130. 多 AI 总体架构

推荐角色：AI-ARCH、AI-DOMAIN、AI-EXECUTION、AI-INFRA、AI-CONTENT、AI-ACTOR、AI-UI、AI-STUDIO、AI-TEST、AI-REVIEW。

## 131. Owner AI

一个 Gameplay Module 的 Domain / Application / Infrastructure **最好由一个 Owner AI 主导**。

其他 AI 可做 Test、Content、Presentation、Proposal、Review，**但不得同时修改同一核心 Foundation**。

## 138. 01 V1.2 最终冻结规则

**架构**

```
Presentation → Application → Execution → Domain → Kernel
Infrastructure = 技术适配边界
Content = Definition / Schema / Pack / Index 体系
```

**行为语义**

```
Intent → Command
Read → Query
Fact → Event
Requirement → Condition
State Change → Effect
Business Rule → Rule
Multi-State Mutation → Transaction
```

**状态**

```
Definition ≠ Runtime State ≠ Execution State ≠ Save DTO
```

**所有权**

```
One State → One Owner → Controlled Mutation
```

**模块**

```
Module → Responsibility → Boundary → Contract → Owner
跨模块：Public Contract Only
```

**Godot**

```
Godot = Runtime / Adapter / Presentation Technology
Godot ≠ Domain State Source of Truth
Domain ↔ Godot 深度协作仅经白名单 Adapter / Boundary（宪法 V1.4 RULE 001）
```

**AI**

```
Read → Understand → Scope → Contract → Owner → Transaction
→ Implement → Test → Gate → Merge
```

**Foundation**

```
Shared Foundation → Frozen → Write Lease → Single-thread Governance
```

**证据**

```
没有 Compiler Evidence / Static Check / Test Evidence / Gate Evidence
/ Reproduction / Benchmark / Build Artifact / Change Record
就不能声称 COMPLETE
```

## 139. 01 总体架构一句话总纲

> Content 描述世界，Domain 定义世界规则，Command 表达意图，Execution 保证状态变化安全发生，Transaction 保证多状态变化的原子性，Event 记录已经发生的事实，Application 编排用例，Infrastructure 连接现实，Presentation 展示结果，Studio 建造内容，Tests 监督边界，AI 在冻结的建筑规则内施工。
>
> 最终目标不是建立一个「看起来很专业」的架构，而是建立一座：可以持续施工、可以多人施工、可以多 AI 并行施工、可以失败、可以回滚、可以审查、可以测试、可以迁移、可以替换、可以扩展、可以长期维护，而不会因为某一个 AI、某一个模块、某一次需求变化就牵一发而动全身的工程系统。

**01 的职责到此为止：定义整座建筑如何站立。**

具体 Domain / Application / Execution / Infrastructure / Content / Actor 怎么实现，由后续对应施工图继续展开。

**01 不实现模块。01 定义模块应该如何共存。**
