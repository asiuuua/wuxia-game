## B. Foundation Graph（横向能力必须怎么逐步铺）

> **关键认知**：这些不是「某一章一次性做完」，而是随 Vertical Slice 增长的横向能力。

```
Contract        ← Command / Query / Result / Error / Event 强类型契约
   ↓
Testing         ← 73 个现有测试迁移 + Architecture/Contract/Transaction Test
   ↓
Execution       ← Transaction / Mutation Journal / Rollback / Scheduler【最高 ROI】
   ↓
Persistence Fnd ← Repository Contract + Memory/Fake Adapter（Save v1.1.0 已就绪）
   ↓
Composition     ← ApplicationRoot 统一装配（替代 15 Autoload）
   ↓
Content Fnd     ← Content Registry + Index（72 JSON 已就绪，需 Registry 化）
   ↓
Actor Fnd       ← Actor/NPC Runtime（现有 NPC 数据迁移）
   ↓
Gameplay Modules← 逐个绞杀式迁移
```

**每项先建最小可用能力，再随 Slice 增长。** 现状盘点：

| Foundation | 现状 | 就绪度 |
|---|---|---|
| Contract | 无强类型 Command/Query；有 EventBus（84 信号，2 处 Dictionary） | 🟡 20% |
| Testing | 73 测试 + 9 门禁，但无 Architecture/Contract/Transaction Test | 🟡 50% |
| Execution | **完全缺失** | 🔴 0% |
| Persistence | `SAVE_VERSION 1.1.0` + 迁移步骤 + 版本校验 | 🟢 70% |
| Composition | 15 Autoload + God Object GameManager | 🔴 10% |
| Content | 72 JSON 数据驱动 + `data/schemas/`，但无 Registry/Index | 🟡 55% |
| Actor | NPC 数据分散在 `regions/*/npcs.json` | 🟡 40% |

### 当前（Phase 0-2 期间）的并行判定

规范第 0-G.8 节定义的**并行禁区**（无锁不得并行）：
```
Kernel / Public Command / Public Query / Public Event
Transaction Contract / Content Schema / Save Schema
Composition Root / Module Loader / Capability Registry
```

⚠️ **Phase 0-2 的全部工作内容恰好都落在并行禁区内**——
即：**架构地基施工阶段本身不适合多窗口并行**，必须由单一 Owner 串行推进。

**可以并行的（不触碰禁区）：**

| 可并行工作 | 说明 | 前提 |
|---|---|---|
| Content 生产 / 校验 | 新增 NPC、任务、对话数据 | 不修改 Schema |
| 补充单元测试 | 为既有模块补测试 | 不改实现 |
| 文档与 ADR 撰写 | Module Card、Contract 文档 | — |
| Studio 工具改进 | 编辑器、校验器 | 不改 Content Schema |
| Legacy Bug 归档（第 173 节） | 整理 BUG 档案 | — |

**必须先串行完成、才能解锁后续并行的：**
1. Kernel 契约冻结（解锁各模块 Domain 并行）
2. Execution/Transaction 冻结（解锁 Economy/Inventory/Crafting 并行）
3. Composition Root 收敛（解锁 Presentation 并行）
