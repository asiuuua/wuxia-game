## 1. 背景与问题

01 图 §74 明令「Autoload 越少越好，禁止为方便新增 EventBus/GameManager/SaveManager/AudioManager/ConfigManager Autoload」——现存 18 个 Autoload 是 V1.1 时代的**历史存量**，其中 GameManager 实际承担了 Composition Root 职责（Create/Inject/Register 全在 `_ready`）但**同时持有业务编排**（场景切换、加载 UI、平台适配），正是 01 图 §73 警告的「演变成 GameManager 2.0」形态。ACR-0001 将装配收敛定性为**最高风险迁移项**，01 §128 Phase 路线第 3 步「装配收敛(18 Autoload)」。宪法 0-G.8 要求 Kernel/Public Command/Query/Event/Transaction Contract 的修改必须持锁并行——本日实录两波 core/ 撞车即为无锁并行代价。

## 2. 目标形态（01 §73 冻结链，不得偏离）

```
ApplicationRoot（新增，唯一装配点）
 ↓
ContentRegistry → Repositories → Application Handlers
→ Execution Runtime → Event Handlers → Module Loader → Capabilities
```

- **Composition Root 只组装不业务**；Assembly 期间禁止读存档、禁止发业务事件。
- GameManager **不删除**：瘦身为「场景/加载/平台壳」（Presentation 边界壳），业务服务装配权移交 ApplicationRoot。
- Autoload 只保留**引擎必需壳**（EventBus 信号背骨 / 生命周期入口），其余降级为普通服务由 ApplicationRoot 持有。

## 3. 现状盘点（2026-09-06 实扫）

| Autoload | 性质 | 收敛动作 |
|---|---|---|
| EventBus / ConfigManager / SaveManager / GameState / SettingsManager / WeatherTimeService / AudioManager / ErrorHandler / UIManager / LocalizationManager / TransitionManager / DefeatHandler / SaveValidator / DifficultyManager / PatchManager(core) / ObjectPool(services) / PerformanceMonitor(tools) | 历史存量（§74 违例候选） | 分批降级/收编（见 §5） |
| GameManager | 装配+业务混合壳 | 双装配期过渡 → 瘦身壳 |

services 装配点：`GameManager._init_services()` 单点 new 12 服务（inventory/quest/ability/equipment/alchemy/forge/shop/sect/combat/bond 族/dialogue）——迁移即把这段 Create/Inject 移交 ApplicationRoot，GameManager 改为持引用（引用不换代，调用方零改动）。

## 4. Write Lease（已落地，本 ADR 的并行前提）

`tools/write_lease.py`（宪法 0-G.8 载体）：append-only 租约事件流，FROZEN_SCOPE（core/kernel/、core/execution/、EventBus.gd、arch_linter_baseline.json 等）无租约禁止动；目录前缀冲突判定；4h 自动过期。**纪律：进入本 ADR 任何批次施工前，涉事目录必须 claim。**

## 5. 分批方案（每批独立 commit、verify_all 双闸门、可随时停）

- **批A（骨架，零行为）**：新建 `application/application_root.gd`（普通 RefCounted/Node，非 Autoload）；实现 Create/Inject/Register 三段骨架；GameManager._init_services() 委托调用（行为等价开关：`USE_APPLICATION_ROOT` 常量，默认 false）。DoD：双开关各跑一次 verify_all 全绿。
- **批B（首批迁移，低风险三件）**：shop_service（含升表口「每笔 new Runtime → ApplicationRoot 注入共享 Runtime 工厂」）、quest_service、inventory_service 迁入 ApplicationRoot。DoD：76+ 套件全绿 + A1 集成链绿（直接覆盖 quest/inventory 消费面）。
- **批C（ConfigManager 收编）**：05 图 ContentRegistry 骨架接管 ability/item/dialog 加载（05 图批1 已建），ConfigManager 收敛为薄代理。DoD：内容五类套件全绿。
- **批D（GameManager 瘦身）**：业务编排迁出（场景切换归 TransitionManager、平台适配归 Presentation 壳）；Autoload 表收缩（保留 EventBus/生命周期入口）；本批完成即 Phase3 收口。DoD：Autoload 数 ≤ 8 且全为引擎壳。
- **每批回滚**：单批 revert 即回退（分批 commit 隔离）；批A 开关可秒切旧装配。

## 6. 升表口衔接（ADR-0005/0006 登记在案，随本 ADR 实施）

- IGameClock / IRandomProvider：Composition Root 统一实例化注入（01 §29 直修），废弃全局钟。
- ShopService Transaction Runtime：每笔 new → 注入（D-10 收编备忘既定口）。
- GATE23 Changed File Scope：Write Lease 元数据就绪后点亮（04 图 §2 既定）。

## 7. Phase D（C3，随批 B~D 并行的模块增量通道）

02 图 O-4 既定：契约骨架 Phase B 已落地，**具体 Command/Query 由各模块在 Phase D 增量实现**（非集中批次）。通道规则：各模块按 02 图 §15 迁移映射逐条登记（kernel 契约实现 → 服务收编 → 契约测试），每条独立 commit 走更改日志；EffectRegistry/事务类消费面迁移必须持 Write Lease。Phase D 完成判据：02 图 §15 映射表全条目落地 + kernel 契约 100% 被 services 消费。

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 18 Autoload 初始化顺序依赖（GameLogger/ConfigManager 时序） | 批A 骨架只移交 services 装配（时序敏感的 autoload 不动）；分相消费范式已验证（B6） |
| 测试直接 new 服务/访问 GameManager 成员 | 引用不换代策略：GameManager 持引用转发，测试零改动 |
| 多窗口并行施工撞车 | Write Lease 强制 + FROZEN_SCOPE 红线 |
| 装配期读存档/发事件（01 §73 禁） | ApplicationRoot 组装段静态断言（批A 落地）+ 评审 checklist |

## 9. 验收 DoD（Phase3 收口判据）

①ApplicationRoot 为唯一 Create/Inject/Register 点；②Autoload ≤ 8 且全为引擎壳；③GameManager 无业务装配代码；④verify_all 十五槽全绿 + A1 集成链绿；⑤02 图 §15 映射表 Phase3 条目全销；⑥更改日志逐批留痕。
