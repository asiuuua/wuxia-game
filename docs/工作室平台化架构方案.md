# 工作室开发平台 —— 平台化架构方案（可落地执行层）

> 版本：v1.0 草案 ｜ 定稿日期：2026-09-02 ｜ 作者：架构梳理（AI-架构）
> 定位：把当前「单机版武侠内容工作室」演进为「横向能力模块 × 纵向工程版本」的二维解耦平台，
> 支持多角色登录、版本一键切换、跨项目总控台与 git 元数据中心，未来可整体抽成独立后台工具。
> **本质再定位（2026-09-02）：平台是「连接器」而非「数据容器」** —— 只对接各工程、不复制工程数据；
> 提供三大复用能力：①新 AI 一眼读懂各工程架构（ai_context）②换皮不换药·小白只换图/乐/文（reskin）③前人踩坑与经验跨项目复用（knowledge）。
> 远程调度紧迫度极低，已延后（记入待办清单），架构预留配置化绑定 + 鉴权前置，需要时一步扩展。

---

## 〇、一句话总纲

当前工具 = 一个**写死单个工程（武侠游戏）的单页 Web 工具**。
目标平台 = 一个**插件化、可鉴权、多工程切换、带跨项目总控台的内容开发中台**；
它**只对接工程、不持有工程数据**——是辅助不同职能人员（美工/前端/架构/PM/代码审核/任务追踪/剧情）高效工作的「连接器」。

演进不推翻现有代码，而是分 6 个 Phase 把 `studio_core.py` 的「单体现状」逐步重构成「模块注册中心 + 工程适配器」两层解耦，每一层都能独立发布、独立复用。
平台最高价值不在"功能多"，而在**让经验跨项目复用、让换皮成本趋近于零、让新 AI 秒懂你的架构意图、让多工程进度一眼纵览**（详见第十二章）。

## 一、现状剖析（五个视角）

### 1.1 程序员视角（最痛：单体 + 硬编码）
- `studio_core.py` 一个文件 200+ 函数，全部业务混在一起（NPC/剧情/登录/战棋/资源/回收站/日志）。
- 加一个功能 = 同时改三个文件：`studio_core.py`（逻辑）+ `studio_server.py`（路由）+ `index.html`（界面），耦合极高。
- 工程路径写死：`_paths()` 直接拼 `D:/武侠游戏/...`，换项目必须改源码。
- 无单元可测：每个模块没有独立入口，只能整服务跑 `security_selftest`。

### 1.2 架构师视角（缺：插件总线 + 适配器）
- 没有「模块自描述清单」，前端 tab 全靠 `index.html` 里手写 `<section>` + `<button data-tab>`。
- 没有「工程适配器」概念，无法在不改核心的情况下接第二个工程（小程序/未来 RPG）。
- 本地 `127.0.0.1` 绑定是硬上限，远程能力为零。

### 1.3 前端视角（缺：清单驱动 + 角色渲染）
- `index.html` 118KB 单文件，11 个 tab 全部渲染在 DOM 里，无组件、无路由、无动态加载。
- 想做「角色只看到自己模块」= 只能 JS 隐藏 tab，但逻辑和接口仍全暴露，不安全。
- 模块界面应改为「模块自带前端片段 + 注册中心按角色动态挂载」。

### 1.4 后端/运维视角（缺：鉴权 + 远程 + 可移植存储）
- 仅 `ThreadingHTTPServer` + Origin 白名单，无账号、无会话、无 HTTPS → 不能上公网。
- 数据落用户 `AppData/Local/StudioProTool`，换机器/换人不可移植。
- 无部署故事（仅 PyInstaller onefile 本地 exe）。

### 1.5 项目经理视角（缺：分类 + 所有权 + 总控台）
- 11 个 tab 功能蔓延，无逻辑归类、无模块所有权概念。
- 看不到「各工程总流程 / 人员进度 / 推进状态」——这正是本次补充要求的「总控台」。

## 二、现有功能归类（Domain Module 横向分类）

把当前 11 个 tab + 隐含能力，按**业务领域**归为 5 大 Domain Module。这就是你讲的「大方向先分类」。

| Domain Module | 当前挂接的 tab/功能 | 未来可下沉的能力 |
|---|---|---|
| **UI 视觉模块** | 登录界面、UI 贴图、预加载界面、主菜单布局、按钮背景、多分辨率变体 | 主题色板、字体、图标库、动效配置 |
| **剧情创作模块** | NPC 数据、剧情对话、欢庆模块 | 任务线编辑器、分支剧情树、配音字幕、过场 CG 编排 |
| **战斗关卡模块** | 战棋布局、Demo 立绘 | 技能数值表、敌人配置、关卡事件触发器 |
| **资产资源模块** | 立绘一键导入、纹理压缩(tscn_assets/compress_textures)、回收站(共享) | 音频库、特效库、资源依赖检查、批量导出 |
| **系统治理模块** | 设置、操作日志、待办清单、协同启动卡 | **跨项目总控台**、工程元数据中心、RBAC 用户管理、版本切换 |

> 归类原则：凡是「换游戏也依然存在、只是改配置」的能力放 Domain；凡是「只属于某个游戏的数据路径/格式」放 Adapter（见第五章）。

## 三、平台化目标架构（六层 + 总控台）

```
客户端层 ── 浏览器 / 远程桌面 / 本地 exe
   │  HTTPS / WSS
网关 + 认证层 ── 登录鉴权 / 会话 / RBAC角色路由 / 工程版本选择
   │
模块注册中心 ── 插件总线 / 模块自描述清单 / 动态路由
   ├─ UI视觉 Module  剧情创作 Module  战斗关卡 Module  资产资源 Module  系统治理 Module
   │   （每个模块自包含：路由 + 逻辑 + 前端片段，可独立增删）
   │
工程适配器层 ── 武侠游戏 Adapter / 小程序 Adapter / 未来RPG Adapter
   │   （每个 Project 一份 manifest.yaml：数据路径·格式·可用模块·校验规则）
   │
数据层 ── 本地JSON / 远程DB / Git仓库（可插拔）
```

### 3.1 总控台（Super-Admin 跨项目视图）—— 本次新增要求
位于「系统治理 Module」之上的一层 **Meta Dashboard**，只有超级管理员可见：
- **总流程看板**：各工程当前阶段（原型/内容填充/联调/发行）。
- **进度状态**：每个工程的任务完成率（来自该工程 git 的 handoff/commit_queue/change_log）。
- **人员当前进度**：各工程的 AI 窗口署名提交量、当前 open 派单、谁在推进什么。
- **推进进度**：跨工程的时间线、里程碑、阻塞项（红门禁）。
- 实现方式：总控台**不自己存数据、也不重写任务清单**——每个工程的任务进度清单由该工程在本地写好
  （`docs/backlog.json` / `tools/handoff.py dashboard` / `docs/更改日志.md` / `.workbuddy/memory/`），
  平台只**对接、复查、聚合显示**在后台软件上，让你一眼纵览多个工程的真实进度。这正是「连接器而非容器」的体现（详见第十二章）。

## 四、角色权限与专区设计（RBAC）

### 4.1 角色清单
| 角色 | 可见模块 | 说明 |
|---|---|---|
| 超级管理员（你） | 全部 + 总控台 | 看所有工程、所有模块、用户管理、版本切换 |
| 剧情创作者 | 剧情创作 | 只看到 NPC/对话/欢庆专属专区 |
| UI 美术 | UI 视觉 | 登录/贴图/预加载/主菜单 |
| 战斗策划 | 战斗关卡 | 战棋/技能/Demo |
| 资产管理员 | 资产资源 | 立绘/纹理/回收站 |
| 治理专员 | 系统治理(限本工程) | 日志/待办，看不到别工程数据 |

### 4.2 登录与鉴权流程
1. 用户访问 `/login` → 输入账号密码（或口令）。
2. 网关校验 `users.json`（本地先实现，远程可换 DB/LDAP）→ 签发会话 token。
3. 服务端按角色过滤「模块清单」返回前端 → 前端只渲染该角色有权限的专区。
4. **接口级兜底**：每个 API 路由在执行前校验 `token.role ∩ module.required_role`，客户端隐藏只是体验，服务端拦截才是安全边界（解决前端「隐藏但仍能调」的隐患）。
5. 选择工程版本 → 加载对应 Adapter → 模块按该工程 manifest 二次过滤（某工程没配剧情模块就不显示）。

## 五、工程版本切换 + 项目元数据中心（git-backed）

### 5.1 工程适配器 manifest（一份 YAML 描述一个工程）
```yaml
# projects/wuxia_game.yaml
project_id: wuxia_game
display_name: 墨影江湖（武侠RPG）
data_root: D:/武侠游戏
modules:                # 该工程启用哪些 Domain Module
  - ui_visual
  - narrative
  - combat
  - asset
  - governance
adapters:               # 各模块在这个工程下的数据映射
  narrative:
    npc_path: data/configs/npcs/town_npcs.json
    dlg_dir: data/configs/npcs/dialogs/shards
  ui_visual:
    login_bg: assets/ui/main_menu_bg.png
git_repo: D:/武侠游戏     # 元数据中心来源
```
切换版本 = 加载另一份 `manifest.yaml`（小程序/未来 RPG）。Domain 逻辑不动，只换映射。

### 5.2 元数据中心（本次补充要求：从 git 读各版本项目情报）
每个工程把以下文件清单纳入 git（当前项目已部分具备）：
- `docs/更改日志.md`（change_log 回填）— 任务进度/历史改动
- `docs/多AI协同机制_SOP.md` + `docs/变更通告_*.md` — 协作流程/skill 流程
- `tools/handoff.py dashboard` 输出 — open 派单/隐患/人员归属
- `tools/commit_queue.py` — 提交队列/推进状态
- `docs/契约总表.md` / `screens.json` — 设计结构/接口契约
- `.workbuddy/memory/MEMORY.md` + 每日日志 — 开发思想/架构/踩坑

平台「治理 Module / 总控台」读取这些文件（本地直接读、远程走 git API/clone 快照），渲染：
**任务进度 · 设计结构 · skill 流程 · 曾经 BUG · 开发思想 · 架构** 六个情报面板。
这样「从平台也能看各版本项目任务进度、设计结构、skill 流程、BUG、思想、架构」即成立，且数据源是 git（单一真相源，可复用、可审计）。

### 5.3 工程详情面板（每个版本的详细记录全景）— 本次补充要求
总控台点开「某个工程版本」后，不只看进度数字，还要能调阅该工程从 0 到现在的**全套详细记录**。这些记录按维度归类，全部以 git 仓库为单一真相源（本地直接读、远程走 git 快照/API）：

| 记录维度 | 平台呈现内容 | 数据源（git 内文件/目录） |
|---|---|---|
| **开发落地架构** | 模块分层图、依赖方向、装配中枢、数据流 | `docs/架构总览.md`、`autoload→core→data→...` 目录结构，`docs/契约总表.md` |
| **项目预设** | 引擎版本、平台目标、世界结构、战斗模式、画面目标态 | `project.godot`、`docs/项目预设.md`、各 `data/configs/**` 初始清单 |
| **后台源代码** | 服务/逻辑入口索引、关键模块文件树、接口清单 | `tools/**`、`studio_core.py`、各 `core/**`、`services/**`（`gen_contract` 产出） |
| **开发工具** | 工具清单、用途、快捷指令、自检脚本 | `tools/` 各脚本 + README、`security_selftest.py`、各 `.bat` 启动器 |
| **整体约束** | 架构铁律、安全红线、双闸门门禁、UI 硬规 | `.workbuddy/memory/MEMORY.md`、`docs/多AI协同机制_SOP.md`、pre-commit 钩子说明 |
| **框架思维** | 设计权衡、踩坑教训、决策记录、演进路线 | `.workbuddy/memory/YYYY-MM-DD.md` 每日日志、`docs/变更通告_*.md`、commit 留言 |
| **任务进度**（既有） | 完成率、open 派单、里程碑 | `handoff.py dashboard`、`commit_queue.py`、`docs/更改日志.md` |
| **设计结构 / skill 流程 / 历史 BUG**（既有） | 界面树、协作 SOP、回归记录 | `screens.json`、`docs/多AI协同机制_SOP.md`、`change_log` 查询 |

> 关键设计：**工程详情面板不新建数据库**，而是「git 文件 → 平台结构化渲染」。
> 每个工程把自己的文档/配置/源码纳入 git，平台按上面的映射表解析并分维度展示。
> 换一个工程版本 = 换一份 `manifest.yaml` 指向另一个 git 仓库，详情面板自动呈现那套工程的记录。
> 好处：记录永远跟着工程走、可审计、可迁移、不重复维护；新项目照模板补齐这些文件即可被平台直接读。

## 六、远程调度与部署（未来预留）

| 能力 | 当前 | 目标 |
|---|---|---|
| 绑定地址 | 127.0.0.1 | 配置化（0.0.0.0 走反代/隧道） |
| 传输 | HTTP | HTTPS（反代或内嵌证书）+ WSS 长连接推进度 |
| 鉴权 | 无 | 网关统一鉴权（第四章） |
| 存储 | AppData 本地 JSON | 可插拔：本地 JSON / 远程 DB / Git |
| 部署 | 本地 exe | 容器化常驻（Docker）或继续 exe 但支持远程隧道 |
| 审计 | studio_log.jsonl | 操作审计 + 总控台跨工程聚合 |

> 远程前置条件 = 必须先有第四章鉴权，否则绝不暴露公网（当前 Origin 白名单不足以抗公网）。

## 十一、性能与初学者选型指导（大数据不卡顿 + 可复用）

### 11.1 需要你拍板的四个方向（架构师不敢替你猜）
1. **远程的紧迫度**：✅ **已决策（2026-09-02）**：紧迫度极低，当前完全用不到、离落地很远。
   → 远程（Phase 4）延后，已记入待办清单（`platform` 模块）；架构已预留「绑定地址配置化 + 鉴权为前置条件」，
   未来真要公网时按 Phase 4 一步扩展，不阻塞当前任何开发。
   → Phase 3 鉴权可降级为「本地多角色权限」（成本低），真要远程再补网关鉴权。
2. **"大型数据"到底是什么规模**：是 NPC/剧情条目上万条？还是贴图/音频几十 GB？还是跨工程的历史文档库？解法完全不同。
3. **技术栈偏好**：继续纯 Python（你已会），还是接受 Node/前端框架？——决定"不卡顿"前端实现的难度。
4. **单人还是真多人并发**：现在只是你 + 几个 AI 窗口，还是要真人同时编辑同一份数据（并发冲突）？——决定要不要上数据库事务/锁。

### 11.2 不卡顿的三招（前端 + 后端 + 资产）
- **前端三招**：分页（一次只取 50 条）、虚拟滚动（只渲染可见行）、懒加载（点开再取详情）。**绝不一口气渲染万行**。
- **后端三招**：用 SQLite 替代"每次读整个 JSON 进内存"、按需查询、大文件走 URL 引用不内联 base64。
- **资产铁律**：贴图/音频/视频留文件系统，数据库只存路径。绝不把二进制塞进 JSON/数据库。
- **当前工作室的瓶颈点**：每次 GET 把整个 `town_npcs.json` 读进内存返回——几百条 OK，上万条会卡。改 SQLite 或分页即解。

### 11.3 小白也能驾驭的最小可复用选型
- **后端**：Python + `sqlite3`（标准库自带，零安装）+ 现有 `http.server` 够撑到中等规模。
- **前端**：保持原生 JS，但加"列表分页 + 只取当前页"。
- **数据分两类**：结构化（配置/日志/NPC/change_log）进 SQLite；大二进制（贴图/音频/视频）留文件系统，DB 只存路径。
- **这套组合能撑**：单机 / 小规模远程毫无压力，且你已会、零新依赖。

### 11.4 架构师该拦的过度设计（现在别碰）
- **别现在上 Docker / PostgreSQL / Redis / K8s**：对单人项目是负担，等真有并发再引入。
- **别现在拆微服务**：单体 + 模块注册中心（Phase 1）足够，微服务是团队 >10 人后的事。
- **别为"将来可能"预建所有表**：先按现有 5 个 Domain 建最小表，缺什么加什么（加法式演进）。
- **一句话原则**：先用最少的工具把事做对，卡了再优化，别为想象中的规模提前受罪。

## 十二、平台本质再定位：连接器 + 三大复用能力（2026-09-02）

> 本章是你对平台本质的最新拍板，是后续所有 Phase 的「设计宪法」。
> 一句话：**平台是辅助不同职能人员的「连接器」，不是任何工程的数据容器。**
> 它只对接工程、不持有工程数据；最高价值 = 经验跨项目复用 + 换皮成本趋零 + 新 AI 秒懂架构 + 多工程进度一眼纵览。

### 12.1 连接器而非容器（核心铁律）
- **不复制、不存储工程数据**：平台只描述"工程在哪、有哪些模块、怎么对接"（即 `manifest.yaml`），工程数据始终留在各工程自己的 git 仓库。
- **任务进度本地写好、平台对接复查显示**：每个工程的任务清单由该工程在本地写好
  （`docs/backlog.json` / `tools/handoff.py dashboard` / `docs/更改日志.md` / `.workbuddy/memory/`），
  平台只**对接、复查、聚合**显示在后台软件上，绝不写第二份、绝不重写。
- 好处：平台自身极轻、永不膨胀；任一工程删了平台不受影响；新工程照模板补一份 `manifest` 即接入。

### 12.2 能力一：AI 可读上下文（ai_context）—— 新 AI 秒懂你想要的架构
- `manifest` 的 `ai_context` 段 = 工程的「上岗说明书」，新 AI 窗口 / 新人接手即懂你大致想要的架构，不用每次重新摸索。
- 包含维度：`architecture_intent`（架构意图）/ `key_decisions`（关键决策）/ `conventions`（约定）/ `common_pitfalls`（高频坑）/ `role_responsibilities`（各角色边界）。
- 平台把这一段直接作为「接手本工程的 AI 系统提示」喂给对应窗口，等于把你的架构思维标准化、可传承。
- 模板见 `tools/desktop_studio/projects/manifest_template.yaml` 的 `ai_context:` 段。

### 12.3 能力二：换皮不换药（reskin）—— 小白只换图/乐/文，底层不动
- `reskin` 段列出"可被替换而不破坏工程"的资产/文本层（立绘/头像/音频/剧情文本/主视觉）。
- 不懂开发的小白只换这几类，底层 `core/ services/ autoload/` 与 `EventBus` 契约（见 `docs/契约总表.md`）**绝不碰** → 换皮成本趋零。
- `reskin.locked` 段明确"换皮绝不碰"的边界，平台可据此自动生成一份「换皮清单」给非开发者照着填。
- 价值：同一套底层可批量出"皮不同、内核同"的项目（如换题材/换美术风格/换文案），复用底层经验、边际成本骤降。

### 12.4 能力三：知识复用（knowledge）—— 前人踩坑与经验跨项目复用
- `knowledge.refs` 指向本工程 git 内的经验沉淀，**首推 `docs/项目经验白皮书.md`**（大厂级工程梳理 + 评价方案 + 复盘调优总源，新 AI/新人优先读），另含 `docs/多AI协同机制_SOP.md` / `.workbuddy/memory/MEMORY.md` / `docs/变更通告_*.md` / `docs/契约总表.md`。
- `reusable_patterns` / `predecessor_mistakes` 把"前人怎么做的、踩过什么坑"结构化，跨项目可被检索。
- 总控台（Phase 6）读取 `knowledge.refs` 渲染「经验库」面板：你以后开发小程序等新项目时，能直接看到武侠项目沉淀的架构思路、踩坑、约定，新 AI 也能一键继承。

### 12.5 与版本切换的关系（二维落地的收口）
- **切换版本 = 加载另一份 `manifest`**（小程序 / 未来 RPG）。
- 同一份 Domain 逻辑（横向能力），不同 `manifest` 的 `ai_context / reskin / knowledge` 不同 → **既共享底层，又各自沉淀经验**。
- 这就是你说的"大方向一致（Domain 模块：UI/剧情/战斗/资产/治理），具体项目不同（manifest 对应各工程）"。

### 12.6 对 Phase 计划的微调
- **Phase 2** 落地 `manifest` 时即带 `ai_context / reskin / knowledge` 三段（几乎零额外成本，模板已备好）。
- **Phase 3** 鉴权：因远程延后，降级为「本地多角色权限」（成本低、体验好），真要远程再补网关鉴权。
- **Phase 6** 总控台增加「经验库」面板，读取 `knowledge.refs` 聚合跨工程经验。

> 落地产物：本章理念已固化为可直接复制的 `tools/desktop_studio/projects/manifest_template.yaml`（含三段注释模板），
> 任一新工程复制该文件、填本工程路径与上下文即可被平台一键对接。
