## 一、审计方法（可复现）

```bash
python tools/audit_signal_contract.py --json /tmp/signal_audit.json
```

- 从 `autoload/EventBus.gd` 解析全部 `signal X(...)` 声明（名 + 形参个数）。
- 全工程（排除 `.git`）扫 `.gd`：
  - emit：`EventBus.X.emit(` 与 `EventBus.emit_signal("X"`
  - connect：`EventBus.X.connect(` 与 `EventBus.connect("X"`
- 逐信号输出 emit 数 / connect 数；判定孤儿（emit=0 或 connect=0）与未声明引用。
- 局限：经中间变量转发（`var b=EventBus; b.X.connect`）或极个别字符串化订阅可能漏计；本报告对每处高危发现均做了**二次定向 grep 复核**（见 §三/§四）。

## 三、FINDING-1 🔴 战斗内用药被 consume 但 `item_used_in_battle` 无订阅方 → 效果静默丢失

- **【模块】** battle（缺失订阅方在战斗场景；生产方在 inventory）
- **【维度】** 隐藏风险（表面不报错但行为异常 / 资产损失）
- **【严重度】** 🔴 红（扣料丢产出：物品消失、治疗/经验不生效）
- **【证据】**
  - 生产：`services/inventory/inventory_service.gd:450`（`_apply_use_heal` 战斗分支）、`:521`（`_apply_use_exp` 战斗分支）均 `consume_instance(inst.instance_id)` 后 `EventBus.item_used_in_battle.emit(item_id, effect)`，返回 `BATTLE_PENDING`。
  - 契约说明：`autoload/EventBus.gd:25` 注释明确「背包不直接改 PlayerState，由战斗场景经战斗状态(护盾/溢出/HUD)结算」。
  - 消费：**全工程零 `EventBus.item_used_in_battle.connect`**（含字符串形式），二次 grep 复核仅命中声明/测试 SEAMS 表/2 处 emit。
- **【正向推演】** 设计意图：战斗内用消耗品 → 背包扣物品 → 广播 `item_used_in_battle` → 战斗场景监听并结算 hp/mp/exp。代码实现了前两步，第三步（战斗场景订阅）缺失 → 链路断在最后一环。
- **【逆向推演】** 触发路径：战斗内通过 inventory 走 `use_item(item, "battle")` → `consume_instance` 已扣物品 → emit 无人接收 → 玩家损失物品、血/蓝/经验无变化。`GameLogger.info("已派发战斗结算")` 制造"成功"假象，掩盖失效。
- **【修改建议】** 战斗窗口在 `BattleScene`（及战术版）`_ready` 内 `EventBus.item_used_in_battle.connect(_on_item_used_in_battle)`，按 `effect.hp/effect.mp/effect.exp` 经战斗状态结算（护盾/溢出/HUD）；或改为 inventory 直调 `combat_service.apply_item_effect`（绕过 EventBus）。**先确认战斗用药 UI 是否真走 `inventory_service.use_item(..., "battle")`**（若战斗有独立用药入口则本路径为死代码，但仍应修契约）。
- **【待办归类】** type=隐性BUG  status=open  （已写入 backlog `battle` 模块；handoff 派单战斗窗口）
- **【主权】** 需改战斗场景代码 → 越权禁改，handoff 派战斗窗口。

## 四、FINDING-2 🟡 17 个 EventBus 信号未接线（死信号 / 契约漂移）

- **【模块】** audit（契约/共享地基层清理；改 EventBus.gd 须双窗口协同）
- **【维度】** 代码坏味道 / 接口契约漂移
- **【严重度】** 🟡 黄（无运行时崩溃，但契约噪音 + 维护负债；`@warning_ignore` 掩盖 unused_signal 警告）
- **【证据 · 16 个完全死信号（emit=0 且 connect=0）】**
  - **CMD 模式被直调替代（7）**：`cmd_buy`、`cmd_sell`、`cmd_forge`、`cmd_join_sect`、`cmd_contribute_sect`、`cmd_set_unit_faction`、`cmd_apply_story_buff` —— 声明为"UI→服务指令型"，但商店/锻造/门派实际走 `GameManager.xxx_service` 直接 DI 调用，EventBus CMD 通道被弃用。
  - **事件信号未接线（9）**：`bond_romance_stage_changed`、`combat_character_died`、`config_loaded`、`config_validation_failed`、`grid_unit_moved`、`quest_ready_to_turn_in`、`ui_screen_opened`、`ui_screen_closed`、`unit_downed` —— 声明为事件通知，但生产方/消费方均缺失。
- **【证据 · `player_exp_changed`（connect=1 但 emit=0）】**
  - `scenes/ui/overlays/hud/status_card_panel.gd:50` 完整 `connect(_refresh)`（且 `:77` 对称 `disconnect`），但 `data/runtime/player_state.gd` 的 `gain_exp()`（`:87-100`）只 `experience += amount` 并在升级时 `emit player_level_up`，**从不 emit `player_exp_changed`**。
  - 且 `_refresh`（`:84-114`）只读 hp/mp/level/silver/attrs，**不读 exp** → 即使补 emit 也不改变显示。HUD 状态卡当前无经验条。
- **【正向推演】** 契约声明了经验变化通知 + HUD 订阅，设计希望经验条随增益刷新；实际生产端缺失 emit 且订阅者不渲染经验 → 信号为死重。
- **【逆向推演】** 影响面：无运行时崩溃，但（1）`player_exp_changed` 占用 HUD 连接槽位却永不触发；（2）16 死信号使 EventBus 契约表膨胀，新 AI 按契约真源 `test_eventbus.gd` SEAMS 表误以为这些信号在用，可能写出接空信号的代码。
- **【修改建议】** 架构/共享地基窗口统一处置：① CMD 7 个确已改直调 → 删 EventBus 信号 + 调用方残留（若有）；② 事件 9 个确为预留 → 补 `reserved` 注释或删；③ `player_exp_changed` 要么 `gain_exp` 补 `emit` 且 HUD 显示经验条，要么删信号 + HUD connect。**`EventBus.gd` 是共享地基（冻结清单），任何改动须 `change_log` + 双窗口确认，单窗禁擅改。**
- **【待办归类】** type=占位  status=open  （已写入 backlog `audit` 模块）
- **【主权】** 改 `EventBus.gd`（共享地基）+ HUD → handoff 派架构/UI 窗口协同。
