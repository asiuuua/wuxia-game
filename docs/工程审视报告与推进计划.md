# 工程审视报告与推进计划

> 审视日期：2026-08-29 · 审视范围：全工程（300 文件 / 83MB，含 18 个 autoload、9 个 service、5 个场景）
> 本文是**项目管理视角**的总览。战斗域的技术细节见 `docs/战斗逻辑层架构设计.md`。

## 一、总体判断

### 架构骨架：✅ 正确，且高于多数独立游戏项目水平

| 维度 | 评价 | 证据 |
|---|---|---|
| 分层 | ✅ | `autoload → core → data → services → scenes` 五层单向依赖 |
| 解耦 | ✅ | 业务层（services）全部 `RefCounted`，零 Node 持有 |
| 数据驱动 | ✅ | 数值全在 `data/configs/**/*.json`，代码零硬编码数值 |
| 事件驱动 | ✅ | 跨模块只走 `EventBus`，60+ 信号 |
| 难度系统 | ✅ | 5 档配置 + `DefeatHandler` 复合行为，**代码零难度 if** |

### 但有三处「形似神不似」

1. **流程编排权在表现层手里。** 分层解决的是"数据放哪"，没解决"流程谁管"。战斗的回合流程写在 `BattleScene._on_action_pressed()`，城镇的交互流程写在 `TownScene._physics_process()`。**分层做对了，流程归属没做对。**

2. **业务层之间靠"隐式顺序契约"耦合。** `equipment_service.load()` 依赖 `player_state` 先加载完成——这个依赖**只存在于一行注释里**，没有任何机制保证。谁调整了 `SaveManager.register_saveable()` 的调用顺序，装备加成就会静默失效且零报错。

3. **`PlayerState` 一肩挑。** 同时是数据容器 + 属性计算中心（`recalculate_stats`）+ 事件发射器。

### 最危险的不是架构，是护栏为零

已实现 70% 垂直切片，但：**无版本控制、无战斗测试、无存档保护**。在这个状态继续加内容，等于在沙子上盖楼——每加一块都在增加推倒重来的成本。

> **已修复**：2026-08-29 建立 git，293 文件纳入版本控制，首次提交 `1414831`。

## 三、未来隐患（3–6 个月后会爆）

1. **EventBus 单文件 60+ 信号只增不减** → 高频事件唤醒全部订阅者；无订阅关系可视化，调试只能全局搜。
2. **配置表字段级 schema 校验覆盖存疑** → 内容量上来后一个 typo 就是运行时崩溃。
3. **`renderer/rendering_method=gl_compatibility`** → 2D 够用，未来要 2.5D 光照/法线/SDF 会受限。**现在换成本最低。**
4. **安卓是首发平台但零适配**：无 handheld 屏幕方向、无触屏输入映射、无 `[input]` 段。
5. **无 CI** → 靠人肉开 Godot 看报错；多 AI 并行时 A 改坏 B 不知道。

## 五、多 AI 协同纪律（2026-08-29 增补）

现状：两个 AI 并行改同一文件夹，无 git 时任何误覆盖都不可逆。**已建立 git 后，追加以下纪律：**

1. **每完成一个可验证的小改动就提交一次。** 提交信息写清楚改了什么、为什么。
2. **改名/删文件前先提交。** 否则 `git checkout` 救不回来。
3. **Godot 验证必须串行**——多个 Godot 进程抢 `.godot` 类缓存会玄学报错。
4. **`docs/` 下同一篇文档不要两人同改。**（今日已发生：项目日志文件被两个进程同时追加）
5. **文件主权划分**见 `docs/战斗逻辑层架构设计.md` 第 6 章。
