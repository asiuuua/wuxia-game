# UI 构造统一路线规范（2026-08-29 拍板）

> **本文件是架构决策（ADR）性质的硬规范**，回答一个被反复讨论、此前悬而未决的问题：
> 「本项目的 UI 究竟用 『编辑器静态装配 `.tscn`』 还是 『代码 `script.new()` 构建』？」
>
> 结论：**两者都不排斥，但按组件分层采用不同主模式，且无论哪种流派都必须遵守统一纪律。**
> 本规范与 `docs/HUD常驻系统落地方案v2_2026-08-29.md`（落地设计）、`docs/契约总表.md`（信号真源）、`docs/模块设计规范.md`（四底线）配套执行。

---

## 0. 一句话决策

| 组件类别 | 推荐主模式 | 一句话理由 |
|---|---|---|
| **全屏界面屏**（背包/结缘/设置/菜单/任务/武学/地图…） | **代码 `script.new()` 构建** | 数量多、配置驱动、diff 可读、门禁可验、多 AI 并行零 `.tscn` 冲突 |
| **HUD 顶层面板**（状态卡/任务追踪/技能栏/右上菜单） | **代码构建 `Control` 子类 + `setup()` 门面** | 常驻、需精确控制层级/生命周期、与 `UIManager` 坐标系耦合，代码更可控 |
| **HUD 叶子组件**（技能格/任务条目/血条/名字条） | **优先 `.tscn` 预制** | 纯展示、复用率高、编辑器可见、`preload` 收益最大 |

**核心判句**：*机制服从团队拓扑，纪律重于机制。* 单一项目内允许混合两种流派，前提是**统一纪律对所有组件强制生效**，且**每个组件能指出现有先例**。

---

## 1. 选型裁决理由（三视角）

### 1.1 设计哲学视角：`.tscn` 预制在「工作室规模」占优
- 美术/策划可在编辑器可视化装配、断点调试、复用拖拽、PR 评审直观。
- 适合**稳定、低频变更、由非程序员维护**的叶子组件（技能格、任务条目）。

### 1.2 代码工程视角：代码构建在「代码主导型团队」占优
- **Diff / 合并可读**：`.gd` 的改动是文本，Code Review 直接看到节点树；
  而 `.tscn` 是 Godot 二进制/文本混排的资源格式，合并冲突极难人工解决（多 AI 同分支并行已在本仓产生过"幽灵 `.tscn`/`.gd` 残留"）。
- **门禁可验**：`Godot --check-only --script res://x.gd` 能静态编译每个脚本；
  `.tscn` 的节点错误要等场景实例化（或跑具体 `*.tscn` 主场景）才暴露。
- **配置驱动天然**：本项目的全屏屏本就由 `data/configs/ui/screens.json` 名→脚本映射、运行时 `script.new()` 实例化，改动一处配置即上线新屏。

### 1.3 安全 / 严谨视角：代码构建在「协同防回归」占优
- 多 AI 并行同分支时，`.gd` 合并是行级文本冲突（可读、可解）；
  `.tscn` 合并是整块资源冲突（Godot 不保证三方合并正确，常静默丢节点）。
- 本仓治理铁律是"分层单向依赖 + 数值全进 JSON + 跨模块只走 EventBus"，
  这天然偏向**代码构建**（逻辑、数据、表现分离在 `.gd` / `.json` / `EventBus` 三处，而非压进 `.tscn` 的节点属性里）。

**结论**：本项目是代码主导 + 多 AI 并行 + 配置驱动的团队拓扑，故**代码构建为默认主模式**；仅当组件是"高复用、纯展示、低频变更"的叶子件时，`.tscn` 预制收益才超过其合并风险。

## 2. 分级采纳表（落地细则）

### 2.1 全屏界面屏 → 保持 `script.new()`
- **现有先例**：`autoload/ui_manager.gd` 的 `open_screen(screen_name, layer)`，
  由 `data/configs/ui/screens.json` 查 `script` 路径，`script.new()` 实例化。
- **新建屏流程**：①写 `scenes/ui/screens/<name>/<Name>Screen.gd`（继承 `Control`）；
  ②在 `screens.json` 纯追加一行 `{"name":"X","script":"res://.../XScreen.gd"}`；
  ③`UIManager.open_screen("X", UIManager.Layer.FULLSCREEN)` 打开。**不新建 `.tscn`**。
- **禁止**：把全屏屏改成 `.tscn` 静态挂载（`UIManager` 的屏幕栈只认 `script.new()`）。

### 2.2 HUD 顶层面板 → 代码构建 `Control` 子类 + `setup()` 门面
- **现有先例**：`scenes/ui/overlays/hud/Hud.tscn`（`.tscn` 壳）+ `Hud.gd`（代码建内部节点）。
  即"壳可 `.tscn`、内部全代码"，本规范沿用此混合先例：**面板根可以是 `.tscn` 壳，但内部节点一律代码建**。
- **每个面板暴露 `setup(...)` / `refresh()` 门面**，内部节点私有（`_xxx` 前缀），外部只调门面、禁 `$子节点` 跨文件访问。
- **挂载**：经 `UIManager.mount_hud(panel)` 进 `Layer.HUD` 的 `CanvasLayer`（见 v2 方案第 5 节），**禁止 `add_child` 到 `Node2D`**（会被 `Camera2D` 影响）。

### 2.3 HUD 叶子组件 → 优先 `.tscn` 预制
- **适用**：`skill_slot`（技能格）、`quest_track_entry`（任务条目）、单位血条/名字条等纯展示、复用频繁的组件。
- **构建**：编辑器建 `res://scenes/ui/overlays/hud/<name>.tscn`（根 `Control` 子类 `<Name>.gd`），
  父级用 `preload("res://.../<name>.tscn").instantiate()` 实例化，再调 `instance.setup(data)`。
- **纪律边界**：预制内部脚本**允许**用 `$自身子节点` 访问自己的子节点（合法）；
  **禁止**外部文件用 `$` 跨预制访问其内部节点——一律走 `setup()` / 自定义信号。
- **注意**：叶子件若需被 `preload` 编译期校验，其 `.tscn` 必须随屏一起入库，且 `import` 规则一致（见第 5 节门禁）。

## 3. 统一纪律（不论哪种流派，强制）

从 `docs/模块化预制实践文档评审` 提炼，上升为本项目 **UI 窗口硬性纪律**：

1. **单一职责**：一个组件只管一件事（一个面板 / 一个格子 / 一条条目）。
2. **内部封闭**：只暴露 `setup()/refresh()/@export` + 自定义信号；内部节点私有，外部禁 `$内部节点`。
3. **数据外部传入**：禁在组件内硬编码业务 ID / 数值；数据走 `setup(data)` 或 `GameManager.*_service` 公开 API（契合"数值全进 JSON"铁律）。
4. **`preload` 非 `load`**：循环/热路径实例化用 `preload`（编译期校验），不在循环内 `load()`。
5. **`_exit_tree` 断信号**：销毁时 `is_instance_valid(EventBus)` 判空 + `.is_connected()` 判真后 `disconnect`，防切场景 `freed object` 崩溃。
6. **通信优先级**：事件总线（`EventBus`）> 自定义信号 > `@export` 引用。跨模块**只走 `EventBus`**。
7. **禁轮询**：状态变化才 emit 刷新，禁 `_process` 里拉数据。
8. **嵌套 ≤ 2–3 层**：预制/面板嵌套过深难维护、难定位。
9. **禁硬编码坐标**：用 `Anchor + Offset + 安全区`（`UIManager.apply_safe_area(self)`），适配安卓刘海/挖孔。
10. **防穿透**：弹窗打开时 HUD `mouse_filter = IGNORE`，关闭恢复 `STOP`（订阅 `EventBus.ui_screen_opened/closed`）。

## 4. 与现有地基的映射（不得自创）

| 关注点 | 真实地基（务必复用，禁自造） |
|---|---|
| 屏实例化 | `UIManager.open_screen(name, layer)` + `screens.json`（代码 `script.new()`） |
| HUD 挂载 | `UIManager.mount_hud(panel)` → `Layer.HUD`（layer=50）的 `CanvasLayer` |
| 事件总线 | `EventBus`（**非** `GlobalEventBus`/`PopupUIManager`）；信号 `cmd_`(请求)/`notify_`(事实) |
| 数据源 | `GameManager.quest_service` / `ability_service` / `player_state` / `romance_service` 公开 API（**无 `get_instance()`**） |
| 信号真源 | `docs/契约总表.md`（由 `tools/gen_contract.gd` 重生成；共享地基只增不改） |
| 主题/令牌 | `core/constants/ui_theme.gd` 的 `UIPalette` + `data/configs/ui/ui_anim.json` + `ui_sfx.json`（禁裸色/裸时长） |
| 本地化 | `data/configs/localization/strings.csv`（禁界面内硬编码中文串） |

## 5. 多 AI 主权与门禁

- **本规范 owner = UI 窗口**（构造路线属 UI 主权）。其它窗口新增 UI 时**必须遵守本规范**，有异议走 handoff 协商，不得私自换流派。
- **新屏 / 新组件登记**：屏名入 `screens.json`（UI 主权）；组件若新增 `EventBus` 信号，走"共享地基只增不改"协议（追加 + 重跑 `gen_contract` + 写《变更通告》"共享地基增量"表）。
- **双闸门 + 构造校验**（每次改动须全绿）：
  1. `Godot --headless --quit` 零 `SCRIPT/PARSE/COMPILE/ERROR`；
  2. `tests/unit/run_all.tscn` 无 `✗`（退出码不传播，以 `✗` 为真实失败判据）；
  3. 若新增 `.tscn`：确认 `import` 成功（`.godot/imported/*` 生成），且被某 `.tscn` 主场景或 `preload` 引用，避免"孤立 `.tscn` 静默 null"。
- **git 收口**：改动统一由 UI 模块精确 `git add` 所列文件（**禁 `git add -A` / `git add .`**），提交信息 `[UI 窗口]` 前缀。

## 6. 违例判据与存量迁移

**违反本规范的情形**：
- 全屏屏改用 `.tscn` 静态挂载而非 `open_screen`；
- HUD 面板 `add_child` 到 `Node2D`（吃 `Camera2D`）；
- 组件内硬编码业务 ID / 数值 / 中文串；
- 跨预制用 `$` 访问内部节点；
- 新增屏未入 `screens.json`、新增信号未登 `契约总表`。

**存量不一致迁移**（已规划，不阻塞当前开发）：
- 现有 `Hud.gd` 已是"`.tscn` 壳 + 代码建内部"混合，符合本规范 2.2，**保持并拆 4 面板**（见 v2 方案第 9 节迁移步骤）。
- 技能格 / 任务条目当前在 `Hud.gd` 内联代码建，按 2.3 逐步迁 `.tscn` 预制（低风险、可独立派单）。
- 全屏屏已全量 `script.new`，无需改动。

## 7. 图标与美术接入（美术替换预留）
- **独立规范**：`docs/图标替换与美术接入规范.md`（解析接口 / 目录命名 / 数据配置 `icon` 字段 / 各界面接线点 / 美术导入设置 / 主权）。
- **核心接口**：取图标只走 `UIManager.get_icon(id)`（底层 `scenes/ui/icon_registry.gd`）；`id` 不含扩展名、可带子目录（如 `skills/fire_sword`）；资源只放 `resources/icons/<分类>/<名>.<ext>`。
- **美术零代码**：加图标 = 丢文件 +（首次）在数据配置写 `"icon": "<id>"`；换图标 = 同名覆盖。缺图标返回占位图、绝不 `null` 崩。
- **主权**：`scenes/ui/icon_registry.gd` + `UIManager.get_icon` 属 UI 窗口；其它窗口只读调用，不改引擎。美术直接管理 `resources/icons/`。
