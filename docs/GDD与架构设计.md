# 武侠江湖 · 游戏设计文档与架构设计（GDD）

> 版本 v0.1 · 2026-08-27 · 状态：**开工草案**
> 本文档是项目逻辑的「总锚点」。所有后续开发以本文为基线，新增系统须在对应章节追加，不推翻重来。

---

## 0. 文档用途
把分散的诉求收敛成可执行的逻辑基线：类型、平台、架构、系统清单、资产管线、分阶段路线、风险。

## 1. 项目定位与愿景
- **类型**：等距（俯视角）2.5D 武侠 RPG（单机）
- **画面**：3D 场景 + 2D 角色（立体江湖 + 纸片人立绘；Godot 中用 3D 地形/建筑 + Sprite3D 角色实现）
- **基调**：高自由度、CRPG 策略感、武侠 × 修仙混搭
- **终极目标（北极星）**：开放世界、多系统深度融合的「大型」武侠单机
- **现实约束（必须接受）**：纯个人开发 → 采用「数据驱动 + 模块化 + 分阶段切片」策略，先精做后扩展

## 2. 平台与技术栈
- **引擎**：Godot 4.x（目标 4.7）
- **首发平台**：Windows（桌面，质量最高）+ 安卓（移动，次优先）
- **后期平台**：iOS（需 Mac + 苹果开发者账号 $99/年）、Web（wasm 包体/线程限制，需精简）
- **语言**：GDScript（主）+ 必要时 GLSL 着色器
- **联网**：无联网、无账号、纯本地存档（单机）

## 3. 整体技术架构
### 3.1 设计原则
- **数据驱动**：技能/物品/敌人/任务/门派全部用 JSON/Resource 定义，由 `DataManager` 加载，逻辑与数据分离
- **模块化**：每个系统为独立模块（autoload 或场景），松耦合、可插拔、可增量添加
- **平台适配层**：输入（键鼠/触控）抽象、UI 自适应、导出配置分离

### 3.2 模块划分（详见架构图）
- **核心层**：`GameManager`（全局状态）、`DataManager`（数据加载）、`SaveManager`（存档）
- **世界层**：`RegionLoader`（区域枢纽式场景加载）、`TownScene`、NPC、交互/传送
- **战斗层**：`TurnBattle`（回合制状态机 + 自动战斗 AI）
- **养成层**：`SectSystem`（门派/武学树）、`CultivationSystem`（境界突破）、`WeaponSystem`（兵器专精）、`CompanionSystem`（伙伴协同）、`PetSystem`（宠物养成）
- **内容层**：`QuestSystem`（任务）、`DialogueSystem`（对话）、`EventSystem`（高自由度事件/抉择）
- **表现层**：3D 场景渲染、Sprite3D 角色、UI/HUD、特效

### 3.3 世界结构
**区域枢纽式**：城镇/野外为独立场景，读条切换（非无缝大地图）。等对距 RPG 主流做法，加载可控、单人友好。

## 4. 核心玩法循环
探索城镇/野外（区域枢纽切换） → 接取任务/触发事件 → 遭遇战斗（回合制 + 可自动战斗） → 获得经验/掉落/武学 → 修炼突破/学艺 → 自由度抉择 → **循环**

## 5. 系统模块详述（需求清单）
### 5.1 战斗系统
- 回合制 + 自动战斗（已选定）
- 行动顺序按速度；玩家指令 or 自动 AI
- CRPG 策略感（站位/阵法/buff 联动）放 Phase 2 再加深

### 5.2 武学体系（全部采纳，数据驱动批量接入，避免硬编码）
- 门派 + 武学树（加入门派学独门武功）
- 内功 + 招式自由搭配（DIY 流派）
- 境界突破（练气 → 筑基 → …）
- 兵器专精（刀枪剑棍）
- 伙伴协同上场
- 宠物饲养

## 6. 美术与资产管线（用户选定：AI 生成 + 自修）
- **规格表先行**：分辨率、调色板、风格参考图、帧数
- **生成**：2D 精灵用 AI 出图 → 修；3D 场景买底料 + AI/手改
- **风格一致性**：固定 LoRA/seed/参考图，避免「千人千面」
- **导入**：精灵帧动画 / 3D 模型 → `assets/` 规范命名
- **版权**：单机离线风险低，但商用/上架需确认授权

## 7. 分阶段路线图
- **Phase 0 脚手架与范式验证（本次开工）**：工程结构、数据驱动管线、战斗最小样例
- **Phase 1 垂直切片（1 城镇 + 1 战斗）**：区域枢纽城镇、一场回合战斗（含自动）、武学/境界数值骨架、本地存档
- **Phase 2 系统填充**：门派/武学树/内功外功/兵器/伙伴/宠物
- **Phase 3 内容扩张**：多区域、主线支线、CRPG 策略层、高自由度事件
- **Phase 4 平台适配**：安卓导出与触控优化 → 再 iOS → 再 Web

## 8. 风险与缓解
| 风险 | 缓解 |
|---|---|
| 范围过大 | 切片 + 数据驱动，先小后大 |
| 资产瓶颈 | AI + 自修，规格表控一致性 |
| 单人精力 | 模块化，每阶段可玩可见 |
| 平台坑（iOS/Web） | 放后期，先 Windows/安卓 |
| 手感/打击感 | 回合制影响小，Phase 1 后迭代 |

## 10. 工程纪律与代码规范（强制）
新增硬约束（用户要求）：代码必须**精简干练、零废物代码**，且**可拓展、可维护、易读**。
- **精简**：单函数单职责；不写永不被调用的死代码、不写无信息量注释、不过度抽象（YAGNI）
- **可拓展**：新系统走「数据驱动 + 模块化」接入；加技能/门派/敌人只加数据不改核心逻辑
- **可维护**：低耦合、单一职责；全局状态集中在 autoload 单例，不散落具体场景
- **易读**：中文注释解释「为什么」；命名见名知意；禁止魔法数字（常量集中定义）
- 已吸收**腾讯编码规范**（命名 / 注释 / 常量 / 单字符变量禁令）与**腾讯代码安全指南 secguide**（禁硬编码密钥、输入校验、日志不记敏感、第三方组件安全、单元测试），全部适配 GDScript 官方风格，详见 `docs/代码规范.md` §4–§7
- 企业级开发全标准见 `docs/开发规范.md`（架构分层 / 目录 / EventBus / 存档 / 模块 / UI / 性能 / CI 等二十章），为硬性底线；冲突以四底线（分层 / 事件驱动 / 数据驱动 / 命名）为准
- 业务模块权威设计基线见 `docs/模块设计规范.md`（用户提供的 11 维模块设计规范，覆盖玩家/背包/装备/武功/战斗/任务/存档等 P0–P3 全模块），Phase 1 已按此落地垂直切片
- 详细落地规范见 `docs/代码规范.md` 与 `docs/开发规范.md`，Phase 1 起所有提交前按「自检清单」过一遍
