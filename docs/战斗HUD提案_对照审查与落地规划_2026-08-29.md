# 《逸剑风云决》战棋战斗 HUD 提案 · 对照审查与落地规划

> 审查对象：用户提交的「战棋战斗HUD完整模块实现」（含 `battle_hud_root` / 左右状态卡 / `battle_top_right_panel` / `battle_skill_bar_hud` / `BattleGridNode` / `BattleEntity` / `BattleService` 片段）。
> 对照基线：本工程**真实**战斗架构（`CombatService` + `CombatCore` + `CombatState` + `CombatCharacter` + `BattleScene`/`BattleView`/`CombatDirector` + `EventBus` + `ability_service`）。
> 视角：程序员 / 项目经理 / 架构 / 美工 / 前端 / 后端 六重。
> 结论先行：**这份提案是一份高质量的设计蓝图，方向完全正确（数据-视图分离、EventBus 驱动、网格只画+收点击、输入状态机），但它是“通用 Godot 模板”，与本工程真实 API 完全不对齐，直接贴代码会编译失败；且它引入的是“网格移动 + 选格目标”的范式升级，当前战斗内核不具备位置/范围概念。应作为蓝图，落地时做一层“翻译+适配”，而非照搬。**

## 〇、一句话定位（给项目经理）

提案的 UI 结构（四角面板 + 底部技能栏 + 网格高亮）**可以直接复用**，但它假设的背后服务层（`BattleService` 单例、网格坐标、`SkillResource`、`unit_turn_start` 等信号）在本工程**全部不存在**。可落地的真实工作量 = 提案 UI 外壳（约 3 人天） + 提案未写全的服务层（网格数据层 + A* + 内核位置概念 + 敌人网格 AI + 输入状态机，约 15–20 人天）。**先出正交俯视 Spike 验证链路，再做等轴测皮肤**，可避开最大的隐形坑。

## 一、逐模块对照表（提案 vs 真实基线）

| 提案元素 | 真实基线现状 | 对齐结论 |
|---|---|---|
| `BattleService.get_instance()` | `CombatService`（RefCounted，挂在 `GameManager.combat_service`），**无类单例 get_instance** | ❌ 改名：`GameManager.combat_service`；或包装一个 `BattleGridController`（Node，战斗窗口主权）持有 `CombatService` + `BattleGrid` |
| `GlobalEventBus` | `EventBus`（autoload） | ❌ 改名 `EventBus`；且提案信号名**全部不存在** |
| `unit_turn_start(unit_id)` | 无；我们有 `combat_started/combat_ended/combat_character_died` | ❌ 需新增 `combat_unit_turn_started` 等信号（共享地基纯追加，走派单） |
| `unit_hp_changed/unit_mp_changed/unit_buff_changed` | 无对应；HUD 当前靠 `BattleView.play_event(CombatEvent)` 直设 | ❌ 提案用“信号广播全量”，我们架构是“事件流直设”。**建议沿用事件流契约**（内核吐 `MOVE/HP/STATUS` 事件），不要另起一套广播信号 |
| `grid_highlight_update(dict)` | 无；`BattleGridNode` 不存在 | ❌ 需新增 `combat_grid_highlight(dict)` 信号 + `BattleGridNode` 节点 |
| `unit_move_anim/unit_die/skill_cast_anim` | 无；演出走 `BattleView` 消费 `CombatEvent.Type.*` | ❌ 应扩展 `CombatEvent` 增加 `MOVE`/`SKILL_CAST`/`DIED` 类型，由 `BattleView` 播放，而非新增平行信号 |
| `auto_battle_toggled(bool)` | 无 | ❌ 需新增 `combat_auto_mode_changed(bool)` |
| `BattleUnitData`（`grid_pos`/`skill_list`/`buff_list`/`character_resource`） | `CombatCharacter`（有 `hp/mp/shield/cooldowns/status_effects/ai_kit/speed`，**无 grid_pos/skill_list**） | ❌ 给 `CombatCharacter` 加 `grid_pos:Vector2i`；`skill_list` 玩家侧来自 `GameManager.ability_service.equipped_combat`，敌人侧来自 `ai_kit`；`character_resource.portrait` → `UIManager.get_icon("npc/player" / "enemies/"+id)` |
| `SkillResource`（`icon`/`range`/`range_shape`/`area`） | `skills.json` 经 `ConfigManager.get_ability(id)` 返回 `Dictionary`（`qi_cost/cooldown/target/power/effects`） | ❌ 扩展 `skills.json` 加 `range`/`area`/`move_cost`（向后兼容，默认近身）；`icon` 走 `UIManager.get_icon("skills/"+id)` |
| `get_unit_data/get_skill_resource/get_current_battle_config` | `CombatService.get_state()` + `ConfigManager.get_ability(id)` + 无“战场条件配置”概念 | ⚠️ 部分复用；`win/lose_condition_text` 需新增 `battles.json` 字段 |
| `select_skill / on_grid_click / set_grid_highlight / spawn_battle_entity` | 全无（内核无位置/范围概念） | ❌ 全新增（Phase 2/3/4） |
| `try_flee_battle` | `CombatService.try_escape()` | ✅ 改名复用 |
| `do_action_regen` | `CombatService.player_rest()` / `CombatCore.player_rest()` | ✅ 改名复用 |
| `battle_surrender` | 无（当前只有逃跑/胜利/失败） | ⚠️ 需新增（认输=直接 DEFEAT） |

**核心判断**：提案里“UI 外壳层”（节点树、面板划分、输入状态机、两层 TileMap、HUD 只消费）**可直接落地**；它假设的所有“服务/数据/信号”**都需要按本工程命名重建一层适配**。这不是小改，是“多写一个战斗网格子系统”。

| 维度 | 直接照搬提案 | 经适配后落地 |

## 三、是否符合本项目（架构 / 主权 / 治理）

### 3.1 方向契合 ✅
- **数据-视图分离** ↔ 架构铁律（autoload→core→data→services→scenes）。
- **EventBus 驱动、HUD 只消费** ↔ 我们的 `notify_*` 哲学。
- **两层 TileMap 分离高亮** ↔ `BattleView` 只播不改的好作风。
- **输入状态机**（`IDLE/MOVE/SELECT_SKILL/SELECT_TARGET`）↔ 正是当前 `BattleScene` 缺失的（现在是“按钮即动作”）。

### 3.2 范式冲突 ⚠️（最致命的隐藏隐患）
当前战斗是 **非网格、无移动、自动/半自动回合制**（玩家点“普攻/技能”按钮 → 敌人全动）。提案是 **方格战棋：移动 + 选技能 + 选格子目标**。这是**战斗核心范式迁移**，不只是 UI 改皮：
- `CombatCore._resolve_hit` 只看 `target` 引用，**没有距离/范围/命中格概念**；
- `CombatState` 只有 `player + enemies`，**没有队伍坐标表、没有格子占用表**；
- 所以“蓝色可移动格 / 红色技能范围格”在现有结算里**没有对应判定逻辑**，必须给内核注入“位置”概念。

### 3.3 与现有 v2 HUD 的主权冲突 ⚠️（需你拍板）
- 我们已有全局 `Hud.gd`（layer 5）四面板，其中 `skill_bar_panel` 订阅 `notify_skill_cd_update`（秒读秒）。
- 提案的 `battle_skill_bar_hud` 是**战斗场景内独立技能栏**。两套并存会重复且可能打架。
- **决策建议**：战斗内技能栏**独立实现**（战斗冷却是“回合”不是“秒”，语义不同），进战斗时隐藏/不挂载全局 `skill_bar_panel`；或战斗 HUD 作为战斗窗口主权、全局 HUD 仅大世界用。归属需厘清（之前记忆里“BattleScene 是否 mount_hud”仍待决策）。

### 3.4 治理铁律
- 提案触碰 **共享地基**（EventBus 追加信号）→ 必须写《变更通告》+ 跨窗派单打招呼（纯追加，不动旧信号）。
- 战斗内 HUD / 网格 / 输入 = **战斗窗口主权**；按治理铁律，本窗口只产代码 + 双闸门 + 写通告，不自 git commit 它窗 WIP。

## 四、隐藏隐患（逐条，含提案自身 bug）

### 4.1 提案代码结构本身的缺陷（即便按本工程命名改对，依旧有 bug）
1. **`update_hp_mp(unit_id, current:int, max:int)` 语义错乱**：调用处 `update_hp_mp(id, current_hp, current_mp)` 把“当前真气”当“max”传入，`mp_bar.value = max` 是巧合正确；且**没有重设 hp/mp 的 max_value**，升级/ buff 改 max 时不会刷新。→ 应改为 `(hp, max_hp, mp, max_mp)` 四参。
2. **`BattleEntity.get_parent()` 取网格**：注释说“父容器 BattleEntityContainer”，但代码 `get_parent()` 取的是直接父。若实体加在 container、grid 是其兄弟，则拿不到 grid。→ 应**显式注入** `battle_grid` 引用（setup 传参或 `@export`）。
3. **`grid_to_world` 局部/全局混用**：`tilemap_ground.map_to_local(grid_pos)` 返回**局部坐标**，却赋给 `entity.global_position`（全局）。若 TileMapLayer 不在原点/有缩放，世界坐标错位。→ 应 `+ tilemap_ground.global_position` 或用 `to_global`。
4. **等轴测致命坑（最大隐形坑）**：`tile_size (128,64)` + `map_to_local/local_to_map` **默认是正方形网格**！Godot `TileMapLayer` 默认 `tile_set` 为正方形；要做 45° 等轴测，必须把 `TileSet.tile_shape` 设为 `TILE_SHAPE_ISOMETRIC`（2:1 half-offset）。否则 `map_to_local` 返回正交偏移，**斜 45 视觉与点击拾取全部错位**，且这种错位是“看着差不多但其实全错”的最难调类型。
5. **`_input` 依赖项目 InputMap 注册 `mouse_left_click`**：未注册则点击无响应；且 `_input` 全局触发，没做“点中哪个格子”的命中测试边界（靠 `is_grid_valid` 兜底，可接受）。
6. **`_exit_tree` 手动 `disconnect` 未判 `is_connected`**：若节点 add 但未进树即 free，`_ready` 未跑、信号未连，disconnect 会抛错；且 `battle_ended` 已在 `_on_battle_cleanup` 里 `queue_free()`，`_exit_tree` 再 disconnect 同一信号——应加 `is_connected` 判断或 `if event_bus.has_user_signal`。
7. **`on_grid_click` 未给 `cancel_select` 出口**：进入 `PLAYER_SELECT_TARGET` 后，点空白/右键无取消路径，易卡死状态。
8. **`execute_unit_move` / `execute_skill` 在提案 `BattleService` 里未实现**，依赖 `_reachable_move_grids` / `_skill_target_grids` / `BattleState` 枚举——全是要新写的核心逻辑。

### 4.2 与现有架构冲突的隐患
9. **平行信号 vs 事件流**：提案另起 `unit_move_anim/skill_cast_anim/unit_die` 信号，与现有 `CombatDirector.play_events(Array[CombatEvent])` 事件流**双轨并行**，会导致演出时序失控（两套动画驱动源）。→ 应**扩展 `CombatEvent`** 增加 `MOVE/SKILL_CAST/DIED` 类型，由 `BattleView` 统一播放（延续现有契约）。
10. **冷却语义分裂**：提案让 `BattleService` 维护“回合冷却”，但全局 `skill_bar_panel` 订阅的是 `notify_skill_cd_update`（秒）。两套冷却语义并存会显示不一致。→ 战斗内冷却走内核 `cooldowns`（回合），由 `CombatService` 在回合末 emit 给战斗 HUD；全局 HUD 的秒读秒仅大世界用。
11. **A* 与占用表的跨单位竞争**：多个敌人同时求“走到玩家相邻格”，若无占用表会挤同一格。→ `BattleGrid` 必须维护 `occupancy: grid_pos → unit_id`，移动前占用、移动后释放。

## 五、优点清单（提案做对的、必须保留）

- ✅ **数据/视图彻底分离**：网格只画+收点击，逻辑全在 Service。和架构铁律一致。
- ✅ **两层 TileMap**（地形/高亮分离），高亮层易清空——好，避免改原始地图。
- ✅ **EventBus 信号驱动、HUD 只消费**——和 `notify_*` 哲学一致。
- ✅ **输入状态机**（`PLAYER_MOVE` / `PLAYER_SELECT_TARGET`）——正是缺失的结构，方向正确。
- ✅ **状态卡 `_bind_unit_id` 过滤 + `_exit_tree` 断信号**——好习惯（实现有瑕疵但思路对）。
- ✅ **自动战斗仅控我方、怪物永远 AI**——和我们“自动战斗上限防死循环”的稳健思路一致。

## 六、详细落地规划（分阶段，含契约与主权）

> 总工作量约 **18–26 人天**（数据层 3 + 内核 A*/位置 6 + 视图 6 + 输入/AI 5 + 测试/收口 4–6）。
> 首切片（Spike）约 **3–5 人天**：正交俯视 2D 方格（先不做等轴测）、玩家+1 敌、移动+普攻、敌人走到相邻普攻、左下状态卡+底部普攻按钮。

### Phase 0 · 契约/地基（共享地基纯追加 · 需派单打招呼）
- `EventBus` 追加（**仅追加，不删旧**）：
  - `combat_unit_turn_started(unit_id:String)`
  - `combat_grid_highlight(dict:Dictionary)`（`{0:move_cells, 1:enemy_warn, 2:skill_cells}`，用 int 枚举代替提案的 enum 避免跨脚本 enum 耦合）
  - `combat_unit_moved(unit_id:String, from:Vector2i, to:Vector2i)`
  - `combat_skill_cast(caster_id:String, skill_id:String, targets:Array)`
  - `combat_unit_died(unit_id:String)`
  - `combat_auto_mode_changed(is_auto:bool)`
  - `combat_battle_condition(win_text:String, lose_text:String)`
- 写《变更通告_战斗网格信号增量》，对 GameManager/ability/quest 等跨窗派单确认 emit 点。
- 重跑 `gen_contract` 同步契约总表。

### Phase 1 · 数据层（战斗主权）
- 新增 `data/runtime/battle_grid.gd`（`BattleGrid` RefCounted）：`width/height`、`obstacles:Array[Vector2i]`、`occupancy:Dictionary(Vector2i→unit_id)`、`is_walkable/grab/occupy/release`。
- `CombatCharacter` 加 `grid_pos:Vector2i`（默认出生点由 `battles.json` 的 `spawns:[{id,grid}]` 注入）。
- `skills.json` 扩展 `range`(int, 默认 1) / `area`(int, 默认 0) / `move_cost`(int, 默认 1)，向后兼容。
- `battles.json` 加 `win_condition_text` / `lose_condition_text`。

### Phase 2 · 内核（战斗主权）
- `CombatCore` 增：
  - `compute_reachable(unit) -> Array[Vector2i]`（BFS + 占用表 + `move_cost` 上限）
  - `compute_skill_cells(skill_id, caster) -> Array[Vector2i]`（以 caster.grid_pos 为中心、按 `range/area` 生成合法格）
  - `execute_move(unit, grid_pos)`：更新 `grid_pos` + `BattleGrid` 占用 + emit `MOVE` 事件
  - `select_skill(slot)` / `execute_skill_by_cell(slot, grid_pos)`：**格子只决定“目标单位是谁”（取该格 occupancy 上的单位），真正命中结算仍走现有 `_resolve_hit`**——这点关键，避免重写结算。
- 敌人网格 AI：A* 走到玩家相邻格 → 选招（`_pick_enemy_ability` 复用）→ `execute_skill_by_cell`。

### Phase 3 · 视图（战斗窗口主权）
- `BattleGridNode`（Node2D + 两层 `TileMapLayer`；**`TileSet.tile_shape=ISOMETRIC` 仅在 Spike 之后换皮时配**；正交 Spike 用默认方形）：
  - 订阅 `combat_grid_highlight` 画高亮层；`_input` 拾取格 → `CombatService.on_grid_click`。
  - `grid_to_world` 用 `tilemap_ground.map_to_local(gp) + tilemap_ground.global_position`。
- `BattleEntity`（Node2D + `AnimatedSprite2D` + 头顶 `UnitHud` 风格飘字）：
  - `setup(unit_id, battle_grid)` **显式注入 grid**；`MOVE` 事件驱动 Tween 插值；`DIED` 事件播死亡后 `hide()`；`battle_ended` 统一 `queue_free()`。
  - **复用现有 `UnitHud` 的飘字/血条思路**，不要另写一套。
- `BattleHudRoot`（Control, layer=10）四子面板：`unit_status_card_left/right` + `battle_top_right_panel` + `battle_skill_bar_hud`，仅做订阅/转发，不写业务。

### Phase 4 · 输入状态机（战斗窗口主权）
- 新增 `BattleInputController`（或并入 `BattleScene`）：`IDLE → MOVE → SELECT_SKILL → SELECT_TARGET`，`on_grid_click` 按状态分派；提供 `cancel_select`（点空白/右键）。
- 手动/自动切换：`auto` 时**复用敌人同一套 AI 接口**驱动我方单位（提案点 3 的正确要求，保证行为一致，避免双逻辑分叉）。

### Phase 5 · 收口（双闸门 + 通告 + 派单 + git）
- 双闸门：`--headless --quit` 零 SCRIPT/PARSE/COMPILE ERROR；`run_all` 零 ✗。
- 新增单测：`test_battle_grid`（可达集合/占用）、`test_battle_move`（移动改坐标+释放占用）、`test_battle_skill_range`（范围格生成正确）。
- 写《变更通告_战棋战斗网格子系统落地》。
- 跨窗派单：EventBus 增量打招呼；确认 `ability_service`/`quest_service` emit 点未被破坏。
- 精确 `git add`（禁 `-A`），提交信息 `[战斗窗口]` 前缀。

## 七、给项目经理的取舍建议

1. **先 Spike 后皮肤**：正交俯视 2D 先跑通移动/AI/演出整链（避开等轴测 tile_set 大坑），再换等轴测视觉。
2. **格子只做目标过滤，不碰结算**：内核 `_resolve_hit` 不动，新系统只负责“把格子翻译成目标单位”，风险最小。
3. **沿用事件流契约**：扩展 `CombatEvent` 类型，不要让提案的平行信号和 `CombatDirector` 双轨。
4. **战斗内 HUD 独立**：和全局 v2 HUD 厘清主权，战斗冷却走回合语义。
5. **共享地基改动必派单**：EventBus 信号追加走《变更通告》+ 跨窗打招呼，守住治理铁律。
