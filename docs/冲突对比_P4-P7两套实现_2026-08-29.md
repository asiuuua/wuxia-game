## 二、逐模块代码级对比

### 2.1 资源管理器 ResourceManager

| 维度 | `D:\武侠游戏`（静态 `class_name ResourceManager`，无 Autoload） | `wuxia-game-fresh`（Autoload `extends Node`） |
|---|---|---|
| 注册方式 | 纯静态类，全局 `ResourceManager.xxx()` 调用 | 注册为 Autoload 单例（project.godot:42） |
| 同步获取 | `acquire_sync()` → `StreamingMediaLoader.load_blocking()` | `load_cached()` → 直接 `load()`（**主线程阻塞**） |
| 异步获取 | `acquire_async()` → 后台线程 + **process_frame 自动泵**回调 | `stream_resource()` + `poll_stream()`（**需调用方手动每帧 poll，无自动泵**） |
| 引用计数 | ✅ 三级：L1 常驻(refcount>0)/L2 温存 TTL/L3 冷回收 + 硬上限 256 | ✅ refcount + LruCache，无 TTL/硬上限分级 |
| 回收 | `reclaim_idle()`（限频扫描）/ `reclaim_all()`（**集中清立绘+战斗池**）/ `force_reclaim_all()` | `release()`（减引用）/ `evict()`（立即清）/ `clear()`（仅自身，不联动立绘/战斗池） |
| 关闭释放大资源 | 经 `release()` 归零后由 TTL/上限回收 | `evict()` 立即清（CG 界面关闭时逐路径 evict） |
| 铁律合规 | ✅ 零新 Autoload | ❌ 新增 ResourceManager Autoload（违反"不增新 Autoload"） |

**决定性差异**：武侠游戏的异步路径由 `SceneTree.process_frame` 信号泵驱动（`_ensure_pump` 连接一次），完成即回调，**真正不卡帧**；
fresh 的 `stream_resource` 只发起请求，`poll_stream` 必须由某处每帧调用，而 `CelebrationOverlay` **并未调用**——它实际走的是 `load_cached` = 同步 `load()`，**大 CG 视频会阻塞主线程**。

### 2.2 流式媒体加载 StreamingMediaLoader

- `D:\武侠游戏`：`core/streaming_media_loader.gd` 静态类，封装 `ResourceLoader.load_threaded_request/status/get`，提供 `request/get_status/take/load_blocking/cancel`，被 `ResourceManager.acquire_async` 与 `AudioManager` 语音池共用。
- `wuxia-game-fresh`：**无独立加载器**。`stream_resource/poll_stream` 直接内联在 `autoload/resource_manager.gd` 里，且无自动泵，等于半套异步。

### 2.3 对象池 / 实体池

| 维度 | `D:\武侠游戏` `CombatEntityPool`（静态） | `wuxia-game-fresh` `PoolManager`(Autoload)+`ObjectPool`(通用) |
|---|---|---|
| 注册 | 静态类，无 Autoload | `PoolManager` 是 Autoload（project.godot:38，两版都有，但武侠游戏**未使用=孤儿**） |
| 适用 | 专用于战斗实体：`Array[BattleEntity]` / `Array[UnitHud]` **类型安全** | 通用：`PackedScene` 驱动，可池化任意节点（飘字/特效/投射物） |
| 复用 | 空闲表复用 + `reset()` 清零防串场 + 超额 `queue_free` | prewarm 实例化 initial 个隐藏子节点；acquire/release + 自动扩容 |
| 隐患 | 静态空闲表跨整个引擎会话常驻（可接受） | ⚠️ `ObjectPool.acquire()` 在池空且超 `max_size` 时 **`_active.pop_front()` 偷一个在用对象** → 复用冲突/视觉串台；且池父节点随场景销毁后 `PoolManager` 仍持引用 → 悬空（靠 `unregister` 兜底） |
| 铁律合规 | ✅ | ❌ PoolManager 为 Autoload（预存共用，非本次新增；但武侠游戏侧已弃用） |

### 2.4 CG 视频 / 图片 / 语音接入（P5 落地）

- `D:\武侠游戏` `CelebrationOverlay._apply_media`：`ResourceManager.acquire_async(mpath, hint, _on_media_ready)` → 后台线程加载，**文字立即显示、媒体流式补位**，回调里才 `new VideoStreamPlayer/TextureRect`。`VideoStream` 显式 type_hint。✅ 真流式。
- `wuxia-game-fresh` `CelebrationOverlay._apply_media`：`ResourceManager.load_cached(mpath)` = 同步 `load()`，**阻塞主线程**；代码注释自称"大音频可改用 stream_resource"，但界面本身没用。❌ 名不副实的"流式"。

### 2.5 立绘 LRU（P2，图片 3000+）

- 两版 `core/portrait_cache_manager.gd` **字节级一致**（仅行尾差异）：静态 LRU、`cap=50`、`get_portrait/preload_portrait/clear`。**图片层无冲突、已共识。**
- 集成差异：武侠游戏的 `ResourceManager.reclaim_all()` 会顺带 `PortraitCacheManager.clear()` 做统一回收；fresh 的 ResourceManager 不联动立绘缓存。

### 2.6 超长文本（P1，对话分片）

- 分片数据 `_index.json` + `shards/*.json` 两版 **完全相同**（不在 75 冲突清单内）→ 按需加载 1M+ 对话的策略两版一致。
- `dialogue_service.gd` 仅差 **一行**：武侠游戏多 `"voice": line.get("voice","")`（P5 每行可选语音，数据驱动、零代码改动即可配语音）。**武侠游戏为严格超集，无冲突、无扩容差异。**

### 2.7 工程规范与批量校验（P7）

- `D:\武侠游戏`：`tools/validate_project.gd` 独立静态校验器（JSON 合法/禁 `.tres`/禁硬编码 `res://data|assets` 路径/类名 PascalCase/禁重复 class_name），已跑通 0 违规。
- `wuxia-game-fresh`：`tools/gen_contract.gd`（契约总表生成），无独立合规校验器；把 `ResourceManager` 纳入 autoload 表与契约。

## 三、架构优劣与隐患

### `D:\武侠游戏`（acquire / 静态）优劣
- ✅ **零新 Autoload**，完全符合项目铁律；与既有 `PortraitCacheManager`/`CombatEntityPool` 同构，风格统一。
- ✅ **CG/语音真异步**（process_frame 泵），不卡帧；三级分级回收内存有界。
- ✅ 战斗实体 **类型安全 + reset 清零**，杜绝跨战串场；`reclaim_all()` 一处管全部回收（立绘+战斗池+资源）。
- ✅ 超长文本/立绘为严格超集，共享地基零冲突。
- ⚠️ 静态空闲表跨引擎会话常驻（有界，可接受）；`project.godot:38` 仍注册了未使用的 `PoolManager` Autoload（**孤儿，建议清理**）。
- ⚠️ 仅在场景切换点调用 `reclaim_all()` 才集中回收；若某路径遗漏，温存条目靠 `reclaim_idle` 限频扫描兜底（不泄漏，但非即时）。

### `wuxia-game-fresh`（load_cached / Autoload）优劣
- ✅ 通用 `ObjectPool` 思路可复用于飘字/特效/投射物，灵活性高。
- ✅ `LruCache` 带 `pin/unpin`（对话/战斗进行中锁资源不被淘汰），概念好。
- ❌ **新增 ResourceManager Autoload**，违反"不增新 Autoload"铁律。
- ❌ **CG/大资源实际走同步 `load()` 阻塞主线程**，P5 流式目标落空（界面没用 stream 路径）。
- ❌ `stream_resource` 无自动泵，需调用方每帧 `poll_stream`，否则回调永不触发（**静默挂起/黑屏**风险）。
- ❌ `ObjectPool.acquire()` 在超限时会**偷一个在用 active 对象**，造成节点复用冲突/视觉串台（真实 bug）。
- ❌ `PoolManager` Autoload 持有场景局部父节点的池，场景卸载后易悬空（靠 `unregister` 兜底，脆弱）。
- ❌ 立绘缓存未被其 ResourceManager 联动回收。

## 四、四维度扩容适配性评估（用户关注点）

| 维度 | `D:\武侠游戏` | `wuxia-game-fresh` | 胜方 |
|---|---|---|---|
| **超长文本（1M+ 对话）** | 分片策略与 fresh 一致；额外支持每行语音，严格超集 | 分片策略一致，但无每行语音 | 武侠游戏（持平偏胜） |
| **战斗（百敌/多战/实体复用/无泄漏）** | 类型安全 `CombatEntityPool` + reset 清零 + 超额真释放；`reclaim_all` 统一回收 | 通用 `ObjectPool` 灵活，但 steal-active bug + 悬空风险 + Autoload | 武侠游戏 |
| **图片（3000+ 立绘 LRU）** | 与 fresh 完全相同（共识） | 与武侠游戏完全相同（共识） | 平手 |
| **CG 视频加载（流式/不卡帧）** | 真异步（threaded + process_frame 泵），文字先显媒体补位 | 同步 `load()` 阻塞；stream 路径无自动泵、界面未用 | 武侠游戏（决定性胜） |

**结论：4 项中武侠游戏胜 3、平 1，且唯一胜项为用户最在意的 CG 视频流式加载。**
