# 战斗逻辑层架构设计（可视化战斗版）

> 定位：本文档是战斗域重构的**唯一执行基线**。逻辑侧（战斗窗口）按此实现，UI 侧按第 6 章契约对接。
> 版本：v1.1 · 2026-08-29 · 基于 `docs/模块设计规范.md` 与 `docs/项目进度与协同开发框架.md` 的分层铁律。
>
> **M1 状态：✅ 已交付（2026-08-29）** — 事件契约 `CombatEvent`、逻辑内核 `CombatCore`、`ATB` 行动顺序、双资源（气血+真气）、招式分阶与冷却、真实状态引擎（DoT/HoT + 属性修正 + 层数/持续）、确定性随机 `SeededRNG` 全部落地；`combat_service` 门面保留旧接口零回归；13 项战斗单测 + 6 项存档单测全绿。第三章契约已按实际落地签名修订，原"理想签名"与实现不符处以实际代码为准。

---

## 一、现状诊断（重构理由）

当前战斗链路：`BattleScene`（表现层）→ `combat_service`（业务层）→ `CombatCharacter`（数据层）。

分层本身没错，但**流程编排权在表现层手里**，导致七个硬伤：

| # | 问题 | 位置 | 后果 |
|---|---|---|---|
| 1 | 回合流程写在表现层 | `BattleScene._on_action_pressed()` 手动串起 攻击→敌人回合→判胜负→结算 | 换表现层 = 重写流程；无法插入演出 |
| 2 | 战斗一帧跑完 | `player_attack()` 同步返回，自动战斗是 `while` 死循环 | 动画根本没机会播 |
| 3 | 无行动顺序概念 | `enemies.json` 的 `speed` 字段**从未被任何代码读取** | 快慢刀客无差别，策略感为零 |
| 4 | 随机数内联 | `CombatCharacter.take_damage()` 直接调 `randf()`，`AbilityService` 也是 | 不可复现、不可回放、不可单测 |
| 5 | 伤害公式硬编码 | `max(1, amount - int(defense * 0.5))` 写死在类里 | 改数值要改代码，违背数据驱动铁律 |
| 6 | 状态效果死代码 | `StatusEffect` 类 + `active_effects` 数组存在，但**从不 tick** | 中毒/内伤/增益全线缺失 |
| 7 | 表现层读字符串 | 只能拿 `CombatState.entries: Array[String]` | 不知道"谁对谁造成多少伤害"，飘字/血条动画无从下手 |

**结论**：不是 UI 做得不够好看，是逻辑层没给 UI 任何可演出的素材。

## 二、目标架构：四层 + 一条事件流

```
① 输入层   玩家 / 自动 AI  →  调用 CombatCore 行动方法（不碰状态）
                    ↓
② 逻辑域   CombatCore（纯 RefCounted，零 Node / 零 randf 依赖 / 零 Tween）
           ├ action_order()   速度条决定谁先动（ATB）
           ├ player_basic / player_skill / player_rest   玩家行动
           ├ enemy_phase()    敌人阶段（M3 接入权重 AI）
           ├ _resolve_hit()   伤害公式（属性 + 暴击 + 减伤，全确定性）
           └ tick_unit()      状态效果 tick（DoT/HoT + 持续递减 + 到期移除）
                    ↓  返回 Array[CombatEvent]
③ 事件流   CombatEvent 队列 · 唯一的层间契约 · 可序列化
                    ↓
④ 表现域   CombatDirector（演出编排，await 逐个播）→ CombatView（血条/飘字/立绘）
                    ↓  队列空
            请求下一回合，回到 ①
```

### 四条不可妥协的规则

1. **逻辑域不认识 Node，也不认识时间。** 没有 `await`、没有 `Tween`、没有 `delta`，一秒内算完一百回合是正常能力。
2. **战斗内事件不走 EventBus。** EventBus 是跨模块总线，战斗事件是高频有序流，走总线会污染全局订阅且顺序不可控。战斗内事件用**函数返回值**传递；只有 `combat_started` / `combat_ended` / `combat_finished` 这类跨模块通知才发 EventBus（注：`item_used` 因战斗内用药需刷新背包 UI，作为例外走 EventBus）。
3. **表现层只读事件，不读 CombatState。** 事件自带 `actor_id`/`target_id`/`value`/`crit`/`dodged`，演出层据此飘字、动血条，不回查状态对象。
4. **随机源必须注入。** `CombatCore` 持有 `SeededRNG`（包 `RandomNumberGenerator`），种子可外部指定，保证同一 seed + 同一指令序列 = 同一结果。

## 三、契约定义（先签契约，再分头实现）

### 3.1 新增枚举 `core/enums/combat_enums.gd`

⚠️ 此文件属**共享契约**，UI 窗口只读不改，改动需双方确认。

M1 仅在原文件**增量**追加了回合模式枚举（其余 `CombatResult` / `CombatType` / `Difficulty` / `DefeatBehaviour` 沿用旧值）：

```gdscript
enum TurnMode { SEQUENTIAL, ATB }   # 固定顺序(缺省回落) / ATB 行动值(对标逸剑集气条)
```

> **与原设计差异**：最初设想的 `EventType` / `EventFlag` / `Faction` / `CommandType` 四个枚举**未单独建立**——事件类型直接落在 `CombatEvent.Type`（见 3.2），暴击/闪避用 `bool` 字段而非位运算标记，阵营/指令类型由 `actor_id`/`target_id`/`skill_id` 承载。理由：GDScript 4.x 下少一层枚举包裹更省类型推断成本，且事件类型与事件结构强绑定，放一起更内聚。

### 3.2 `data/runtime/combat_event.gd`（新建 · 逻辑/表现层契约）

```gdscript
extends RefCounted
class_name CombatEvent

enum Type {
	TURN_START,      # 某单位开始行动（ATB 轮到它，顺序条高亮）
	ACTION_BASIC,    # 普攻
	ACTION_SKILL,    # 施展招式
	QI_COST,         # 真气消耗（招式付出）
	QI_GAIN,         # 真气回复（调息 / 心法）
	COOLDOWN_SET,    # 招式进入冷却
	DAMAGE,          # 造成伤害（含闪避/暴击标记）
	HEAL,            # 治疗
	STATUS_APPLIED,  # 施加状态
	STATUS_TICK,     # 状态每回合生效（DoT / HoT）
	STATUS_EXPIRED,  # 状态消失
	OUTCOME,         # 战斗结束（VICTORY / DEFEAT / FLEE）
}

var type: int = Type.DAMAGE
var actor_id: String = ""        # 发起者（如 "player" / "bandit_001"）
var target_id: String = ""       # 承受者
var value: int = 0               # 数值（伤害 / 治疗 / 真气 / DoT）
var crit: bool = false
var dodged: bool = false
var status_id: String = ""       # 状态 id（STATUS_* 事件用）
var stacks: int = 0              # 状态层数
var skill_id: String = ""        # 招式 id（ACTION_SKILL 用）
```

> **与原设计差异**：未带 `target_hp_after` / `target_max_hp` / `targets` 字段。M1 的演出层尚未接入（M2 才做血条直设值），当前事件以"谁对谁造成多少"为主，足够飘字与日志；M2 若需血条直设可补 `target_hp_after`（属共享契约，需双方确认）。

### 3.3 行动指令：未单独建 `combat_command.gd`

原设计想用 `CombatCommand` 对象解耦输入层。M1 落地时改为 **`CombatCore` 直接暴露行动方法**（`player_basic` / `player_skill` / `player_rest`），由 `combat_service` 门面把旧调用包装成这些方法。理由：当前只有一个输入源（玩家 UI），抽象出 Command 对象收益不大；待 M3 接入敌人 AI、M2 接入自动战斗时再评估是否需要 Command 层。

### 3.4 `services/combat/combat_core.gd`（新建 · 逻辑内核 · 单一文件）

> 原设计拆成 `turn_scheduler` / `damage_resolver` / `effect_system` 多个文件。M1 收敛为**单个 `CombatCore`**：更利于保持确定性随机源的单一持有者，避免多文件各自拿 RNG 导致 seed 序列错乱；后续若文件过大可按职责再拆（拆时不破坏对外方法签名）。

```gdscript
extends RefCounted
class_name CombatCore

var rng: SeededRNG = SeededRNG.new()   # 确定性随机源（注入，不用全局 randf）
var state: CombatState = null

## 绑定战斗状态。seed_val=0 时按时间派生（不可复现），非 0 严格可复现
func configure(p_state: CombatState, seed_val: int = 0) -> void

## 玩家普攻 → 事件流（内部先 tick 自身状态，再结算命中/伤害）
func player_basic(target_id: String = "") -> Array[CombatEvent]

## 玩家招式（slot=快捷栏位）→ 事件流（耗真气 + 冷却 + 施加状态 + 群攻展开）
func player_skill(slot: int, target_id: String = "") -> Array[CombatEvent]

## 调息（rest）：回血回真气 + 清除 clear_on_rest 状态
func player_rest() -> Array[CombatEvent]

## 敌人阶段：所有存活敌人依次行动 → 事件流
func enemy_phase() -> Array[CombatEvent]

## 单位回合开始 tick：DoT/HoT 生效 + 持续回合 -1 + 到期移除
func tick_unit(unit: CombatCharacter) -> Array[CombatEvent]

## ATB 行动顺序：按 effective_charge_rate()（speed + 状态修正）降序，返回 id 列表
func action_order() -> Array[String]
```

属性聚合在 `CombatCharacter` 上：`effective_attack()` / `effective_defense()` / `effective_crit_rate()` / `effective_dodge_rate()` / `effective_charge_rate()` —— 全部 `基础值 + Σ(status.value * stacks)`（flat 直接加、pct 按百分比）。伤害公式：`max(1, power - int(defense*0.5))`，暴击 ×`crit_damage`，再 ×`damage_taken_mult`（难度倍率），全程经 `rng` 决定闪避/暴击。

### 3.5 `services/combat/combat_service.gd`（改造为门面，保持对外兼容）

现有 `BattleScene`、`GameManager`、`DefeatHandler`、任务系统都在调它，**接口一律不动**，内部改为持有 `CombatCore` 并转发：

```gdscript
var _core: CombatCore = null

func start_combat(battle_id: String) -> void       # 保留，内部构建 CombatState 后 _core.configure(state)
func get_state() -> CombatState                    # 保留，返回 _state
func is_over() -> bool                              # 保留
func finalize() -> void                             # 保留（结算 + 写回 PlayerState + EventBus 广播）
func try_escape() -> bool                           # 保留
func get_core() -> CombatCore                       # 新增：给 Director / 测试注入 seed 用
func player_rest() -> Array[CombatEvent]            # 新增：调息（M1 双资源核心指令）
func player_use_item(instance_id: String) -> Dictionary  # 新增：战斗内用药（只结算战斗快照，不直调 InventoryService 回写）
```

`player_attack()` / `player_cast()` / `run_enemy_turns()` 保留为**兼容方法**（内部委托 `_core` 对应方法，再用 `_events_to_res()` 抽回旧式 `{hit,damage,crit,dodged}` 摘要供旧调用方）。**M1 未标 @deprecated**——等价 @deprecated 的收益要等 M2 演出层全面接管后才体现，提前废弃只会逼 BattleScene 大改；待 M2 完成再清理。

## 四、速度条与回合制（ATB）—— M1 已落地

### 4.1 ATB 模式（已在 M1 实现）

每个单位有 `speed`（来自 `enemies.json` / 玩家基线 10），`effective_charge_rate()` = `speed` + 状态修正（`疾行`类状态可加速）。`action_order()` 按该值降序排序，产出"接下来谁动"的 id 列表，供 M2 顺序条可视化。

- **终于消费了 `enemies.json` 里躺了很久的 `speed` 字段**——快刀客排在慢甲前，策略感起底。
- `battles.json` 的 `turn_mode: "atb"` 控制是否启用；缺省 `SEQUENTIAL`（与旧行为一致，保证不回归）。

### 4.2 保守 SEQUENTIAL 模式

固定顺序（当前实现为玩家先、敌人按配置序），每轮全员各动一次。实现简单、易调试，作为缺省回落。

### 4.3 配置化

`battles.json` 增加 `turn_mode` 字段：

```json
{
  "id": "battle_bandit_001",
  "name": "城外山贼",
  "turn_mode": "atb",
  "enemy_ids": ["bandit_001", "bandit_001"],
  "reward_exp": 30
}
```

## 五、演出编排（CombatDirector + CombatView）—— M2 待做

### 5.1 职责切分

| 层 | 文件 | 能做什么 | 禁止做什么 |
|---|---|---|---|
| 编排 | `battle_director.gd`（Node） | 取事件 → 分派 → `await` 等待完成 → 取下一个；管理加速倍率 | 不知道伤害怎么算 |
| 视图 | `battle_view.gd`（Control） | 播动画、跳数字、动血条，完成后发 `anim_completed` 信号 | 不判断战斗逻辑、不读 CombatState |

### 5.2 核心循环

```gdscript
func play_events(events: Array[CombatEvent]) -> void:
	for ev in events:
		await _play_one(ev)
	_emit_all_finished()

func _play_one(ev: CombatEvent) -> void:
	match ev.type:
		CombatEvent.Type.DAMAGE:
			_view.play_damage(ev)
			await _view.anim_completed      # 或 await 定时器兜底
		CombatEvent.Type.STATUS_APPLIED:
			_view.play_status(ev)
			await _wait(AnimToken.duration("fast"))
		_:
			await _wait(AnimToken.duration("fast"))
```

**超时兜底**：每个 `await` 都要配 `create_timer(duration * 3).timeout` 竞速，防止 View 漏发信号导致战斗卡死。这是新手最容易踩的坑——卡住以后没有任何报错。

### 5.3 时长一律走 UI 令牌

演出时长从 `data/configs/ui/ui_anim.json` 的 `durations` 读取，**不在脚本里写裸数字**。战斗演出需要的令牌若不存在，由 UI 窗口补进 `ui_anim.json`（属共享契约，需确认）：

```json
"battle": {
  "damage_pop": "normal",
  "hit_shake": "fast",
  "death_fade": "slow",
  "turn_gap": "gentle"
}
```

### 5.4 加速与跳过

- **加速**：Director 持 `_speed_scale`（1× / 2× / 4×），所有 duration 除以此值。
- **跳过**：`_speed_scale = 999`，且 View 的 `set_instant(true)` 直接跳到终态不播动画。
- 逻辑层**完全无感**——这正是分层的收益。

## 六、与 UI 窗口的协同契约（重要）

### 6.1 文件主权

| 归属 | 路径 | 说明 |
|---|---|---|
| **UI 窗口独占** | `scenes/ui/**`、`data/configs/ui/**`、`core/constants/ui_theme.gd`、`autoload/ui_manager.gd`、`resources/themes/**` | 战斗窗口不碰 |
| **战斗窗口独占** | `services/combat/**`、`data/runtime/combat_*.gd`、`data/configs/scenes/battles.json`、`scenes/gameplay/battle/**`、`data/configs/abilities/skills.json`、`data/configs/npcs/enemies.json` | UI 窗口不碰 |
| **共享契约（改前打招呼）** | `autoload/EventBus.gd`、`core/enums/combat_enums.gd`、`data/configs/ui/ui_anim.json`、`data/configs/ui/screens.json` | 单边改动必须告知 |

### 6.2 给 UI 侧的三条接口约定

1. **View 只实现这三个信号/方法，其余由 Director 调**：
   ```gdscript
   signal anim_completed
   func play_event(ev: CombatEvent) -> void    # 内部按 ev.type 分派
   func set_instant(enabled: bool) -> void     # 跳过模式
   ```
2. **血条不要自己去问"现在多少血"**。M2 事件若补 `target_hp_after` / `target_max_hp` 则直接设值；过渡期可据 `DAMAGE` 事件的 `value` 估算。这样断线、加速、跳过都不会错位。
3. **战斗界面若注册进 `screens.json`**（如 `BattleHUD`），命名与路径由 UI 窗口定，战斗窗口只负责在 `BattleScene` 里 `add_child(view)`。

### 6.3 防冲突三条

- 契约先落地（3.1–3.5 全部就位）再并行开发。
- **Godot 验证必须串行**——多个 Godot 进程抢 `.godot` 类缓存会玄学报错。
- `docs/` 下同一篇文档不要两人同时改。

## 八、风险与踩坑预案

| 风险 | 预案 |
|---|---|
