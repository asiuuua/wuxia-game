# 跨窗口协作隐患传递板规范

> 痛点：多 AI 并行开发，一个窗口改东西时常**踩到需要另一个窗口才能修的隐患**（如战斗窗口发现背包函数有缺口、UI 窗口发现某事件没广播）。以前只能跨窗口喊话。
> 方案：用一块「传递板」把"需要别窗做的事"写进去派给对应窗口；对方窗口隔段时间**自行认领、修完自验、标记完成**；派单方看到完成后，执行自己的后续依赖并收尾。全程无人值守。

生效日期：2026-08-29
负责人：背包窗口（兼 PM / 架构师）

---

## 一、总体架构

```
发现隐患的窗口（派单方）              执行窗口（认领方）              派单方收尾
────────────────────────            ───────────────────            ──────────
issue（派单）                  scan（定期扫 to==我）
   │  handoff_out_<派单方>.jsonl      │
   │                                  ▼
   │                            claim（认领）
   │                                  │  handoff_status_<执行方>.jsonl
   │                                  ▼
   │                            done（修完 + 按 verify 自验）
   │                                  │
   ▼ 看到 done                        │
followup（执行本窗后续依赖）◄─────────┘
   │  handoff_status_<派单方>.jsonl
   ▼
close（关闭）
```

- 目录 `.workbuddy/handovers/` 已加入 `.gitignore`，**不进版本库**。
- **派单方只写** `handoff_out_<派单方>.jsonl`（任务创建）；**执行方只写** `handoff_status_<执行方>.jsonl`（claim/done 事件）；派单方做后续时写 `handoff_status_<派单方>.jsonl`（followup/close）。每窗自有文件，append-only，无锁竞争。
- 任务状态由**事件重放**推导：`open → claimed → done → followup → closed`。

---

## 二、两阶段交接协议

### 阶段一：派单 → 认领 → 执行方自验（执行窗口主导）
1. **派单（issue）**：发现隐患的窗口完成任务式派单：
   ```bash
   python tools/handoff.py issue --from 战斗窗口 --to 背包窗口 \
     --title "CombatCharacter 缺不屈复活钩子" \
     --desc "M3-3 演出需要背包在 item 消耗时广播事件" \
     --files data/runtime/item_instance.gd \
     --verify "背包加事件后 run_all 背包测试 0 失败" \
     --followup "无（战斗侧已就绪）"
   ```
2. **认领（claim）**：执行窗口定期 `scan --window <我>`，看到 `open` 任务即认领：
   ```bash
   python tools/handoff.py claim --by 背包窗口 --id <id>
   ```
3. **执行方自验（done）**：执行窗口实际改文件，按 `verify` 字段自行核验（跑单测 / Godot `--quit` / 读代码确认），通过后：
   ```bash
   python tools/handoff.py done --by 背包窗口 --id <id> --note "已加广播事件，背包测试 28 项 0 失败"
   ```

### 阶段二：派单方后续（派单方主导）
4. **派单方后续（followup）**：派单方 `dashboard` 看到自己的任务已 `done`，执行依赖动作（如接上演出），记录：
   ```bash
   python tools/handoff.py followup --by 战斗窗口 --id <id> --note "演出已接上广播事件"
   ```
5. **关闭（close）**：双方确认后任一方 `close`。

> 一句话：**谁派单，等对方 done 后做自己的后续；谁认领，修完自验即 done。**

---

## 三、各窗口职责与边界

- **派单方**：写明 `to`（必须是该隐患真正归属的主权窗口）、`files`（尽量精确）、`verify`（可核验的通过标准）、`followup`（自己的后续依赖）。派单即承诺描述准确。
- **执行方**：认领后只改**本窗主权内**文件；若任务实际要求改共享地基或其它窗口主权文件，**不得擅自改**，改为在 `done` 备注里说明并标记放弃，回报用户/派单方另行协商。
- **主权边界**同《提交队列协同规范》：共享地基（`core/enums/*_enums.gd`、`EventBus.gd`、`ConfigManager.gd`、`ui/screens.json`、`strings.csv`）冻结，任何改动须先协商。
- 执行方 `done` 前的自验**必须真实跑过**（不跑 Godot 重验证的豁免仅适用于提交队列 flush，不适用于隐患修复——修隐患本身就要验证）。

---

## 四、PM / 背包窗口的自动化兜底

已建每小时自动化「协作隐患认领执行」（与提交队列自动化并列）：
- `scan --window 背包窗口`，对 `open` 任务取第一条 `claim`；
- 实际修复（守主权，越界则跳过回报）；
- 按 `verify` 自验；
- `done` 标记；
- 同时 `dashboard` 看本窗作为派单方的任务是否已 `done`，触发 `followup` 收尾；
- 每轮最多处理 1 条新认领，避免 runaway；无需询问用户。

其它窗口需在各自会话里也定期 `scan` 本窗 + 执行 + `done`（把这段贴进各自会话即可）。

## 五、命令速查

```bash
# 派单（发现需他窗做的事）
python tools/handoff.py issue --from <派单方> --to <执行方> --title "..." --desc "..." \
  --files a.gd --verify "..." --followup "..."

# 执行窗口：扫待办 / 认领 / 自验完成
python tools/handoff.py scan --window <窗口>
python tools/handoff.py claim --by <窗口> --id <id>
python tools/handoff.py done --by <窗口> --id <id> --note "..."

# 派单方：做后续 / 关闭
python tools/handoff.py followup --by <窗口> --id <id> --note "..."
python tools/handoff.py close --by <窗口> --id <id>

# 全局看板
python tools/handoff.py dashboard
```
