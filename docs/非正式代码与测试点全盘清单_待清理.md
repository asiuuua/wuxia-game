## 0. 门禁现状（盘点时实测 → 已修复）

| 闸门 | 命令 | 结果（盘点时） | 结果（2026-08-30 修复后） |
|---|---|---|---|
| GATE1 | `--headless --path "D:/武侠游戏" --quit` | ✅ 零 SCRIPT/PARSE/COMPILE ERROR | ✅ 仍零硬错 |
| GATE2 | `res://tests/unit/run_all.tscn` | ❌ **套件：通过 42 · 失败 1** | ✅ **套件：通过 43 · 失败 0** |

**原失败套件：`tests/unit/test_object_pool.gd`**
- 第一层根因：脚本调用全局单例 `ObjectPool`，但 `services/object_pool.gd` 未注册进 `project.godot` 的 `[autoload]`，导致 `Parse Error`（日志第 388 行起）。→ 已补注册（`ObjectPool="*res://services/object_pool.gd"`）。
- 第二层根因（注册后暴露）：`services/object_pool.gd` 原先带 `class_name ObjectPool`，与 autoload 单例名撞名 → `hides an autoload singleton` 加载失败 → 去掉 `class_name`（autoload 名已提供全局实例引用）。
- 第三层根因（仍失败）：原始 `test_object_pool.gd` 本身有误——① 用整型闭包计数 `made += 1`，而 GDScript 4.x lambda 对**值类型按值捕获**，断言读到外层恒为 0；② `test_clear_frees_all` 期望"空闲桶=10"在正确池化下本应是 1（循环内释放会复用单节点）。→ 已重写测试：改用引用类型数组计数，并改为"先建 10 个不同节点再释放"。

> ⚠️ **门禁判据盲点（重要经验）**：Parse Error 套件是**静默失败**——脚本没执行到断言，**一个 `✗` 都不会打印**，`grep -c "✗"` 返回 0 却实际已红。
> **判定 GATE2 必须同时看 `套件：通过 N · 失败 M` 的 M 值，不能只 grep `✗`。** 本次修复即靠该双判据确认回绿。

## 13. 清理时的铁律

1. **每删一批必重跑双闸门**：GATE1（`--quit` 零 SCRIPT/PARSE/COMPILE ERROR）+ GATE2（`run_all.tscn`）。
2. **GATE2 判据用两条**：`grep -c "✗"` 为 0 **且** `套件：通过 N · 失败 M` 的 M == 0。
   （本次盘点证明：Parse Error 型失败不打印 `✗`，只看 `✗` 会误判为绿。）
3. **删数据条目前先全工程 grep id**：`demo_*` / `tactical_*` 这些 id 常被 NPC、任务、对话索引、单测多处引用。
4. **删函数前先 grep 函数名**：项目已有"删函数留残留调用 → `Invalid call Nonexistent function`"的踩坑史。
5. **Godot 进程串行**：多进程抢 `.godot` 类缓存会导致假报错。
6. **不要动 `tests/unit` 的正式套件**：它们是回归防线，靠导出预设排除即可，不需删源码。
