## 4. 核心功能链路

```
【游戏侧】
启动(Bootstrap) → ConfigManager 全量加载配置 → GameManager 初始化服务
→ 主菜单 → 新游戏/读档(SaveManager) → 城镇(TownScene)
→ 对话(DialogOverlay → DialogueService) → 接任务(QuestService)
→ 战斗(BattleScene/TacticalBattleScene → CombatService/CombatCore)
→ 战斗胜利 → 任务目标推进(QuestService._advance_on_victory)
→ 任务完成 → 发奖励(InventoryService/AbilityService) → 存档(SaveManager)

【工作室侧】
studio_server 启动 → 读配置 → 剧情设计台(index.html)
→ 编辑NPC/对话/任务图 → save_json 写回 data/configs/
→ 双闸门验证(GATE1/GATE2) → commit_queue 入队 → 推送
```

**关键发现**：游戏侧链路完整闭环；工作室侧"编辑→写回→游戏读取"链路存在**两套数据源**（全局表 vs 区域表），存在"编辑器改了 A 套、游戏读 B 套"的错位风险。

## 6. 7 人评审团独立审查

### 6.1 项目经理（交付风险）

**核心判断**：项目功能面广（战斗/任务/对话/结缘/锻造/炼药/商店/门派/存档），交付节奏快，但存在**数据错位**和**任务目标类型未闭环**两个会反复产生返工的风险点。

**交付风险清单**：
- **P0**：两套 NPC 数据并存 → 后台编辑可能改错表，产生"改了不生效"的返工
- **P0**：村长等 NPC 行为入口为空 → 玩家体验断裂（NPC 不可交互）
- **P1**：任务系统只实现战斗目标 → 采集/对话类任务无法自动完成
- **P1**：save_json 非原子写入 → 异常退出可能损坏数据，需人工恢复
- **P2**：TownScene / studio_core 职责过重 → 后续加功能互相踩脚
- **P3**：index.html 巨型化 → 前端迭代速度下降

### 6.2 系统架构师（架构健康度）

**核心判断**：分层意识好（服务层不持有 Node、EventBus 解耦、ISaveable 统一存档），但存在 **God Object 型管理器** 和 **数据源不唯一** 两个架构级问题。

**关键结论**：
1. 当前架构属于"**单例组合根 + 服务门面 + 事件总线**"混合架构，方向正确
2. **GameManager 是 God Object 风险**：服务实例、流程调度、战斗入口、场景切换、加载覆盖层、婚礼/日程推进全集中在一个 autoload
3. **ConfigManager 职责过重**：路径常量、加载、缓存、容错、版本、引用校验一肩挑
4. **数据源不唯一**：全局表 + 区域表并存，靠 `_load_regions()` 合并，重复 ID 区域覆盖全局，长期是隐患
5. **UI-业务耦合**：DialogOverlay/TownScene 直接调 `quest_service.accept()`、`bond_service.set_affection()` 等业务方法
6. **"半年后还能不能继续加功能"**：能，但前提是先把数据源唯一化和 God Object 拆分做掉

### 6.3 资深程序员（代码质量）

**核心判断**：命名规范、注释质量、错误处理整体**高于平均水平**，冗余和死代码**不算严重**，但存在若干值得清理的点。

**重点发现**：
- 重复逻辑：`sort_bag`/`_organize_bag` 排序重复、`_apply_use_heal`/`_apply_use_exp` 战斗限制重复
- 死代码/疑似死代码：`MathUtil` 未被使用、`combat_service.use_item_events()` 因战斗禁用药成为空壳
- 魔法字符串：`ability_enums.gd` 的 `WeaponType.CLIFF` 语义可疑
- 命名：`save_validator` 实际会修复+发事件，名不副实；`_last_known_day` 语义过宽
- 错误处理：`SaveManager._load_json` 解析失败降级为空字典，无法区分"空存档/损坏存档"

### 6.4 前端/UI 工程师（UI 健康度）

**核心判断**：UI 层组织清晰（components/overlays/screens 分层），但存在**事件泄漏**和**Tween 生命周期**两类典型问题。

**重点发现**：
- `ui_manager._ready()` 订阅 EventBus 但无 `_exit_tree()` 断开 → 重复订阅风险
- `DialogOverlay._fade_right_bust()` 每次切换立绘 `create_tween()` 不清理 → 快速切换时旧动画堆积
- `DialogOverlay` / `TownScene` 直接操作业务服务 → UI 承担业务职责
- `BattleScene` / `TacticalBattleScene` 结果面板逻辑几乎复制 → 样板重复
- `TownScene._physics_process()` 每帧 O(n) 遍历 NPC → 数量增长后性能风险

### 6.5 运维工程师（可运行性）

**核心判断**："开发机能运行，不代表用户机器能运行"——本机绝对路径、非原子写入、并发日志是三个跨机器/跨场景风险。

**重点发现**：
- `studio_server._godot_exe()` 回退到本机绝对路径 `C:/Users/Administrator/.workbuddy/binaries/godot` → 换机失效
- `studio_core.save_json()` 备份后直接写目标文件，非原子 → 异常退出半截文件
- `studio_core.log_event()` 未用已有 `_lock` 保护 JSONL 追加 → 并发日志错乱
- `change_log.py add_row()` 无锁追加 → 多 AI 窗口并发登记竞争
- `migrate_to_lfs.py` 是高风险一次性脚本（可触发 `git lfs migrate`），应限制暴露

### 6.6 迭代规划师（优先级排序）

**核心判断**：不能按严重等级简单排序，必须先解决**数据源唯一化**这个根问题，否则其他修复都会在错误的数据上打转。

**整改依赖链**：
```
数据源唯一化(两套表合并)
  ↓
NPC 行为入口补齐（村长等）
  ↓
任务目标类型闭环（COLLECT/TALK）
  ↓
God Object 拆分（GameManager/ConfigManager）
  ↓
原子写入 + 并发保护（save_json/change_log/log_event）
  ↓
UI-业务解耦 → 样板去重 → 死代码清理
```

### 6.7 测试工程师（测试覆盖）

**核心判断**：测试体系**相当优秀**（59 个单元测试 + 冒烟 + 双闸门 + pre-commit 契约审计），但存在**业务覆盖盲区**和**测试有效性待验证**。

**重点发现**：
- 强项：`run_all.gd` 自动发现、`_test_base.gd` 反射运行、`test_eventbus.gd` 契约校验、`test_inventory_service.gd` 覆盖满溢出生产者驱动
- 盲区：任务目标类型（COLLECT/TALK）无测试（因为没实现）、区域表数据一致性无测试、UI 层事件泄漏无测试
- 待验证：GATE1/GATE2 机制完整但需实际跑一次确认全绿；`_test_base.gd` 失败时未打印方法名，定位慢

#### [🔴] 问题 1：两套数据体系并存，区域表覆盖全局表

**问题位置**：`autoload/ConfigManager.gd` 第 620-642 行，`_load_regions()` / `_merge_region_kind()`

**问题描述**：`_load_npcs()` 先加载全局 `town_npcs.json`，`_load_regions()` 再把 `regions/*/npcs.json`、`quests.json`、`items.json`、`battles.json`、`enemies.json` 合并进同一张全局表，重复 ID 由区域版本覆盖。全局表与区域表两套数据源长期并存。

**大白话**：就像"全镇花名册"和"各村花名册"同时存在，最后以各村为准，但两份都留着，谁改哪份很容易搞混——后台编辑器改的是 A 份，游戏读的可能是 B 份。

**影响范围**：NPC/任务/物品/战斗/对话全链路；桌面工作室编辑与游戏读取的一致性；后续扩展（新增区域）会持续放大问题。

**证据**：`ConfigManager.gd:637-642` 五处 `_merge_region_kind` + `_register_region_dialogs`。

**整改方案**：
1. 明确"区域表接管"策略：游戏运行时**只读区域表**，全局表降级为"通用 NPC/兜底表"或直接废弃
2. 禁止同一 ID 同时存在于两个数据源（加启动校验）
3. 桌面工作室编辑入口统一指向区域表
4. 同步修改 `_validate_references()` 校验区域交叉引用

**预计工作量**：M（3-7 人日，涉及数据迁移与校验）

## 24. 最终结论（回答 10 个问题）

1. **现在这个项目最大的风险是什么？** 两套数据体系并存，后台编辑与游戏读取可能错位，且会持续放大。
2. **有没有会导致游戏运行失败的问题？** 未发现明确的启动崩溃问题；但数据错位可能导致功能静默失效。
3. **有没有可能导致数据丢失或损坏的问题？** 有：save_json 非原子写入（工作室侧）；游戏侧有备份机制，风险较低。
4. **有没有明显的架构瓶颈？** 有：GameManager/ConfigManager God Object、UI-业务耦合、数据源不唯一。
5. **有没有大量重复代码？** 没有大量重复；有 4 处明确重复（排序、战斗限制、战斗结果面板、武器枚举）。

7. **哪个模块最需要重构？** 数据配置层（两套表合并）优先级最高；其次是 GameManager/ConfigManager。
8. **哪个问题最值得现在马上修？** 两套数据源唯一化——它是其他修复的前提。
9. **如果继续开发大量功能，最可能在哪里崩盘？** 数据一致性（两套表越扩越乱）→ 其次是 GameManager 膨胀导致迭代互相踩脚。

    8. UI 层与业务层解耦

    10. 清理死代码与冗余（MathUtil、_gen 脚本、战斗结果面板）
