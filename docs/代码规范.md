# 代码规范（工程纪律）

> 编码层速查标准。完整企业级工程全标准见 `docs/开发规范.md`（架构 / 目录 / EventBus / 存档 / 模块 / UI / 性能 / CI）。二者冲突以 `开发规范.md` 的四底线为准。

版本 v0.2 · 2026-08-27
适用范围：武侠江湖 Godot 工程全部 GDScript / 配置 / 数据
强制级别：所有提交必须满足，PM/架构师在 Code Review 中拦截违规
规范来源：本项目铁律（精简/可拓展/可维护/易读）＋ **腾讯编码规范** ＋ **腾讯代码安全指南（secguide）**

---

## 0. 总纲
代码是写给人看的，机器只是顺便执行。三条铁律不可破：
1. 精简干练，零废物代码
2. 可拓展、可维护
3. 易读、易接手（方便其他人后续读取修改）

> 命名风格以 **GDScript 官方约定为准**（函数/变量 snake_case、类/资源 PascalCase、常量 ALL_CAPS），腾讯规范的「精神」全部吸收，仅在冲突处让位于 GDScript 官方风格。

---

## 1. 精简（Anti-废物代码）
- 不写永不被调用的函数 / 变量 / 脚本
- 不写复述代码行为的注释（如 `# 把 hp 设为 0`）；注释只写「为什么」
- 不引入当下用不上的「未来可能」抽象（YAGNI）
- 不复制粘贴；复用抽成函数 / 组件

## 2. 可拓展（数据驱动 + 模块化）
- 数值 / 配置写 `data/*.json` 或 `*.tres`，由 `ConfigManager` 加载，逻辑不硬编码
- 新实体（技能 / 物品 / 敌人 / 门派）只加数据 + 一套统一接口，不改战斗 / 养成核心
- 系统间用信号（signal）或单例解耦，不直接互相 hold 引用
- 扩展点用基类 / 资源继承（如 `Skill` 基类派生具体招式）

## 3. 可维护
- 单一职责：一个脚本只管一类事
- 全局状态走 `GameManager` / `ConfigManager` 等 autoload 单例，不塞进具体场景
- 目录严格分层：`autoload` / `core` / `data` / `battle` / `world` / `ui`
- 魔法数字（腾讯【必须】）集中为 `const` 或写进数据文件，禁止散落字面量

---

## 4. 命名（吸收腾讯编码规范）
- **见名知意**：禁止无意义缩写（反例 `condi`）、禁止拼音与英文混用（反例 `getPingfenByName` / `int 数量`）
- **常量**：全大写 + 下划线，语义完整（正例 `MAX_STOCK_COUNT`，反例 `MAX_COUNT`）
- **禁止单字符变量**：`i` / `j` / `k` 仅允许作局部循环变量，其余变量必须有含义
- **风格统一**：同一项目内命名风格自始至终一致，不可来回变化
- **基类前缀**：抽象基类用 `Base` / `Abstract` 前缀（如 `BaseCharacter`、`AbstractBuff`）
- 对外可调状态用 `@export` 暴露；信号用 `_changed` / `_pressed` 等惯用后缀

## 5. 注释（吸收腾讯编码规范）
- 每个脚本 / 类 / 重要方法写注释，说明**职责与意图**（why），不只复述行为
- **必须注释**：分支语句、循环、重要变量（尤其全局 / 跨场景共享状态）
- **注释量适中**（腾讯建议有效注释 20%~30%）：提示而非文档，不喧宾夺主
- 注释用中文；不以拼音 / 中文直接命名标识符
- 每个脚本顶部一行说明职责，并标注所属 Phase / TODO

## 6. 安全（吸收腾讯代码安全指南 secguide，适配单机游戏）
- **【必须】禁硬编码敏感配置**：源码不写密钥 / 账号密码 / 内部地址；配置走 `data/` 或外部配置（即便单机也保持习惯，防日后联机泄露）
- **【必须】输入校验**：所有外部输入（存档读取、配置文件、后期联机数据）先校验格式 / 范围再使用，防损坏数据崩溃
- **文件操作**：存档读写前做存在性 / JSON 格式校验；解析失败走兜底而非 panic
- **日志**：不记录敏感信息；重要行为用 `print` / `push_warning` 记日志，便于排查
- **第三方资源 / 组件**：引入外部素材、插件、SDK 前确认授权范围（呼应资产版权），禁用来源不明组件
- **口令 / 隐私**（联机时适用）：任何用户凭证不可逆加密 + 随机 salt 存储，禁止明文 / 弱算法

## 7. 测试与审查（吸收腾讯 standards-go）
- **格式化统一**：编辑器默认格式化，提交前无残留格式差异
- **函数长度 / 嵌套**（腾讯【必须】）：单函数建议 ≤ 40 行，嵌套层级 ≤ 3；超了拆
- **错误处理**：不吞异常；资源加载失败有兜底与明确告警
- **单元测试**（腾讯【必须】）：核心系统（战斗结算 / 数据加载 / 数值公式）写最小断言验证，可在编辑器一键跑
- **工具落地**：用静态检查（gdlint / 编辑器警告）做基础拦截，CI 前先本地过
- **Code Review**：提交前过 §9 自检清单；他人接手可读、可改、可扩展是验收标准

---

## 8. 类与脚本约定
- 基类 / 资源用 `class_name`；场景脚本放对应分层目录
- 每个脚本顶部一行说明职责，并标注所属 Phase / TODO

## 9. 提交前自检清单
- [ ] 有没有死代码 / 未使用变量？删
- [ ] 新功能是否只靠加数据 / 模块实现，没动核心逻辑？
- [ ] 命名是否见名知意、有无拼音英文混用 / 单字符变量（循环除外）？
- [ ] 注释是否解释「为什么」、疏密是否适中？
- [ ] 是否引入不该耦合的互相引用？改信号 / 单例
- [ ] 单函数是否过长（>40 行）/ 嵌套过深（>3 层）？拆
- [ ] 魔法数字是否还在代码里？提到 const / 数据文件
- [ ] 外部输入（存档 / 配置）是否先校验再使用？
- [ ] 有无硬编码密钥 / 敏感配置 / 来源不明第三方组件？
- [ ] 核心系统是否有最小验证（断言 / 一键测试）？
