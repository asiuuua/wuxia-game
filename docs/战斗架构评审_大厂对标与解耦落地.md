> 视角：一线大厂 PM + 架构师 + 主程
> 目标：把你给的「大厂资源/实例化架构方案」与现有代码互相举证，对标梦幻西游 / 逸剑风云录，给出优缺与可落地的扩展路线，并逐条映射你的真实需求（完全解耦、任意底图复用、多 NPC、数百特效极致帧率、平滑加载卸载、20 小怪 + 5 友方飘字不丢失）。

## 0. 一句话结论

现有战斗逻辑的**骨架方向是对的**：逻辑层（RefCounted，零 Node 引用）与视图层（Node2D/Control）严格分离，事件总线驱动渲染，数据全在 JSON。对照你给的大厂方案，已经做对的是「解耦 + 事件驱动渲染 + 数据驱动」三件最难的；**缺口是三块工程化基础设施**：① 资源生命周期管理（引用计数的 AssetManager）、② 全局对象池（不止飘字，覆盖单位/粒子）、③ 场景隔离容器与加载/卸载策略。补齐这三块，你的全部真实需求都能落地，且仍可被现有双闸门验证。

## 2. 对照你的大厂方案逐条举证

你给的方案要点：① AssetManager（缓存 + 引用计数）② ObjectPool（按 Prefab keyed）③ BattleView / CombatEventRenderer（事件驱动、不加载）④ 场景隔离 ⑤ 资源路径配置驱动。

| 大厂要点 | 现状核对 | 举证结论 |
|----------|----------|----------|
| **③ 事件驱动渲染（BattleView/CombatEventRenderer）** | ✅ **已正确实现** | `CombatEventRenderer` 正是「技能 effect → HP/MP 更新 + pop_text + 复活闪光」的事件映射器；技能逻辑从不 `new` 粒子/视图节点。这正好印证大厂「渲染与逻辑解耦、事件驱动、运行时零 load」的核心思想。**这部分你做对了，无需改。** |
| **② 对象池 ObjectPool** | 🟡 **部分正确** | 飘字有 `_pop_pool`（BattleEntity 每单位一个，上限 48），单位有 `CombatEntityPool`，这已符合「复用而非反复 new/free」的思路。但**池是分散的、未全局化**，且**完全没覆盖粒子特效**——而你未来要「数十至数百特效」，这里是大缺口。 |
| **④ 场景隔离** | 🟡 **部分正确** | 战术战斗是独立 `TacticalBattleScene`，通过 `GameManager.start_battle` 按 `tactical` 路由，确实「换底图只加载该地图的战棋布局」。但**缺少场景容器/加载策略**（预加载、异步、卸载回收），「进入卸载场景不卡顿」尚未工程化。 |
| **① AssetManager（引用计数 + 缓存）** | ❌ **缺口** | 当前资源（贴图/字体/场景）随场景加载，无统一引用计数与卸载。多场景切换 + 大量特效时，内存与 GC 是把柄。 |
| **⑤ 资源路径配置驱动** | ✅ **已正确实现** | 战场布局、敌人、友方全在 `battles.json`；`get_icon/has_icon` 走 id 派生。符合「数据驱动、不写死路径」。 |

**互相举证的硬结论**：大厂方案里最贵的两块（事件驱动渲染、数据驱动）你已经有了；你缺的是「资源生命周期」与「池的全局化/粒子化」——这恰好对应你「数百特效 + 平滑加载卸载」的需求，而不是「重写战斗逻辑」。

## 3. 对标梦幻西游 / 逸剑风云录

### 梦幻西游（PC ≥20 同屏飘字 / 移动 32；时间切片 + 同目标合并 + 优先级，永不丢弃）
- **对标点 A：飘字不丢弃**。梦幻的飘字在大量同屏跳字时**排队/切片**而非丢弃——你之前发现的「满了就丢」是玩家可见 BUG，已按此思路把 `BattleEntity.pop_text` 改成**队列溢出、槽位释放再播**（MAX_POPS=48，MAX_QUEUE=32）。20 小怪 + 5 友方同屏跳字不再丢失。✅
- **对标点 B：同目标合并 / 优先级**。梦幻对同单位密集伤害会合并或按优先级显示。我们当前是每跳字独立播放——**可后续优化**（同单位 0.2s 内多次伤害合并为「X+Y」或累加），但非阻塞项。
- **差距**：梦幻有成熟的资源预加载与内存分级，我们缺 AssetManager。

### 逸剑风云录（类天地劫战棋：网格移动 + 单机技能 + 回合制）
- **对标点 A：战棋网格**。逸剑/天地劫是六边形/方格战棋，单位在网格上移动施法。我们的 `BattleGrid`（BFS/A*/范围）已具备同等能力，且纯数据层、可任意底图复用。✅
- **对标点 B：演出与逻辑分离**。逸剑的技能演出（特效）与结算逻辑分离。我们的 `CombatEventRenderer` 正是这个角色。✅
- **差距**：逸剑的特效是**确定性、预算内**的（粒子有上限、按场景分级）。我们的粒子预算尚未建立——这是「数百特效极致帧率」需求的直接缺口。

**对标小结**：在「解耦 + 战棋网格 + 事件驱动演出」三件最难的事上，我们已对齐甚至优于独立游戏惯例；在「资源生命周期 + 特效预算」上，我们与两者都有同样量级的可优化空间。

## 4. 现有优缺分析

### 优点（保住，别动）
1. **逻辑/视图零耦合**：6 个逻辑模块全 `RefCounted`，换底图、换渲染器都不碰战斗规则。
2. **事件总线驱动**：跨模块只走 `EventBus`，符合项目铁律，也契合大厂「渲染不反向依赖逻辑」。
3. **数据驱动**：战场/敌人/友方全 JSON，`tactical` 路由让任意底图复用同一套战斗。
4. **双闸门可验证**：`--quit` 零硬错 + `run_all` 零 `✗`，每次改动可快速回归。
5. **飘字已排队不丢**：直接满足 20+5 飘字可见需求。

### 缺点（要补）
1. **无 AssetManager**：资源随场景加载/卸载，无引用计数，多场景 + 大特效易内存抖动。
2. **对象池未全局化、未覆盖粒子**：飘字池分散在各 View，粒子特效目前是「临时 new」思路（装饰层竹子/房屋/雾都是运行时 new），规模上来会 GC 尖刺。
3. **场景隔离无加载策略**：有独立场景，但无预加载/异步/卸载回收容器，「不卡顿」靠运气。
4. **无特效预算**：用户要「数十至数百特效」，当前没有全局并发上限与分级（近景满特效、远景降级）。
5. **飘字池非全局**：每单位独立池，虽不会争用，但无法从全局视角做「同屏总跳字预算」。

## 5. 扩展落地路线（分阶段，每阶段双闸门可验证）

### 阶段 A：全局对象池（解决「数百特效 + GC 尖刺」）
- 新增 `services/object_pool.gd`（RefCounted）：按 key（"float_text" / "hit_spark" / "slash"）管理池，提供 `acquire(key, factory)` / `release(key, node)`。
- `BattleEntity` 飘字池、`CombatEntityPool` 改为向全局池借还；**粒子特效**新增即走池。
- 验证：`test_effect_budget.gd` 扩写「全局池上限 + 借还复用」断言；GATE2 零 `✗`。

### 阶段 B：AssetManager（引用计数 + 预加载 + 卸载）
- 新增 `services/asset_manager.gd`（Autoload 或 GameManager 装配）：`load_ref(path)` / `release_ref(path)`，引用计数归零才 `ResourceLoader` 卸载。
- 战斗入场时按 `battles.json` 预加载该战场所需纹理/场景；出场 `release_ref` 全部。
- 验证：加 `test_asset_manager.gd`（引用计数 +1/+1/-1 不卸载、-2 卸载）；GATE2 零 `✗`。

### 阶段 C：场景隔离容器 + 加载/卸载无卡顿
- 复用现有 `TacticalBattleScene` 作为「子实例」，外包一层 `BattleStageContainer`（Node2D）：负责异步 `preload` 战场装饰、`call_deferred` 挂载、`queue_free` 整树卸载并归还对象池/资源引用。
- 本次的 `tactical_test_riverside`（装饰层 + 复用战斗逻辑）正是这个容器的雏形，可演进为正式容器。
- 验证：GATE1 零硬错；加 `test_stage_lifecycle.gd`（挂载→战斗→卸载→资源归零断言）。

### 阶段 D：飘字全局预算 + 同屏合并（对标梦幻）
- 在全局池之上加「同屏飘字总预算」（如 120）与「同单位 0.2s 合并」策略，超过预算时按优先级丢弃最低优先（而非随机丢）。
- 验证：`test_float_budget.gd` 断言总预算不超、合并生效、20+5 场景关键跳字全可见。

> 落地顺序建议：A → C → B → D。A/C 直接消除「卡顿/GC」风险且改动局部；B 是内存地基；D 是体验打磨。
