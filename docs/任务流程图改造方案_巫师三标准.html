任务流程图改造方案 · 对齐巫师三 QuestGraph 标准

把工作室现有「剧情对话(线性台词表)」升级为「可视化任务流程图(节点图)」 · 高标准、可落地、向后兼容  ·  2026-09-03
给外行的一句话版：现在剧情是"一条项链，一颗珠子连一颗，走到底"。改造后是"一张地图，起点在地图左上角，终点有好几个，路线上的岔路口会弹选项，走哪条由你之前攒下的好感/选择决定"。巫师3每个任务就是这么画的图，我们照着画。

0. 先锚定目标：巫师3 QuestGraph 到底是什么

  • 任务 = 一张节点图（Graph）：无数个小方块(节点)用箭头(连线)连起来，像地铁线路图。
  • 节点类型可怕地丰富：开场、对话、选项、打架、给道具、时间等待、剧情演出、结局……每个节点干一件确定的事。
  • 带类型的连线：一条箭头不是随便连，它带"类型"(正常走/赢了才走/失败才走)，还有条件——只有满足条件这条箭头才通车。
  • 全局状态(Facts/Flag)：游戏背后一本"大笔记"，记你好感多少、哪个选择做了、进度到哪。节点读笔记决定通车，写笔记改变后续。
  • 目标(Goals)与阶段(Phase)：任务分成几段，每段在屏幕右侧显示"当前目标"，玩家知道下一步要干嘛。结局(Ending)是图的多个终点，凑齐条件进哪个终点。

我们在架构上完全照这个模型来，但落地为更贴合 Godot + JSON + 现有工作室的实现。

1. 改造核心：数据模型从"一条线" → "一张图"

改造前 · 现在的线性台词表

dg_1 ──next──▶ dg_2 ──next──▶ dg_3 ──next──▶ (空=结束) (只能一条路走到底，没有岔口不读条件)

改造后 · 巫师三标准节点图

┌─（条件: 帮过乞丐 = 真）─▶ 打山贼→给玉佩→【好结局】 【开场】──▶【对话】─┐ │ └─（条件: 没帮过 = 真）─▶ 【路边折返】→【婉拒结局】 │ └──(顺便记录: 已完成开场)──▶【选项节点】──────▶ ……
  • 一个任务 = 一个 quest_graph，里面有一堆 nodes。
  • 每个节点是一块"积木"，箭头指向下一块。
  • 一个节点能
      出来多条箭头
    = 选项/分支；每条箭头能带条件门。
  • 节点能写状态(记好感/记选择) = 改变后面走哪条。

2. 新数据模型（Schema）

2.1 节点类型总表

节点类型 type干什么关键字段
start任务入口next
dialog弹一段对话（引用现有对话表区间）dialog_ref, lines_from, on_enter, next
choice弹多个玩家选项options[]（每个含 text_key/show/then/next）
battle触发一场战斗battle_ref, on_win[], on_lose[], on_escape[]
flag_set写一段状态（记好感/记进度/记选择）key, value
flag_check读状态做纯判断分流require[]{...}, then/then_else
give_item发放/扣除道具item, qty
advance_time推进时间/天数（服药、休息类联动）days, hour
goal更新右侧"当前目标"文案text_key
end任务/支线终结ending（good/bad/neutral）

2.2 一张完整图长什么样（目标 JSON 样例）

// quests.json 里某任务的"图上身版"（向后兼容，见 §4） { "id": "nv_quest_guard_001", "title_key": "q_guard_title", // 文本与逻辑分离，见 §6 "type": "quest_graph", "version": 2, "start_node": "q_start", "nodes": { "q_start": { "type":"start", "next":"q_goal1" }, "q_goal1": { "type":"goal", "text_key":"q_guard_goal1", "next":"q_dlg" }, "q_dlg": { "type": "dialog", "dialog_ref": "npc_village_chief", // 复用现有对话分片 "on_enter": [{"op":"flag_set", "key":"nv_started_guard", "value":true}], "next": "q_choice" }, "q_choice": { "type": "choice", "options": [ { "text_key": "opt_help", "show": { "all": [{"flag":"nv_maiden_helped", "eq":true}] }, // 条件门 "then": [{"op":"flag_set", "key":"nv_q_accepted", "value":true}], "next": "q_battle" }, { "text_key": "opt_refuse", "show": { "all": [{"flag":"nv_q_accepted", "eq":false}] }, "then": [], "next": "q_end_refuse" } ] }, "q_battle": { "type": "battle", "battle_ref": "nv_battle_bandit", "on_win": [{"op":"flag_set", "key":"nv_bandit_cleared", "value":true}], "on_win_next": "q_reward", "on_lose_next": null // null = 可重试或剧情败走 }, "q_reward": { "type": "give_item", "item":"nv_item_pendant", "qty":1, "then": [{"op":"favor_add", "target":"npc_village_chief", "value":15}], "next": "q_end_good" }, "q_end_refuse": { "type":"end", "ending":"neutral" }, "q_end_good": { "type":"end", "ending":"good" } }, "endings": [ {"id":"good", "require":{"all":[{"flag":"nv_q_accepted","eq":true}]}}, {"id":"neutral", "require":{"all":[{"flag":"nv_q_accepted","eq":false}]}} ] }

3. 状态系统：全局"旅行笔记" FlagStore

  • 新增 FlagStore（落 PlayerState 或独立 autoload）：一个 key → value 的持久化字典。
  • 存四种值：布尔(做过没做过)、整数/计数(进度、次数)、好感/数值(对某 NPC 的好感分)、字符串(当前选项记录)。
  • 条件 DSL 支持：flag(读布尔) / favor(读好感) / quest_progress / 以及 all、any、not 组合。
  • 写状态用副作用数组 then / on_enter / on_win，统一走同一套 op：flag_set / favor_add / remove_item / emit_event。
💡 这等价于巫师3的 Facts(监督者之眼) 和贝塞斯达的 Globals——不同游戏叫法不同，模型同一个。

4. 向后兼容 & 迁移：旧台词表零破坏升级

  • 旧数据一条不删。现有 dialog_id → shards/next_id 台词表 原样保留。
  • 新增的 quest_graph 是另一层新结构。凡是没有 graph 的任务，沿用老逻辑不变；有 graph 的走新引擎。两个并存、互不干扰。
  • 可选自动迁移：写一个迁移工具，把旧台词表自动转成"单一路径的 dialog 节点图"，转出来和分析有者语义一致（就是一条直线）。这样老内容也在编辑器里可见、可继续改造加分支。

5. 工作室编辑器 UI 改造（对齐大厂，但分三步走，性价比最高）

Phase A · 蓝图先行 T1 · 最快见效

  • 后端 studio_core.py 新增任务图读写 API：/api/quest_graph（列/查/存节点/存连线）+ 新增对 choice/require/then 的 schema 校验。
  • 前端「剧情对话」页签里，给台词行加一个「选项」编辑区：每个选项填 文本 + 跳转台词 + 可选条件。
  • 跑 check_crossref 校验图内引用（连到不存在的节点/战斗/物品立刻报红）。
  • 效果：不用画图就能先"填出多分支"，先把分支+条件跑通。

Phase B · 可视化节点图画布 T2

  • 新增「任务流程图」页签：一个轻量画布（自研 SVG/Canvas），节点拖拽摆放、连箭头、点节点在右侧面板改字段。
  • 节点上显示小标：类型徽章、条件小锁、目标文案。
  • 可选导出 PNG/复制 JSON，方便策划评审、写文档。
  • 实现建议：先用 cytoscape.js / jointJS(开源图库) 而非从零写图形算法，成本低、接近大厂手感。

Phase C · 对标大厂完整项 T3 · 可选

  • 调试上帝视角：游戏内热键打开「任务图面板」，看当前走到哪个节点、好感多少、哪个 flag 没开。
  • i18n 文本分离：所有 text_key 统一走文案表，中文先占用，将来多语言零迁移。
  • 编辑器即报错：接线的接口"对不上类型当场红"。

6. 文本与逻辑分离（要高标，这一步顺手做对）

  • 所有面向玩家的话 不写死在 JSON 字段里，改用 xxx_key，指向一张 loc/zh_CN.json 文案表。
  • 好处一条就值回票价：将来繁中/英文/日文，只加一张文案表，不动任何逻辑与图。
  • 格式："q_guard_title": "新手村·守村之任"，key 全局唯一。

8. 分期落地路线 + 验收

阶段交付验收标准（沿用双闸门）
T1数据模型 + FlagStore + graph 解释器 + 编辑器表单级选项/条件GATE1 零错误；GATE2 零失败；check_crossref 全绿；一条示例任务可真实跑出"两个选项、两个结局"
T2可视化节点图画布（开源图库）能拖拽连线、存储回图、重开看得见；旧台词自动迁移进画布
T3调试上帝视角 + i18n + 编辑器即错游戏内可开任务图面板；多语言只加文案表

9. 风险与注意

  • 绝不一次性推倒重写：老台词表与 graph 并存、互不干扰，T1 先跑通再铺开。
  • 共享地基改动需登记：ConfigManager/PlayerState 属共享地基，改动须按项目流程 change_log + 双闸门 + commit_queue 入队。
  • 编辑器 T2 用开源图库，避免从零写图形算法陷入泥潭。
  • 条件 DSL 保持最小：只做 all/any/not + flag/favor/quest_progress，够用不追繁。
最终一句话：这套方案把工作室从「编辑一行行台词」升级为「绘制一张张任务地图」，并在数据模型、条件引擎、状态系统、文本分离、可视化、调试六个维度对齐大厂标准；分 T1(先跑通分支) → T2(上可视化) → T3(补齐 i18n/调试) 三步落地，每一步都能单独验收、不破坏现有内容。
