# 战斗模块：《逸剑风云决》战棋战斗 UI & 逻辑审查与实现方案

> 审查日期：2026-08-29  
> 审查人：AI 程序员 / PM / 架构 / 美工 / 前端 / 后端 联合视角  
> 目标：基于当前 Godot 4.7.2 纯 GDScript 架构，评估实现《逸剑风云决》式方格战棋战斗的可行性、优缺点与最小改动路径。

## 一、当前架构基线（我们已有什么）

### 1.1 分层现状

| 层级 | 当前实现 | 关键文件 |
|---|---|---|
| **数据层** | `CombatState` 单场状态 + `CombatCharacter` 单位快照 | `data/runtime/combat_state.gd`、`combat_character.gd` |
| **业务层** | `CombatService` 门面 + `CombatCore` 逻辑内核 | `services/combat/combat_service.gd`、`combat_core.gd` |
| **演出层** | `CombatDirector` 编排 + `BattleView` 视图 | `scenes/gameplay/battle/battle_director.gd`、`battle_view.gd` |
| **场景层** | `BattleScene` 纯 Control，代码动态建 UI | `scenes/gameplay/battle/BattleScene.gd` |
| **HUD 单元** | `UnitHud`：名字 + 头像 + 气血/真气/护盾条 + 状态行 + 飘字 | `scenes/gameplay/battle/unit_hud.gd` |
| **事件总线** | `EventBus` 全局信号，跨模块唯一通道 | `autoload/EventBus.gd` |
| **武学系统** | `AbilityService` 6 槽快捷栏 + 冷却读秒桥接 | `services/ability/ability_service.gd` |

### 1.2 当前战斗规则

- **回合模式**：`SEQUENTIAL`（玩家先，再敌人）或 `ATB`（按 `effective_charge_rate()` 降序插队）。
- **玩家输入**：按钮选技能/普攻/物品/调息/逃跑，无空间位置概念。
- **伤害结算**：统一走 `CombatCore._resolve_hit`，含闪避、防御减伤、暴击、护盾、反弹、复活。
- **状态引擎**：层数 + 持续回合 + DoT/HoT + 属性修正。
- **事件流**：`Array[CombatEvent]` 驱动演出，视图只播动画不判逻辑。
- **确定性**：`SeededRNG` 注入 seed，可复现/测试/回放。

### 1.3 已可直接复用的资产

1. `UnitHud` 完全可复用为左下/右下状态卡（头像、名字、血条、真气条、状态图标、飘字）。
2. 底部技能栏的 6 槽位 + 冷却逻辑与 `ability_service.equipped_combat` 已对齐。
3. `CombatCore` 的 `_cast_skill`、`_resolve_hit`、`_apply_status`、护盾/反弹/复活机制可直接复用。
4. `CombatDirector` + `BattleView` 的事件流演出机制可直接复用。
5. `EventBus` 的战斗生命周期信号已完整。

## 二、逸剑风云决截图解析

### 2.1 界面元素清单

| 屏幕区域 | 截图元素 | 交互/显示内容 |
|---|---|---|
| 左上 | 战场信息面板 | 胜利条件、失败条件、战场规则 |
| 右上 | 手动/自动切换 | 模式切换按钮 |
| 左下 | 我方角色状态卡 | 头像、名字、气血/真气条、属性、buff 图标 |
| 右下 | 目标/敌方状态卡 | 选中敌人信息 |
| 底部 | 武学技能栏 | 普攻、二式、三式、绝式、轻功、心法；快捷键 1-6 |
| 底部右侧 | 功能按钮 | 调息(Z)、认输(C)、逃跑(X) |
| 世界层 | 斜45°等轴测网格 | 蓝色=我方可移动范围，绿色=敌方范围 |
| 世界层 | 角色/怪物模型 | 绑定网格坐标 `grid_pos` |

### 2.2 截图暴露的核心规则

1. **移动与攻击分离**：先移动（蓝色高亮），再释放武学；轻功也是技能的一种。
2. **真气管理**：招式耗真气，调息回真气并占用整回合。
3. **绝式冷却**：图标右上角数字代表剩余冷却回合。
4. **网格判定优先**：所有移动、范围、目标选择以网格坐标为准，模型只是表现。
5. **自动战斗只控制我方**：怪物永远 AI，开关只切换玩家是否由 AI 托管。

## 三、六重视角联合审查

### 3.1 程序员视角：实现复杂度与改动面

#### 当前架构距离战棋还差什么？

| 功能 | 当前状态 | 战棋需要 | 工作量 |
|---|---|---|---|
| 网格坐标系统 | ❌ 无 | 每个单位 `grid_pos: Vector2i` | 中 |
| 移动范围计算 | ❌ 无 | A* / BFS 可达格子 | 中 |
| 技能范围形状 | ❌ 无 | 配置 `range_shape` + 方向/距离 | 中 |
| 网格点击输入 | ❌ 无 | 射线/点击映射到 grid_pos | 中 |
| 等轴测渲染 | ❌ 当前纯 2D Control | TileMap 或自定义等轴测绘制 | 高 |
| 单位在世界层移动 | ❌ 无 | 模型插值移动到目标格子 | 中 |
| 敌方威胁范围 | ❌ 无 | 每个敌人按移动力预计算 | 中 |
| 多友方单位 | ❌ 当前只有玩家 | `allies` 数组需真正启用 | 中 |
| AI 寻路+选目标 | ❌ 当前只选技能 | A* 到最近目标/最优位置 | 高 |
| 手动/自动切换 | ✅ 已有按钮 | 接入 AI 托管玩家 | 低 |
| 调息/逃跑 | ✅ 已实现 | 逻辑基本可用 | 低 |
| 技能冷却 | ✅ 已实现 | 截图数字显示需 UI 补齐 | 低 |

#### 结论

- **中低风险**：网格逻辑、范围计算、输入处理、状态卡复用。
- **高风险**：等轴测美术资源与渲染、AI 在网格上的移动决策、摄像机 WASD/缩放。
- **最大收益点**：复用 `CombatCore` 的结算链，只把「目标选择」从一维目标 ID 改为二维网格坐标集合。

### 3.2 项目经理视角：风险、排期与里程碑

#### 工作量评估（按最小可玩 demo 计）

| 阶段 | 内容 | 预估人天 | 风险 |
|---|---|---|---|
| P1：网格基础设施 | `BattleGrid` 数据 + `BattleGridNode` 视图 + 坐标转换 | 3-4 | 等轴测坐标转换易踩坑 |
| P2：单位与移动 | 单位绑定 grid_pos、移动动画、移动范围高亮 | 2-3 | 多单位重叠/遮挡排序 |
| P3：技能范围 | 技能 JSON 扩展 range_shape、范围高亮、目标解析 | 2-3 | 与现有目标系统兼容 |
| P4：AI 网格化 | 敌人 AI 移动+选技能+选目标 | 3-5 | 需与玩家共用同一套接口 |
| P5：摄像机 | WASD 移动、滚轮缩放、边界限制 | 1-2 | Godot Camera2D 即可 |
| P6：UI 适配 | 状态卡、技能栏、战场信息、手动/自动 | 2-3 | 低，复用现有 UnitHud |
| P7：集成测试 | 网格战斗端到端 + 确定性回归 | 2-3 | AI 非确定性需固定 seed |
| **合计** | | **15-23 人天** | |

#### 关键风险

1. **美术资源缺口**：等轴测角色/怪物/地形/格子高亮图若从零做，周期可能超过程序。
2. **AI 移动决策**：敌人 AI 需要「走到能打到人的最近格子」+「走回去保持距离」，调试量大。
3. **当前 2D 与目标 2.5D 的技术路线未锁定**：项目记忆里等轴测是目标态，但技术路线待拍板。
4. **性能**：网格大小若超过 20×20，A* 每回合算 N 个敌人可能帧率下降，需缓存或增量更新。

#### 建议里程碑

- **M1（2 周）**：正交俯视方格战棋 demo，暂不做等轴测，先验证网格逻辑。
- **M2（1 周）**：技能范围、AI 移动、手动/自动切换。
- **M3（1-2 周）**：等轴测资源接入、摄像机、视觉打磨。

| 变更 | 影响窗口 | 建议 |
|---|---|---|
| `CombatCharacter` 增加 `grid_pos` | 战斗窗口 + 数据窗口 | 纯追加，低风险 |
| `CombatState` 增加 `allies` 生效化 | 战斗窗口 + 数据窗口 | 当前 `allies` 数组为空，需配置支持 |

- 跨模块只走 `EventBus`。
- 所有高频战斗有序流走返回值 `Array[CombatEvent]`，不走总线。

### 3.4 美工视角：资源需求与视觉风格

#### 等轴测资源清单

| 资源 | 用途 | 规格建议 |
|---|---|---|
| 地形瓦片 | 草地/石板/泥土/水域 | 64×32 或 128×64 等轴测菱形 |
| 角色 sprite | 玩家 + 盟友 + 敌人 4/8 方向 | 等轴测 8 帧行走图 |
| 怪物 sprite | 狼、山贼等 | 与角色同规格 |
| 格子高亮 | 蓝色移动、绿色威胁、红色技能范围 | 半透明菱形/方形 |
| 选中光环 | 当前行动单位脚下光圈 | 金色/白色光环 |
| 头像 | 状态卡使用 | 128×128 方形，与现有 `npc/player` 兼容 |
| 技能图标 | 底部技能栏 | 64×64，与现有 `UIManager.get_icon` 兼容 |
| buff/debuff 图标 | 状态卡小图标 | 32×32 |

#### 技术美术注意

1. **y-sort 必须开启**：等轴测单位在 TileMap 上按 y 坐标排序，避免遮挡错误。
2. **网格与像素对齐**：等轴测瓦片原点建议设为中心点底部，方便 `grid_to_world` 转换。
3. **高亮不要全屏闪烁**：移动范围和技能范围用半透明叠加，避免视觉污染。
4. **角色移动动画**：步行动画 + 插值移动需同步，否则会出现「滑冰」现象。

#### 低成本替代方案（个人开发）

- 先做 **正交俯视 2D 方格**（俯视图角色 + 方形格子），程序逻辑 100% 可用，等美术到位后再换等轴测瓦片。
- 用 **色块 + 简单几何图形** 代替高亮贴图。
- 复用现有 `UnitHud` 和 `UIManager.get_icon` 接口，不重新做 HUD 美术。

### 3.5 前端视角：CanvasLayer 分层与 HUD 布局

#### 推荐 HUD 分层

沿用项目已有的 6 层 `CanvasLayer` 架构（`Layer.HUD=5`，真实 layer 50）：

| Layer | 用途 | 元素 |
|---|---|---|
| 0（世界层） | 网格、单位、摄像机 | `BattleGridNode`、`BattleEntity`、Camera2D |
| 10 | 战斗常驻 HUD | 战场信息、状态卡、技能栏、手动/自动按钮 |
| 20 | 弹窗层 | 物品面板、战斗日志、胜利/失败面板 |

#### 各 HUD 组件职责

1. **BattleInfoPanel（左上）**
   - 只读，读取 `battles.json` 的 `win_condition` / `lose_condition`。
   - 战斗开始构建一次，不再更新。

2. **UnitStatusCard（左下/右下）**
   - 直接复用 `UnitHud`。
   - 左下固定显示当前行动单位；右下显示鼠标/点击选中的目标。
   - 订阅 `CombatEvent` 中的 `DAMAGE` / `HEAL` / `QI_COST` / `STATUS_APPLIED` 等。

3. **BattleSkillBar（底部）**
   - 从 `BattleScene._build_action_buttons` 拆出独立 Control。
   - 当前单位切换时完全重绘，避免残留上一个角色技能。
   - 真气不足/冷却中按钮 `disabled = true` + 灰度 `modulate`。
   - 冷却数字显示在图标右上角（`Label` 叠加）。

4. **ModeSwitch（右上）**
   - 手动/自动切换按钮。
   - 调用 `CombatService.set_auto_battle_mode(bool)`。

5. **FunctionButtons（底部右侧）**
   - 调息、认输、逃跑。
   - 调息调用 `CombatService.player_rest_events()`。
   - 逃跑调用 `CombatService.try_escape()`。
   - 认输直接 `finalize()` 并标记失败。

#### 输入状态机

```
STATE_IDLE -> 点击蓝色格子 -> STATE_MOVING -> 移动完成 -> STATE_SELECT_SKILL
STATE_SELECT_SKILL -> 点击技能按钮 -> 计算范围 -> STATE_SELECT_TARGET
STATE_SELECT_TARGET -> 点击红色范围格子 -> 执行技能 -> STATE_EXECUTING -> STATE_IDLE
```

前端必须维护这个状态机，避免「还没移动就点了技能」或「同时选中两个技能」的时序 BUG。

### 3.6 后端视角：数据模型与算法

#### 新增数据模型

```gdscript
# data/runtime/battle_grid.gd
class_name BattleGrid

var width: int = 12
var height: int = 12
var obstacles: Array[Vector2i] = []          # 不可通行格子
var spawn_points: Dictionary = {}             # "player" -> Vector2i, "enemy_0" -> Vector2i

func is_walkable(pos: Vector2i) -> bool:
    return _in_bounds(pos) and pos not in obstacles

func get_neighbors(pos: Vector2i) -> Array[Vector2i]:
    # 四方向或八方向
    return [...]
```

```gdscript
# data/runtime/combat_character.gd 追加
var grid_pos: Vector2i = Vector2i.ZERO
var move_range: int = 3
```

#### 核心算法

1. **移动范围：BFS / A***
   - 从 `grid_pos` 出发，按 `move_range` 步数扩散。
   - 障碍物和敌方 occupied 格子不可踩（除非是远程敌人可穿）。
   - 返回 `Array[Vector2i]` 给视图高亮。

2. **技能范围**
   - 在 `skills.json` 中扩展字段：
     ```json
     {
       "range": 3,
       "range_shape": "diamond",
       "area": 1,
       "area_shape": "cross",
       "target_type": "enemy"
     }
     ```
   - `range_shape`：diamond（菱形）、square（方形）、line（直线，配合朝向）。
   - `area_shape`：single、cross、square、circle。
   - 计算以某中心点为基准的所有目标格子。

3. **A* 寻路（移动执行）**
   - 标准 A*，四/八方向，`heuristic = manhattan` 或 `chebyshev`。
   - 路径返回 `Array[Vector2i]`，视图按路径逐格插值移动。

4. **回合队列**
   - 复用 `CombatCore.get_round_sequence()`。
   - 当 buff 改变 speed 时，下回合重新排序。
   - 行动单位移动后，仅更新 `grid_pos`，不重建队列。

5. **胜利/失败条件扩展**
   - `battles.json` 增加 `win_condition`：
     - `defeat_all`：击败所有敌人（默认）。
     - `survive_n_rounds`：坚持 N 回合。
     - `protect_unit`：保护某 NPC 存活。
   - 由 `CombatState.is_over()` 读取配置判定。

## 四、优缺点对照

### 4.1 当前架构的优势

| 优势 | 说明 |
|---|---|
| 事件流驱动 | `CombatCore` 返回 `Array[CombatEvent]`，视图与逻辑天然分离，战棋只需把「移动」也变成事件。 |
| 伤害结算链完整 | 闪避、防御、暴击、护盾、反弹、复活已落地，战棋可直接复用。 |
| 确定性随机 | `SeededRNG` 已注入，战棋 AI 移动也能复现。 |
| UnitHud 可复用 | 状态卡、飘字、护盾条、复活特效已做好，直接拖到左下/右下。 |
| 快捷栏 6 槽 | 与逸剑底部技能栏数量一致，无需改配置。 |
| 自动战斗上限 | `MAX_AUTO_ROUNDS=200` 防止死循环，战棋 AI 托管也适用。 |

### 4.2 当前架构的劣势

| 劣势 | 说明 |
|---|---|
| 无空间概念 | 当前战斗是「选技能 → 自动打第一个敌人」，没有 grid_pos、距离、范围。 |
| allies 数组空置 | `CombatState.allies` 已声明但从未使用，多友方战棋需填充。 |
| 技能 JSON 无范围字段 | `skills.json` 只有 `target`（enemy/self/all_enemies），没有距离和形状。 |
| BattleScene 未拆分 | 当前一个文件里建 UI、处理输入、驱动流程，战棋需拆分为 `BattleGridNode`、`BattleEntity`、`BattleSkillBar` 等。 |
| 无摄像机控制 | 当前 Control 根节点无世界摄像机，战棋需要 Camera2D + WASD/滚轮。 |
| AI 过于简单 | 当前敌人只按权重选技能，战棋 AI 需要移动 + 站位 + 选目标。 |

### 4.3 逸剑战棋方案对我们的价值

| 价值 | 说明 |
|---|---|
| 提升策略深度 | 移动、站位、范围、地形障碍使战斗不再是纯数值对撞。 |
| 与大世界联动 | 大世界遇敌 → 战斗场景按地形生成网格（如竹林野外用竹林地图）。 |
| 扩展性强 | 后续可加陷阱、机关、高低差、zoc（控制区）等。 |
| 武侠味儿 | 轻功、调息、绝式冷却与战棋格子天然契合。 |

## 五、最小改动实现路径

### Phase 1：网格基础设施（1-2 周）

1. **新增 `BattleGrid` 数据类**
   - `width/height/obstacles/spawn_points`
   - `is_walkable(pos)`、`get_neighbors(pos)`
   - `grid_to_world(pos)` / `world_to_grid(world_pos)`（先按正交俯视实现）

2. **新增 `BattleGridNode` 视图**
   - 继承 `Node2D` 或 `TileMapLayer`。
   - 绘制基础格子底图。
   - 高亮接口：`show_move_range(cells)`、`show_skill_range(cells)`、`show_threat_range(cells)`、`clear_highlights()`。

3. **扩展 `CombatCharacter`**
   - 增加 `grid_pos: Vector2i`。
   - 增加 `move_range: int`（默认 3）。

4. **扩展 `battles.json`**
   - 增加 `grid_size: [12, 12]`、`spawn_points`、`obstacles`。

5. **扩展 `CombatService.start_combat()`**
   - 从配置构建 `BattleGrid`。
   - 按 `spawn_points` 设置玩家/敌人 `grid_pos`。

### Phase 2：单位视图与移动（1 周）

1. **新增 `BattleEntity` 视图**
   - 继承 `Node2D` 或 `CharacterBody2D`。
   - 持有 `character_id`、sprite、选中光环。
   - 方法：`teleport_to_grid(pos)`、`walk_path(path: Array[Vector2i])`。

2. **BattleScene 改造**
   - 根节点改为 `Node2D`（世界层），添加 `Camera2D`。
   - 在 `BattleGridNode` 上叠加 `BattleEntity`。
   - 现有 `Control` 元素（HUD）放到 `CanvasLayer`。

3. **输入：点击网格**
   - `BattleGridNode` 或 `BattleScene` 处理 `_input(event)`。
   - 左键点击 → `world_to_grid` → 发信号/调用 `CombatService`。

4. **移动事件**
   - `CombatCore` 增加 `move_unit(unit_id, to_pos)`，返回 `CombatEvent.MOVE`。
   - `BattleView` 播放移动动画。

### Phase 3：技能范围与目标选择（1 周）

1. **扩展 `skills.json`**
   - 每个技能增加 `range`、`range_shape`、`area`、`area_shape`、`target_type`。

2. **新增 `SkillRangeCalculator`**
   - 输入：caster_pos、skill_cfg。
   - 输出：`Array[Vector2i]` 可施放格子 和 `Dictionary[center_pos, Array[Vector2i]]` 目标格子。

3. **改造 `_cast_skill` 目标解析**
   - 当前按 `target` 字段直接选敌人/自己/全体。
   - 战棋下改为：玩家先选技能 → 高亮范围 → 选中心格 → 命中该中心格覆盖的所有单位。

4. ** BattleSkillBar 拆分**
   - 从 `BattleScene` 拆出独立脚本。
   - 当前单位切换时重绘。
   - 冷却数字 Label 叠加在图标上。

### Phase 4：AI 网格化（1-2 周）

1. **敌人 AI 流程**
   - 确定目标（最近玩家/盟友）。
   - 计算移动范围。
   - 评估每个可达格子的「行动价值」：能否打到人、打几人、自身安全性。
   - 走到最优格子。
   - 选技能（复用 `_pick_enemy_ability`）。
   - 执行技能。

2. **玩家 AI 托管**
   - 复用同一套 AI 逻辑，只是目标包含敌人。
   - 由 `auto_battle_mode` 开关控制。

3. **AI 评估函数（简单版）**
   ```gdscript
   func _evaluate_move(unit, pos) -> float:
       var score = 0.0
       for target in enemies:
           var dist = grid_distance(pos, target.grid_pos)
           if dist <= selected_skill.range:
               score += 100.0 * expected_damage
           else:
               score -= dist * 5.0  #  penalize 远离目标
       return score
   ```

### Phase 5：演出与 UI 打磨（1 周）

1. **移动动画接入 `CombatDirector`**
   - 新增 `CombatEvent.Type.MOVE`。
   - `BattleView._play_move(ev)` 让 `BattleEntity` 走路径。

2. **战场信息面板**
   - 新建 `BattleInfoPanel`。
   - 读取 `battles.json` 胜负条件。

3. **摄像机控制**
   - `Camera2D` 跟随当前行动单位（可选）。
   - WASD 移动、滚轮缩放、边界限制。

4. **等轴测升级（可选）**
   - 正交俯视验证通过后，把 `BattleGridNode` 的格子绘制改为等轴测瓦片。
   - `grid_to_world` 坐标转换改为等轴测公式。

## 六、关键踩坑点与规避方案

| 坑点 | 原因 | 规避方案 |
|---|---|---|
| 网格坐标与世界坐标转换错误 | 等轴测原点、瓦片尺寸不一致 | 先正交俯视验证逻辑，再换等轴测 |
| 多单位 y-sort 遮挡错误 | 等轴测单位在同一 TileMap 上 | 开启 TileMap y-sort，单位 Sprite `z_index` 按 grid.y 动态设置 |
| 移动范围和技能范围残留 | 回合结束未清除高亮 | `turn_end` 统一调用 `BattleGridNode.clear_highlights()` |
| 玩家 AI 与敌人 AI 逻辑分叉 | 两套实现导致行为不一致 | 都走 `CombatService` 同一套接口，AI 只是输入源不同 |
| 自动战斗死循环 | 双方远程对射无法接近 | 加回合上限 + AI 评估函数鼓励接近 |
| 技能目标选择歧义 | 玩家点击的格子不在范围内 | 前端先做范围校验，非法点击无响应 |
| 战斗结束后旧数据残留 | `CombatState` 未清空 | `finalize()` 时销毁所有视图节点，`CombatService` 释放 `_state` |
| 下一场战斗 spawn 点冲突 | 上一场敌人位置残留 | 每场战斗重新 `start_combat` 构建全新 `BattleGrid` |
| 网络/存档回放 | 战棋随机移动依赖 seed | 所有 AI 决策走 `SeededRNG`，保证同 seed 同路径 |

## 七、推荐的首个可玩切片

为了控制风险和快速验证，建议首个切片只做：

1. **正交俯视 2D 方格**（不做等轴测）。
2. **玩家 + 1 个敌人**。
3. **移动 + 普攻**（先不加技能范围）。
4. **敌人 AI：走到玩家相邻格子并普攻**。
5. **左下状态卡、底部普攻按钮、逃跑按钮**。

这个切片大约 **3-5 天**可跑通，能验证网格逻辑、输入、AI、演出整条链路。等它稳定后再做技能范围、多敌人、等轴测、摄像机。

## 八、结论

**当前架构已经具备演进成逸剑式战棋战斗的坚实基础**：

- `CombatCore` 的结算链、事件流、`SeededRNG` 可以 100% 复用。
- `UnitHud` 可以直接作为左下/右下状态卡。
- `AbilityService` 的 6 槽快捷栏 + 冷却桥接与截图底部技能栏天然对应。
- `CombatDirector` + `BattleView` 的事件驱动演出机制可以无缝接入「移动事件」。

**主要新增成本集中在三块**：

1. **网格数据与视图**（逻辑网格 + 高亮 + 等轴测渲染）。
2. **输入状态机**（移动 → 选技能 → 选目标 → 执行）。
3. **AI 网格化**（移动决策 + 站位评估 + 目标选择）。

**建议走「正交俯视方格 demo → 技能范围/AI → 等轴测美术升级」的分阶段路线**，避免一上来就被等轴测资源和坐标转换拖垮。这样既能快速拿到可玩版本，又能与现有架构的单向依赖、数据-视图分离、事件流驱动等铁律保持一致。
