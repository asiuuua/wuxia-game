## 二、七人评审团

### 1. 项目经理 —— 8.5 / 10

- 亮点：18 图全部 FROZEN、Phase1/Phase2 收官有据、多 AI 交接板/提交队列运转正常、13 图好资产收编策略（§171）执行到位。
- 扣分：**Phase1 收官声明与 13 图映射表不符**——P-S2（key 撞车·P0 资产丢失族）映射 Phase1 但未落地（见缺陷 D-01）；GATE2 flaky 会让"提交队列自动化"在红门禁下产生误判阻塞。
- 建议：建立"Phase 收官 = 映射表逐行打勾机器校验"制度，禁止人工声明收官。

### 2. 架构师 —— 8.0 / 10

- 亮点：依赖方向整体健康（services 未发现反向 import scenes）；buy/sell 预检+回滚、事务根治主链、SV-1 checksum 架构落地质量高。
- 违例（实锤）：
  - **D-04** relationship_service.gd L23/L104 直读 `GameManager.romance_service.sposes`（应为 `.spouses`）内部字典——违反宪法 RULE 007/008（非 Owner 触碰 Owner 内部状态），正是 08 图 DoD-3 要清零的族。
  - **D-05** services 层出现手写 FileAccess + `JSON.parse_string`（romance_service.gd L585-598，解析失败静默 `{}`）——违反 RULE 002 族与 13 图 SV-R10/S-3 精神。
  - 02 图 Transaction Runtime / Mutation Journal 仍未落地，buy/sell 走"手工补偿"过渡态（有回滚意识但非 0-C 统一语义）。
- 建议：romance 暴露公开 Query API（`get_spouse_record(npc_id)`），special_portrait 配置归 ConfigManager。

### 3. 程序员 —— 7.5 / 10

- 亮点：SaveManager 迁移链注册表/register_migration/golden 对/未知版本拒读（P-S1、P-S3、SV-3）实现干净，测试语义与图完全对齐。
- 违例（实锤）：
  - **D-01【P0·Phase1 漏网】** SaveManager.gd L68-70 `register_saveable` 只查对象重复、**不查 key 唯一性**——13 图 P-S2 明载"两个 saveable 同 key → 后写覆盖前写，前一域数据静默丢失"，映射表标注 Phase1，但 Phase1 已收官仍未修。资产丢失 P0 族。
  - **D-02** romance_service.gd L435 受孕判定裸 `randf() < chance`——17 图 DoD-1"业务面全局 rand=0"被新代码破坏；不可回放、不可测试。
  - **D-03** romance_service.gd L437 直读 `Time.get_unix_time_from_system()` 做孕检起点——宪法 §79 明禁业务读系统时间；且 unix 秒与游戏内"天数"语义错位，孕期推进逻辑存在隐患。
- 建议：三处皆为小改（注入 SeededRNG / 改游戏日 / 归口 IO），随 07 图 TimeConsumer 收编同批清。

### 4. 前端开发（UI/Presentation）—— 7.5 / 10

- 亮点：UI/B 路线全量 .tscn 化收官（screens.json）、PopupBase 统一 ESC、溢出 Toast 全局订阅（P2-7 闭环）。
- 违例：EventBus 存在 2 处 Dictionary 载荷信号（`item_used(item_id, effect: Dictionary)`、`grid_highlight_update(highlight_dict: Dictionary)`）——宪法 0-B.12 明禁 Dictionary Event Payload。属存量基线，应登记退役计划而非新增同族。
- 建议：新信号一律强类型参数；存量两处随消费方改造退役。

### 5. 后期运维（发布/兼容）—— 8.5 / 10

- 亮点：RH-1 版本真源、RH-2 日志轮转（5MB×3）、RH-3 死常量退役、provenance 八字段、出包链路全部落地执行；SV-1 老档 checksum 缺失读兼容（缺省值渐进）策略正确。
- 扣分：GATE2 flaky 直接影响"提交队列自动化每小时出队"的可信度（红门禁期自动化行为需要人工判读）。
- 建议：verify_all 增加 REPORT 工件（04 图 Q-5），把 flaky 复跑证据留档。

### 6. 性能极致 —— 8.0 / 10

- 亮点：combat_core 主链已走 SeededRNG；weather 域裸 randi 已退役；add_item 重量增量同步已优化。
- 违例：

  - 17 图 GATE40+ / Benchmark 双 PASS 未建（verify_all 无 GATE40 槽），性能预算体系整体未落地（按图属后续 Phase，如实登记）。
- 建议：删回退分支改为 assert+FATAL，一次性满足 17 图 DoD-2。

### 7. 测试门禁官（第七席·本轮新增）—— 6.5 / 10（全场最低分）

- 亮点：九门禁 + 三 git 钩子在位，退出码 CI-ready，基线制（GATE3 存量 5 / GATE6 基线 263）设计正确。
- 严重缺口（对照 04 图盘点 Q-1~Q-8）：
  - **D-07【P1】GATE2 flaky**（见 §一）——门禁自身可靠性不达标，存档红线测试存在假红/假绿风险。

## 六、总评

项目的**文档治理层（宪法/施工图/门禁政策）质量很高且自洽**，13 图"好资产收编"路线在存档域兑现度最好；但**执行层正在出现三类系统性风险**：①Phase 收官声明与映射表失配（P-S2 漏网）；②新代码（romance 受孕链）绕开已建立的确定性/Owner/IO 铁律——说明铁律还停留在 E0/E1，没有机器防线（GATE21+ 未物理化）；③门禁自身存在 flaky，削弱"门禁非绿阻断"的根基。三件事都不大，但都属于"越早越便宜"的类型，建议按 §五 顺序一周内收口。
