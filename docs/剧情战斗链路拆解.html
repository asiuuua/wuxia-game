ARCHITECTURE · 剧情 x 战斗 x 数据链路

分支剧情、场景NPC、战斗、后台表格 —— 一整条链路是怎么串起来的

以《逸剑风云决》这类"主线多分支 + 战棋战斗 + 多结局"的游戏为参照，映射到我们项目自己的数据表与代码，全程用小白听得懂的话讲。
先记住一个大白话总纲：一个游戏的剧情，本质上是一本"剧本书（表格）+ 一支旅行笔记（状态标记 flag）+ 一群传令飞鸽（事件信号）"。主线是一条有很多分岔的火车轨道，每个岔口由"道岔开关"（好感 / 之前的抉择 / 支线完成度 ）决定走哪根岔道，每条岔道最后通向不同的终点站（结局）。下面逐步拆开。

①三个核心概念 · 三板斧

任何"剧情会分叉、战斗会接入"的游戏，底层都离不开这三样。它们是理解后面全部内容的总钥匙。

概念白话解释在这游戏里对应谁
1. 配置表（数据）"剧本书 + 花名册"。每条任务、每个场景 NPC、每个敌人、每场战斗，都只是表格里的一行。游戏运行时**按 ID 查表**，代码本身不写死剧情。Data 表：quests.json / town_npcs.json / battles.json / enemies.json / dialogs.json
2. 状态标记 Flag（记忆）"旅行笔记"。记录"你走到第几步、做过哪些事、谁对你的好感多少、选过什么"。它决定岔道往哪走。PlayerState / 任务阶段 / 好感度 / 结局计数
3. 事件信号 Event（传令）"飞鸽传书"。剧情推进、战斗结束、好感变化时广播一条消息，全游戏谁想听谁响应，但互不写死。EventBus：quest_accepted / quest_phase_changed / combat_finished / bond_* / scene_changed…
为什么必须拆成这三个？因为把它们拆开，策划就能只改表格加剧情、加敌人、加分支，而不用改代码；代码只做"查表 + 广播 + 听信号"这三件事。这也是咱们项目里 ConfigManager（总管读表）和 EventBus（总管传令）存在的意义。

②分支剧情是怎么"推进"设计的（核心）

2.1 任务不是一条线，是一串"步骤节点"

一个任务 = 一串有序的节点，每个节点就是一行表格：{ 目标做什么 → 触发谁 → 完成了 → 记一笔笔记 → 推进到下一节点 }。用咱们 quests.json 里真实的"清剿山贼"举例：

{
  "id": "q_bandit_001",
  "name": "清剿山贼",
  "type": "main",
  "objectives": [ { "id":"defeat", "desc":"击败山贼",
                    "target_battle":"battle_bandit_001", "need":1 } ],
  "rewards": { "exp":60, "items":[ {"item_id":"pill_...","count":3} ] }
}

这一行的意思是：这一步骤的目标就是打赢 battle_bandit_001 这场战斗。战斗打完 → 目标达成 → 发奖励。派单后 Step ③ 会讲这场战斗又从哪来、赢了之后发啥信号。

2.2 分岔点 = "读笔记 + 扳道岔"

任务进行中→ 玩家在岔口做了抉择（对话选项 / 帮不帮 / 打不打）→ 写进笔记：flag = A 或 B→ 下一节点读该 flag，跳到 A 支 或 B 支

核心就一句话："道岔开关"永远来自"笔记里已存的 flag"，剧情绝不在场景里写死。下次推进时读一下是"帮过老乞丐"还是"没帮"，就走不同对白 / 不同后续战斗 / 开不同门。

2.3 多结局怎么来的：末尾是一排"结局闸门"

逸剑风云决主线结局多达 20 种（旧版 10 + 新版 10），触发全看三项：几位女主的好感、支线完成度、几个关键抉择节点 [$TRAE_REF]。底层翻译成工程语言就是：

  • 三条（甚至更多）"女主好感"其实各是一条笔记分数，随互动 / 送礼 / 陪伴累计；
  • 十几个关键抉择节点分别在岔口写入不同 flag（比如"是否卷入权力斗争"）；
  • 结尾不是"最后一场战斗决定结局"，而是一排"闸门条件"：只有当你笔记里 (好感A≥x && 好感B≥y && 负债flag==true …) 才开某扇门 → 放对应结局演出；缺哪个条件就走别的门。

这也是为什么攻略会提醒你"留档"——因为你没把记号凑齐，就开不了那扇门 [$TRAE_REF]。

③怎么和场景 NPC 勾挂

场景（Scene）只是"舞台布景"，是谁站在台上、说什么话，由 NPC 表格决定。看咱们 town_npcs.json 的真实一行：

{
  "id":"npc_bandit", "name":"山贼",
  "pos_x":700, "pos_y":100,          // 站在城镇哪一格
  "sprite":"res://assets/...",         // 长什么样
  "dialog_id":"npc_bandit",           // 👈 跟他说话放哪段台词
  "quest_id":"q_bandit_001",          // 👈 他能触发哪条任务
  "battle_id":"battle_bandit_001"     // 👈 挨他碰能开哪场战斗
}

这一行就把三个勾挂点全连上了：dialog_id(对话) + quest_id(任务) + battle_id(战斗)。游戏内置一个"碰撞即触发"的逻辑：你走到 NPC 面前按对话，就读 dialog_id；他的对白里若带了"接任务"事件，就调 quest_id 那条。

对话里的分支怎么选

对白本身也存表（dialogs.json），里面每个选项可以带"效果"。看 dialogue_events.json 的真实片段——对话行的 trigger_events 引用这里的 key，触发接任务/完成任务：

"events":{
  "accept_demo_quest":[ { "type":"quest_accept", "quest_id":"demo_quest" } ]
}

所以"选『接下任务』"= 对白里挂一个事件 quest_accept → 动画/音效 + 把任务写进笔记。选"不接"就不挂这个事件、顺手写个 declined=true 的 flag——这就成了未来一个岔口的道岔开关。

④怎么和战斗勾挂

战斗不是"每个场景里内嵌一块棋盘"，而是独立的一场"棋局"，按这次遭遇的参数临时摆出来。看 battles.json 的真实一行（战棋）——棋盘宽度、高度、障碍物、双方站位、敌人是谁，全在表格里写死：

{
  "id":"tactical_ally_inject",
  "enemy_ids":["bandit_001"],         // 👈 敌人=数据id，不是场景
  "turn_mode":"sequential",           // sequential=回合制战棋
  "tactical":true,                    // 👈 标了才是战棋（没标=半即时）
  "allies":["test_ally_npc"],
  "grid":{ "width":10, "height":8,    // 👈 棋盘尺寸也按场配
           "obstacles":["4,3","5,3","4,4","5,4"],
           "deployment":{ "player":[1,4], "bandit_001":[8,4] } }
}

4.1 触发战斗的两条路

触发方式怎么触发对应我们项目
① 明雷 / 撞怪世界上能看见的敌人（明雷），一撞上就切场开战；撞之前是自由的探索层。NPC / 地图上的遭遇点 battle_id
② 剧情战任务节点里点名"这步要打 boss"。逸剑的 BOSS 战/单挑建议用战棋回合制即可参见其攻略 [$TRAE_REF]。quests.json 的 objective.target_battle → battles.json

4.2 打赢 / 打输 / 必败怎么跳支

战斗结束→ 广播combat_finished(结果)信号→ 剧情脚本听结果→ 胜利→推进 A 支 失败/逃跑→推进 B 支 剧情设定"必败"→走由败方触发的演出

逸剑把双模式放在同一块格子上、格子数随场景变，就是说棋台是共用的、只是"盘子大小"不同 [$TRAE_REF]。我们的 turn_mode + tactical 开关 正是同一个棋台的两套打法。

⑤你最关心的：难道每个场景都要盖一个棋盘？资源不炸吗？

直接回答：不用，也不炸。全游戏只有一个共用的战斗棋盘场景（BattleScene），并没有给每个世界场景单独盖棋盘的 .tscn。

5.1 世界和战斗是"两层"，不是"一份文件里塞两样"

  • 探索层：城镇 / 野外的世界地图场景，负责走来走去、对话、接任务——不装棋盘。
  • 战斗层：独立的一张 BattleScene，负责"进战斗时铺棋盘、摆敌人的棋盘布局"。双方一撞 / 一进剧情战，就从探索层切到战斗层；打完再切回探索层。

5.2 棋盘是"参数"不是"美术场景"

棋盘的长相（宽、高、障碍物、谁站哪）是 battles.json 里那几行数字，交给代码按参数铺出来（我们的 grid.width/height/obstacles/deployment 就是干这个的）。敌人也是 enemy_ids 的 id → 去 enemies.json 查几行数据 + 复用同一份棋子模板。加了 100 场战斗，只是表格加 100 行，美术资源几乎不增。

5.3 一次只加载一个场景（这就是"单加载"的真相）

用 Godot 的场景切换（change_scene_to_file）时，内存里几乎同时只有一个大场景在跑：平时驻留"当前所在的世界场景"，进战斗那一刻才把棋盘场景换进来，打完换回去。常驻的只有轻量的管理器（UI、配置、事件总线）。所以哪怕大地图有几十个场景，它们的资源也不是同时塞进内存的——这也是国产这类开放世界同屏不爆炸的关键。

⑥和后台表格的整体关联（五表联动图）

把上面串成一张"关系网"，这就是整条链路的地图。数据流向永远是 Stage → NPC → 对话 → 任务 → 战斗 → 分岔 → 结局，且每一步都靠 ID 在表间跳转：

TownScene / 世界图（探索层）→ town_npcs.json
场景NPC→ dialogs.json + dialogue_events.json
对白 / 分支选项 / 事件
quests.json
任务链 + 分岔道岔→目标 target_battle→ battles.json
遭遇 / 敌群 / 棋盘参数→ enemy_ids → enemies.json
敌人属性
战斗层 BattleScene（唯一共用棋盘）→ combat_finished 信号→ 剧情脚本读 flag + 好感→ 跳对应分岔 → 汇入结局闸门 → 多结局
后台表它是谁怎么和别的表咬合
quests.json任务链 / 剧本主线objective.target_battle→battles；NPC.quest_id→本表；完成发 rewards
town_npcs.json场景站位 / 谁触发dialog_id→dialogs；quest_id→quests；battle_id→battles
dialogs.json / dialogue_events.json台词 / 分支选项 / 效果trigger_events→ quest_accept / quest_complete / 设 flag
battles.json遭遇 + 棋盘参数enemy_ids→enemies；grid喂给 BattleScene；被 quests 引用
enemies.json敌人数值被 battles 的 enemy_ids 查表生成战斗单位

⑦打通整条链路 · 一个小白看得懂的完整例子

咱们把"洛村的乞丐试炼"这条小线从头到尾走一遍（数据都是项目里真实存在的），你就能看到一个剧情怎么一路"拽着"NPC、对话、战斗、flag、结局跑完全程：

#发生什么它读/写了哪张表、哪个信号
1你走进洛村（探索层 TownScene）scene_changed 信号；世界图提供 舞台
2撞见"村口老乞丐" NPCtown_npcs.json 查 demo_npc：长这样 + 站哪 + dialog_id=demo_npc
3按对话，老乞丐说话读 dialogs.json(对话)；对白挂 quest_accept 事件（dialogue_events）
4选"接下寻玉佩"quest_accept → 任务 demo_quest 写进笔记；广播 quest_accepted
5目标：击败城西野狗quests.json 目标 target_battle=demo_battle
6进战斗读 battles.json demo_battle：enemy=demo_enemy → 切 BattleScene 铺棋盘开打；广播 combat_started
7打赢广播 combat_finished(胜利)；任务目标完成 → 发 exp/silver 奖励；quest_completed
8切回洛村，找老乞丐交玉佩又从 town_npcs 读 demo_npc，对白读"拿了玉佩"走感谢分支（由"有玉佩"这个 flag 决定的道岔）
…一路上还有十几条这样的线每条都在关键处写 flag、读 flag
末剧情走到终点"结局闸门"逐条核对 好感A / 好感B / 某抉择flag / 支线完成度 —— 达标开对应结局，否则走另一结局
一句话记住整条链路：场景是舞台 → NPC 是演员（表格定位）→ 对话是台词（表格+分支）→ 战斗是插演一场棋（表格配敌配棋盘）→ 每件事做完都写一笔 flag、广播一个信号 → 下一个岔口和结局闸门靠这些记号扳道岔 → 每个人玩出不同结局。

⑧给咱们项目的落地建议（架构清单）

  • 分支不写死在场景里：所有岔口用"读 flag + condition 表达式"，新增分支=加表+加 flag，不动场景代码。
  • 战斗只做一个参数棋盘：BattleScene 共用一份，grid + enemy_ids + tactical 用 battles.json 按场注入，绝不逐个场景盖。
  • 任务节点统一"目标 → 触发 → 完成 → 推进"四段式：给 quests.json 加 prerequisites(前置flag) 与 then_set(完成后写什么flag) 字段，支撑分支链和结局闸门。
  • 对话选项即道岔：dialogs 每条选项允许 `trigger_events`(可含 set_flag)，用现有 dialogue_events.json 扩展即可。
  • 结局做成"条件闸门表"：新表/字段列出各结局需满足的 flag 与好感阈值，运行时逐条判定，出结局别写进战斗判定。
  • 探索层与战斗层分离：坚持"一次只驻留一个场景 + 常驻管理器"，保证多场景大地图内存可控。
