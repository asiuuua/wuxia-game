## 一、小白版总览（先打个比方）

把整个游戏想成一家**中央厨房 + 若干档口**：

- **配置（data/*.json）** = 菜谱本。所有数值（物品多重、技能多狠、敌人多强）都写在本子里，不写死在程序里。改平衡只翻本子，不用动代码。
- **服务层（services/）** = 后厨师傅。`InventoryService` 管仓库、`EquipmentService` 管穿戴、`AlchemyService` 管炼药……他们只算账、不抛头露面。
- **事件总线（EventBus）** = 餐厅里的**广播喇叭**。"仓库多了个药！""战斗打完了！"师傅们不互相喊，只对着喇叭喊，谁关心谁自己听。这样后厨和前厅（界面）互不认识也能配合。
- **界面层（scenes/ui/）** = 前厅服务员。玩家看到的所有按钮、背包格、血条，都是服务员照着菜谱本和喇叭播报画出来的。
- **自动加载（autoload/）** = 店长+收银台，开机就在，全场都能叫到。

**结论先说**：这家店**框架已经搭起来、后厨能出菜、前厅能点单**，目前是"能跑通全流程的小酒馆"，下一步是"扩成有招牌菜的大酒楼"（填内容、补体验）。

## 二、架构师视角：房子搭得稳不稳

### 2.1 分层（很清晰，这是最大优点）
```
autoload（18 个全局管家，开机常驻）
  └─ core（常量/枚举/工具）
       └─ services（纯业务逻辑，不碰界面节点）
            └─ scenes（ui 表现层 + gameplay 玩法层）
                 └─ data（JSON 配置，数据驱动）
```
铁律执行得不错：**业务层不持有 Node、跨模块只走 EventBus、数值全进 JSON 不硬编码、GameManager 当服务容器**。这三条守住了，后面加功能不会牵一发动全身。

### 2.2 成熟度评分（架构层面）
| 维度 | 评分 | 说明 |
|---|---|---|
| 分层与解耦 | A | EventBus 信号体系完整（约 60+ 个信号），分层干净 |
| 数据驱动 | A | 物品/敌人/技能/战斗/难度全 JSON，改数值不动码 |
| 可测试性 | B+ | 有 run_all 单测 + 背包/战斗冒烟测试，但覆盖率不全 |

### 3.1 代码质量亮点（值得肯定）
- **背包服务写得相当专业**：`try_consume` 两段式事务（先全量校验、再统一扣）、重量感知放入（满负重不再硬塞）、`_next_iid` 实例发号器随存档恢复（杜绝重号）、`O(1)` 数量缓存索引、`{idx,data}` 槽位顺序持久化。这已经接近生产级。
- **空安全兜底到位**：`ConfigManager.get_item` 对"配置里没有的物品"返回 `{}` 而非 `null`，所以存档里残留已删除物品 ID 只会**降级显示**（名字回退成原始 ID、重量计 0），**不会崩溃**。
- **脏刷新优化**：背包刷新从"全量销毁重建"改为"复用节点+内容签名按需重绘"，消除闪烁、降 GC。

## 五、漏洞与隐患盘查（重点）

> 分级：🔴 P0 必修 / 🟠 P1 重要 / 🟡 P2 建议

### 🔴 隐患 1：多窗口并发编辑同一文件（"踩踏"）—— 最高危
- **现象**：本次审查时工作树里 `inventory_service.gd`、`enemies.json`、`skills.json`、`battles.json` 均被改且**未提交**；其中 `battles.json` 在我刚提交 `74ce00a` 之后又被改了——说明多个 AI 窗口在**同时改同一批文件**。
- **后果**：我们**已经吃过一次亏**——`inventory_service.gd` 曾因并发编辑导致缩进损坏、整文件解析失败（P2-1 里修过）。这是会反复发生的真风险，且靠"自觉"不可靠。
- **建议**：① 共享配置文件（enemies/skills/battles 等 JSON）的改动必须**排队**，一次只一个窗口动；② 或引入"文件锁/待办看板"机制；③ 每次提交前必跑双闸门（`--quit` 零错误 + `run_all` 零失败），任何窗口改完立刻提交，别留长脏树。

### 🟠 隐患 2：未提交 WIP 长期堆积
- 当前工作树跨多个窗口都有脏改动。若某窗口会话中断，在途工作可能丢失或只提交一半。
- **建议**：谁改谁立刻精确 `git add`（禁 `-A`）提交，不要攒。

### 🟠 隐患 3：`run_all` "绿灯"会掩盖真实错误
- 测试输出里混着 `ERROR: String formatting error` 和故意触发的 `no_such_battle` / 坏档 报错——这些是**预期内的负向测试**，但和"真出错"长一样。目前闸门只看"失败数=0"，**不看错误日志条数**，一个新 bug 的 ERROR 会被淹没。
- **建议**：把预期错误打标签/隔离，或加一条"非零预期外 ERROR 即判红"的严格闸门。

### 🟡 隐患 4：`--check-only --script` 假阳性（验证陷阱）
- 已知该模式下不加载 autoload，引用 `SaveManager`/`UIManager` 等单例必报 `Identifier not found`——是假错。新人易误判。
- **建议**：单脚本校验用完整 `--quit` 或实际启动，别信 `--check-only --script` 的"找不到标识"报错。

### 🟡 隐患 5：内容薄 —— 骨架有、肉未填
- 物品 36 件、敌人/技能在扩，但门派武学树、伙伴、宠物、境界突破、民俗/克苏鲁氛围表现层基本还是空壳。当前是"能跑的流程"，不是"有内容的游戏"。
- **建议**：这是正常 Phase 3 工作，按路线图推进即可，但要在 roadmap 上明确"内容缺口"量级，避免误判为"功能完成"。

### 🟡 隐患 6：体验短板（非崩溃，但伤手感）
- **动画几乎为零**（仅 UIManager 淡入淡出）、**音效几乎为零**（`resources/audio` 只有一首 login_bgm，SFX 全空，`MenuItem` 悬停音是空 TODO）。
- **建议**：PC 单机影响小；若要"仙侠沉浸感"和安卓首发口碑，动画/音效应尽早排期。

### 🟡 隐患 7：`use_item` 默认 `context="town"`
- UI 在战斗内若未显式传 context，会按"城镇"语义处理用药。当前战斗用药大概率走战斗自身结算、不经此路径，属低危，但接口默认值是个小坑。
- **建议**：战斗内用药显式传 `"battle"`，或去掉默认值的歧义。

### 🟡 隐患 8（预防性）：信号/处理器参数对齐建议做一次全量扫描
- 这类 bug 我们已抓过一例（`InventoryScreen._on_inv_changed` 原 1 参、信号发 2 参，每改背包就报错，已修）。
- 好消息：背包/战斗的冒烟测试**运行时零 "Error calling from signal"**，说明已测路径上参数对齐没问题。
- **建议**：作为上线前例行项，写个小脚本扫一遍"connect 的处理函数参数数 ≠ 信号定义参数数"的情况，防患于未然。

## 六、一句话结论

**代码架构健康、背包/战斗两大核心已达可玩可测的较高成熟度；当前最大风险不是"代码写错"，而是"多人（多 AI 窗口）同时改同一批文件"的协作流程风险，以及"内容尚未填充"的产品风险。** 建议优先级：先锁住隐患 1（并发编辑治理）和隐患 3（测试噪声），再按路线图填内容、补体验。
