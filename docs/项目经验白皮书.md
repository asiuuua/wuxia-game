## 第一章 · 项目概览

### 1.1 基本定位
- **品类**：等距 2.5D 武侠 RPG，**单机**。注：实际代码为纯 2D（等距为美术目标态，待拍板）。
- **技术栈**：Godot **4.7.2**，纯 **GDScript**，无 GDExtension 整体依赖（仅瓶颈处增量引入）。
- **战斗**：回合制 + 自动；战术战棋为独立场景 + 读条切换。
- **平台**：Windows + 安卓（安卓仅设计预留，当前仅在 Win 验证）。
- **开发模式**：个人开发（用户为新手），**多 AI 并行协同**（窗口署名 + 变更留痕）。
- **世界结构**：区域枢纽式（独立场景 + 读条切换，非大地图无缝）。

## 第二章 · 架构总览

### 2.1 分层与单向依赖铁律
```
autoload(17)  →  core  →  data(JSON)  →  services(RefCounted)  →  scenes  →  resources / tests / tools
```
- **四底线**（架构宪法，不可破）：
  1. **单向依赖**：上层可依赖下层，下层绝不反向引用上层（否则循环依赖炸编译）。
  2. **跨模块只走 EventBus**：禁止业务模块互相 `preload` + 直调；谁产生谁 `emit`，谁关心谁 `connect`。
  3. **数值全进 JSON**：所有可调数值（属性/价格/掉率/网格几何）写在 `data/configs/**.json`，策划改数值免改码。
  4. **命名见名知意**：禁止 `tmp/a/b/x` 之类；文件/信号/方法名直述职责（全工程 grep 可定位）。

### 2.2 装配中枢 GameManager（依赖注入容器）
> 真源：`autoload/GameManager.gd`

- 持有全部核心业务服务实例（`combat_service` / `inventory_service` / `shop_service` / `bond_service` … 共 16 个 `var`）。
- `_init_services()` 在 `_ready()` 内 `XxxService.new()` 统一实例化——**业务层不持有 Node**，服务均为 `RefCounted`（切场景存活、无场景耦合）。
- 场景切换**唯一入口**：`_deferred_change_scene(path)` = `await get_tree().process_frame` 后再 `change_scene_to_file`（2026-09-02 主菜单 freeze 根因修复，见 5.2）。
- 指令接线：仅订阅 EventBus 的 `cmd_start_combat` / `combat_finished` / `world_day_advanced` / `bond_wedding_started` 等**全局信号**做编排，自身不直调业务模块。
- 存档入口：`_register_saveables()` 向 `SaveManager.register_saveable(...)` 集中登记可存档对象（玩家状态 + 背包服务）。

### 2.3 EventBus（跨模块唯一信号通道）
> 真源：`autoload/EventBus.gd`

- **100 个信号**，全部 `@warning_ignore("unused_signal")`（GDScript 静态检查误报本类不发，实际由外部模块 emit/connect）。
- **严格区分 NOTIFY / CMD 两类语义**（蓝图中枢事件）：
  - `NOTIFY`（事实已发生，发送方不等返回）：`combat_finished` / `quest_failed` / `unit_downed` / `inventory_item_added` …
  - `CMD`（请求执行动作，接收方执行）：`cmd_start_combat` / `cmd_set_unit_faction` …
- 参数全用**值类型**（String / int / Dictionary / Array），避免跨模块传引用导致隐式耦合。
- 战斗模块发完 `combat_finished` 即结束，**由 GameManager 连线 `quest_service._on_combat_finished` 推进任务**——替代原「战斗直调任务」的反模式。

### 2.4 数据流与存档唯一来源
- **GameState**：存档唯一真源。运行时状态经 `SaveManager.register_saveable` 集中登记，序列化/反序列化统一走 `SaveManager` + `save_validator`（兼容性校验）。
- **UIManager**：6 层 `CanvasLayer` + 屏幕栈（screen stack），`screens.json` 21 项全 `.tscn`，负责界面呈现，不持有业务数据。
- 数据流动：`JSON 配置 → services(RefCounted 逻辑) → EventBus 通知 → scenes/UI 呈现 → 用户操作 → EventBus CMD → services 改状态 → GameState 存档`。

### 2.5 主权边界（多 AI 协同防互踩）
- **共享地基（冻结，只增不改）**：`EventBus.gd` / `ConfigManager.gd` / `core/enums/*` / `screens.json` / `strings.csv`。改动须写《变更通告》并打招呼。
- **窗口主权**：UI 窗口 `scenes/ui/**`、战斗窗口 `scenes/**/battle*`、背包窗口 `services/inventory`、结缘窗口 `services/bond` 各有主权；跨窗只派单（handoff）不直改。

### 3.3 services 层（14 业务域，RefCounted）
**背包 `services/inventory`（777 行 + inventory_transaction 82 行）**
- 子功能：增删物品、重量上限、入包溢出提示、消耗品生效、事务化增减。
- 实现：核心 `InventoryService` + `InventoryTransaction`（事务 API：预检 → 执行 → 回滚）。
- 关键信号：`inventory_item_added/removed`、`inventory_add_overflow`、`item_used`、`item_used_in_battle`。
- 解决：把「扣钱不发货 / 扣料丢产出」类 P0 资产损失用事务锁死（见 `godot-asset-safe-fix` skill）。
- 隐患：`item_used_in_battle` 必须由战斗场景经战斗状态结算（P1-3 修复：背包不直接改 PlayerState），错接会经济/状态错乱。

**商店 `services/shop`（144 行）**
- 子功能：买卖、价格、售卖校验。
- 实现：`shop_service` + 资产预检。
- 解决：**BUG-04 经济漏洞**（售卖锁定物/任务物换钱）→ 售卖方加 `is_locked` / `is_quest_item` 校验，单测回归（P2-A）。
- 隐患：任何新增可售物须带锁定标志，否则重蹈 BUG-04。

**装备 `services/equipment`**
- 子功能：穿戴/卸下/属性加成聚合。
- 解决：装备与背包解耦，属性加成经 PlayerState 单一聚合。

**锻造 `services/forge` / 炼药 `services/alchemy`**
- 子功能：消耗材料产出装备/丹药。
- 关键：材料扣减走 `InventoryTransaction` 事务（扣料丢产出 = P0 红线）。

**战斗 `services/combat`（combat_core 607 + combat_service 500）**
- 子功能：回合制逻辑、战术战棋网格、单位状态、阵营、胜负判定。
- 实现：逻辑层 `CombatCore`（产生 `grid_highlight_update` / `grid_unit_moved` 等网格信号）+ 视图层（BattleGridNode/BattleEntity 订阅 Tween 动画）；`CombatService` 编排。
- 解决：逻辑/视图分离，战斗发完 `combat_finished` 即结束、由 GameManager 连线推进任务（去反模式）。
- 隐患：视图层 Tween 与逻辑帧需对齐；网格几何依赖 `town.json` 底图（见 BUG-14）。

**结缘 `services/bond`（romance 535 / relationship 225 / master 146 / sworn 85 / bond 266）**
- 子功能：姻缘、结义、师徒、关系网。
- 实现：`relationship_service` 为**聚合门面（无状态、不存档）**，其余为唯一真源。
- 解决：**BUG-03 关系双写脏档** → 关系网改单一真源（relationship_service 不存档，避免 romance/relationship 双写不一致）。
- 解决：**BUG-06 婚礼绕过回城钩子** → 接 `bond_wedding_started` 统一回城。
- 解决：**BUG-10 聘礼校验** → `can_propose` 加聘礼校验 + 休息入口推进天数。

**任务 `services/quest`**
- 子功能：接取/推进/完成/失败。
- 实现：`quest_service._on_combat_finished` 接 `combat_finished` 推进战斗目标（事件闭环）。

**对话 `services/dialogue`**
- 子功能：对话树、trigger_events 演出（音效/震屏/接任务）。
- 实现：`DialogueEventExecutor` 订阅对话事件经 EventBus 派发演出。

**武学 `services/ability`**
- 子功能：技能、冷却、武学栏。
- 实现：`AbilityService.tick_cooldowns(delta)` 由 GameManager `_process` 每帧驱动（冷却真值在 `cd_remaining`）。

**门派 `services/sect` / 对象池 `services/object_pool` / 存档 `services/save`**
- sect：门派关系/贡献；object_pool：通用对象池；save：存档读写（接 SaveManager）。

### 3.3.1 战斗系统深度剖析（回合制 + 战术战棋）
> 真源：`services/combat/combat_core.gd`（607 行）、`combat_service.gd`（500 行）、`scenes/gameplay/battle/tactical_battle_scene.gd`、`battle_grid_node.gd`、`core/combat_event_renderer.gd`。

**分层与职责**
- `CombatCore`（逻辑内核，`RefCounted`，**不持有任何 Node**）：接管原 `BattleScene` 的流程编排（攻击→敌人回合→判胜负→结算），逻辑算完吐事件，不再一帧跑完。
- `CombatService`（门面）：从 `ConfigManager.get_battle` 读 JSON 配置构建 `CombatState`（玩家/敌人/友方快照），难度倍率经 `DifficultyManager`（代码零 `if` 难度判断），把战斗委托给 `CombatCore`。
- `TacticalBattleScene` / `BattleGridNode` / `BattleEntity`（视图层）：等轴测战场绘制、四角 HUD、输入状态机、演出；**不持有任何战斗逻辑**，伤害结算永远走 `CombatCore`。

**回合制模型（ATB）**
- `speed`（集气速率）由 `agility` 派生，驱动行动顺序（供顺序条可视化）。
- 双资源：`hp`（气血）+ `mp`（真气/Qi）；招式耗真气、调息回真气。
- 招式分阶（普攻/二式/三式/绝世/轻功/心法/调息）+ 冷却 + 施加状态。
- 真实状态引擎：层数(上限) + 持续回合 + 每回合生效(DoT/HoT) + 属性修正(攻/防/暴击/闪避/集气速率)。
- 确定性随机：所有随机走注入的 `SeededRNG`，同 seed 同结果（可存档/回放/单测）。

**战术战棋网格（逻辑/视图接缝）**
- 逻辑层：`CombatCore` 计算可走格/威胁范围/技能范围，经 EventBus 派发：
  - `grid_highlight_update(highlight_dict)`：`{type:int -> Array[Vector2i]}`，type 0=蓝(可移动) / 1=绿(威胁) / 2=红(技能范围)。
  - `grid_unit_moved(unit_id, from, to)`：驱动 `BattleEntity` 的 Tween 移动动画。
- 视图层：`BattleGridNode` 用 `_draw()` **程序化绘制 45° 等轴测菱形网格**（不依赖 TileSet/贴图，headless 可编译）；连接 `grid_highlight_update` → `_on_highlight_update` 刷新高亮层；提供 `cell_center` / `world_to_grid` 反算坐标供点击拾取；地形用 `MultiMeshInstance2D` 单 draw call 批处理。
- 输入状态机：`IDLE(可点蓝格移动) → 选行动 → AWAIT_TARGET(点红格敌人执行) → 结束回合`；自动战斗走「走近最近敌人→普攻」简易策略，带回合上限防死循环。
- **接缝铁律（高频坑）**：战斗内高频有序流走**返回值** `Array[CombatEvent]`（不走 EventBus，避免信号刷屏）；只有跨模块通知（`combat_finished` NOTIFY）与网格视图更新（`grid_highlight_update` / `grid_unit_moved`）才走 EventBus。视图层 `Tween` 与逻辑帧需对齐，否则表现错位。

**解决了什么**
- 去「战斗直调任务」反模式：`combat_finished` 发完即结束，由 `GameManager` 连线 `quest_service._on_combat_finished` 推进任务（事件闭环）。
- 去硬编码：难度/属性派生全走配置 + `DifficultyManager`（`pc.speed = ps.agility`、`pc.defense = ec.attack*0.5`），无魔法数。
- 去场景耦合：逻辑纯 `RefCounted`，切场景存活、可单测注入固定 seed 验证确定性。

**隐患**
- 视图层 `Tween` 与逻辑帧需对齐；网格几何依赖 `town.json` 底图（误删 = BUG-14）。
- `battle_entity.gd` / `battle_grid_node.gd` 属战斗窗主权，跨窗只派单不直改。

### 3.4 scenes 层（actors / bootstrap / gameplay / ui）
- `ui`：21 个屏幕 `.tscn`（HUD v2 四面板已 .tscn 化），视觉层不持业务数据。
- `gameplay`：大世界/战斗/婚礼等玩法场景。
- `actors`：角色实体（主角 matte 动画立绘、战棋单位实体）。
- `bootstrap`：启动引导。

## 第五章 · 卡住很久的 BUG 专题

> 真实根因 / 解决 / 避免。适合做平台「踩坑→解决→后续避免」沉淀。

### 5.1 BUG-01（Critical）UIManager 缓存屏重开未回写屏幕栈 → 键盘全失效
- **根因**：缓存屏（CacheScreen）重开时未把自身回写进 UIManager 屏幕栈，导致后续所有界面不在栈内，键盘 `gui_input` 收不到。
- **解决**：重开缓存屏时显式回写屏幕栈；补 GATE2 断言测试（加载全部界面遍历节点树）。
- **避免**：缓存屏机制 + 屏幕栈操作必须带单测断言；新界面走 `test_ui_mouse_filter.gd` 接缝校验。
- **状态**：已修（P0）。

### 5.2 主菜单 freeze（2026-09-02，High）`queue_free` 与 `change_scene_to_file` 同帧竞争
- **根因**：点击「继续游戏」时，UI 关闭的 `queue_free` 与 `change_scene_to_file` 在**同一帧**执行，触发 Godot 内部 `Parent node is busy adding/removing children` 死锁，引擎卡死无报错。
- **解决**：所有场景切换统一走 `GameManager._deferred_change_scene(path)` = `await get_tree().process_frame` 后再切，错开帧。
- **避免**：**任何场景切换禁止在 UI 关闭/queue_free 同帧调用 `change_scene_to_file`**；强制走延迟一帧通道（已写入铁律）。

### 5.3 BUG-04（High）商店售卖锁定物 / 任务物换钱（经济漏洞）
- **根因**：售卖方未校验 `is_locked` / `is_quest_item`，玩家把任务关键物/锁定物卖给商店换钱，剧情断裂或资产异常。
- **解决**：`shop_service` 售卖方加锁定/任务物校验拦截；`P2-A` 补 `shop_service` 单测回归。
- **避免**：任何资产增删走 `InventoryTransaction` 事务预检；新增可售物必须带锁定标志。

### 5.4 BUG-03（High）关系双写脏档
- **根因**：姻缘（romance）与关系网（relationship）`双写`，两边不一致时存档脏、读档错乱。
- **解决**：关系网改 `relationship_service` **聚合门面（无状态、不存档）**，romance 为唯一真源。
- **避免**：跨子系统共享数据坚持「单一真源 + 门面聚合」，禁止双写。

### 5.5 BUG-06（Mid）WeddingScene 绕过回城钩子
- **根因**：婚礼场景自行处理回城，跳过统一回城钩子，导致回城后状态/坐标异常。
- **解决**：接 `EventBus.bond_wedding_started` → `GameManager._on_bond_wedding_started` 统一回城。
- **避免**：跨场景流转只走 EventBus CMD + GameManager 编排，禁场景自管回城。

### 5.6 BUG-14（教训）town.json 误删
- **根因**：误把 `town.json` 当死数据删除，实际它是**战术底图几何依赖**（战棋网格映射壳继承其共享网格几何）。
- **解决**：从 git 历史恢复；记入变更通告「共享地基增量」。
- **避免**：删任何 `data/**.json` 前先 `change_log.py query --keyword <文件名>` + `git log` 确认非依赖；调前先查铁律。

### 5.7 纹理压缩 latent bug（2026-09-02，进主菜单卡死真因）
- **根因**：项目默认纹理 `mode=0`（未压缩）；改压缩（`mode=2`）后，`UIBackground._sample_edge_stops` 用 `CompressedTexture2D.get_image().get_pixel()` 取像素，刷屏 `Can't get_pixel() on compressed image` 拖死主线程。
- **解决**：取像素改用 `Image.load_png_from_buffer(FileAccess.get_buffer(...))` 解码源 PNG（跨 4.x 稳定）。
- **避免**：压缩纹理禁 `get_pixel()`；纹理默认 `mode=2`（双保险脚本 `compress_textures.py` + `tscn_assets.py` 写死）。

### 5.8 静默接缝类 BUG（高频，无报错吞输入）
- **根因**：`mouse_filter` 枚举**反直觉**——`STOP=0`（拦截）/ `PASS=1` / `IGNORE=2`（穿透）。装饰子节点误写 `0`（STOP）会盖住按钮本体、吞掉 `mouse_entered` / `button_up`，表现「点不了 / 鼠标卡住 / 无报错」。
- **解决**：四层防线——① `tools/lint_mouse_filter.py`（GATE0 静态扫描，提交前跑，零误报）② `tests/unit/test_ui_mouse_filter.gd`（GATE2 运行时遍历节点树断言）③ git pre-commit 钩子（机器兜底拦提交）④ 启动卡口令（窗口粘 `docs/AI协同启动卡.md`）。
- **避免**：凡装饰子节点要「点击穿透」必写 `2`（IGNORE），**绝不可写 `0`**；逻辑单测抓不到此类静默拦截，须靠接缝测试 + 钩子。

## 第六章 · 项目评价方案

> 用户要求：明确本项目**优点亮点（值得复用）/ 与大厂工程化差距 / 当前显性隐患 / 后期维护建议**。

### 6.1 优点与亮点（值得复用）
1. **双闸门门禁 + 静默接缝四层防线**：个人项目罕见地把「编译零错误 + 53 套件零 ✗ + mouse_filter 静默拦截」做成机器防线，工程成熟度高于多数同体量个人项目。
2. **EventBus 解耦彻底**：100 信号严格 NOTIFY/CMD 分离，跨模块零直调，可维护性强。
3. **单一真源存档**：GameState + register_saveable 集中，避免多写脏档（BUG-03 即反面教材后的正解）。
4. **数值全进 JSON**：策划改数值免改码，降低非程序职能门槛。
5. **事务化资产 API**：`InventoryTransaction` 把「扣钱不发货/扣料丢产出」类 P0 锁死，经济系统稳健。
6. **平台连接器再定位**：本工程经验可经 `manifest.yaml`（ai_context/reskin/knowledge）被新项目/新 AI 直接复用，换皮零成本（见第八章）。

### 6.2 与大厂工程化的差距（诚实对照）
| 维度 | 大厂 | 本项目 |
|---|---|---|
| CI/CD | 云端自动跑 lint+测试 | 本地双闸门 + pre-commit 钩子，非云端 |
| 类型安全 | 强类型全量覆盖 | GDScript 弱类型，部分 Variant |
| 性能基线 | 自动 perf 回归 | 人工审计（无基线告警） |
| Code Review | 真人对审 | 多 AI 协同补位（非真人对审） |
| 数据迁移 | 版本化迁移工具 | 靠 save_validator 兼容，无迁移脚本 |
| 测试量化 | 覆盖率门禁 | 套件数门禁（0 ✗），覆盖率未量化 |
| 架构约束 | lint 全量强制 | 靠记忆 + skill + 启动卡口令（部分未 lint 化） |

### 6.3 当前显性隐患
1. **静默拦截防线不在 git**：`pre-commit` 钩子需 `install_hooks.py` 重装；换机/新克隆若漏装即失守（已知隐患，SOP §11）。
2. **纹理压缩默认仍 mode=0**：依赖双保险脚本兜底，新人易漏跑 `compress_textures.py` 致卡死（5.7）。
3. **多 AI 并行提交**：单分支各窗盲目 push 互覆盖风险，须 PM 整树双闸门全绿后统一推。
4. **服务体量偏大**：`inventory_service` 777 行、`combat_core` 607 行，需拆分降复杂度。
5. **存档无迁移工具**：大版本改结构有脏档风险（仅 save_validator 兼容）。
6. **安卓未实测**：仅 Win 验证，移动端适配未知。

### 6.4 后期维护建议
1. **架构约束代码化**：把「四底线」固化进 `gen_contract` / 静态 lint，不全靠人工记忆。
2. **建云端 CI**：每次 push 自动跑 GATE1+GATE2，红即阻断（现靠本地 + 钩子）。
3. **大服务拆分**：`inventory_service` / `combat_core` 按子域拆文件，接口契约 `gen_contract` 锁定。
4. **存档案版本号 + 迁移脚本**：大版本改结构安全演进。
5. **新人 onboarding 链路**：读白皮书 → 加载项目 skill → 粘启动卡口令，三步即可上手。
6. **平台自动沉淀**：把 `ai_context` / `reskin` / `knowledge` 接进复盘面板，每项目经验自动入库（见第八章）。

## 第七章 · 经验提炼与可复用流程

### 7.1 可复用工程流程（提炼为平台能力）
| 流程 | 做法 | 复用价值 |
|---|---|---|
| 双闸门门禁 | GATE1 headless 零错误 + GATE2 run_all 零 ✗ | 每次改动强制回归，红即阻断 |
| 静默接缝四层防线 | lint(GATE0) + 测试(GATE2) + 钩子 + 口令 | 防无报错吞输入 |
| 事务化资产 API | 预检→执行→回滚 | 防经济/资产 P0 |
| 变更留痕纪律 | change_log add/notice + commit_queue + handoff | 多 AI 不互踩、可溯源 |
| 调前先查 | 改 BUG 先 query 变更日志 + git log | 避免重复踩坑（BUG-14） |
| 延迟一帧切换 | 场景切换统一 `_deferred_change_scene` | 防同帧 queue_free 死锁 |
| 单一真源 + 门面 | 共享数据禁双写 | 防脏档（BUG-03） |

### 7.2 可复用模式（跨项目）
- **装配中枢模式**：GameManager 持有服务实例 + 统一场景/存档入口（任何 Godot 项目可照搬）。
- **EventBus NOTIFY/CMD**：信号语义分层，跨模块解耦标准范式。
- **资源/数据连接器**：`manifest.yaml` 三段（ai_context/reskin/knowledge）让新 AI 秒懂架构意图、换皮零成本。
- **静默接缝测试**：无头 mouse-pick 模拟器 + 节点树遍历断言，抓逻辑单测抓不到的吞输入。

### 7.3 哪些具备复用性（给平台/新项目）
- ✅ 架构分层铁律、双闸门、静默接缝防线 → 直接做成平台「新项目脚手架模板」。
- ✅ 事务化资产 API → 任何含经济系统的项目复用。
- ✅ manifest 三段 → 跨项目经验复用 + 换皮不换药核心机制。
- ✅ 多 AI 协同纪律 → 多 AI 并行项目的标准协作协议。

## 第八章 · 工作室平台价值定位（复盘调优 + 跨项目复用）

> 用户定位：工作室不是「又一个开发工具」，而是**复盘 / 调优 / 经验复用的元软件**——帮一个人 + 多 AI 跑出大厂级工程纪律，把经验资产化。

### 8.1 平台最高价值（逐条对齐用户诉求）
1. **跨项目经验复用**：前项目的架构思路、踩坑、换皮模板，经 `manifest.yaml` 沉淀；新项目一键对接即继承。
2. **换皮零成本（换皮不换药）**：`reskin` 5 层（立绘 / 登录背景 / 按钮 / 音频 / 剧情）仅换资源、底层不变，不会开发的小白也能只替换图片/音乐/文本剧情，降低类比开发成本。
3. **新 AI 秒懂架构意图**：`ai_context.architecture_intent` 让新 AI 直接读架构意图，不必重读全码；前人的错误（`common_pitfalls` / `predecessor_mistakes`）一并可读。
4. **多工程进度纵览**：各工程本地写好 `backlog.json`，平台对接复查、聚合显示在后台，一眼看全多项目状态。
5. **任务进度与缺失定位可查**：平台聚合各工程 open 派单 / 缺口，卡点一眼定位（谁卡、卡在哪、谁的责任窗口）。
6. **项目经验总结与复盘**：白皮书 / 审计报告 / 变更通告自动可查，复盘不靠人脑记忆。
7. **当前状态 / 风险 / 后续调优思路**：平台汇总各工程显性隐患（第六章 6.3）+ 调优项（6.4），调优有方向。
8. **踩坑 / 解决 / 后续避免**：变更通告 + BUG 专题（第五章）沉淀为「踩坑→解决→避免」知识库，新人/新 AI 直接避坑。

### 8.2 平台本质再定位（连接器而非容器）
- 平台**只对接工程、不持有工程数据**（每个项目本地写好自己的清单/数据，平台聚合显示）。
- 横向 Domain Module（UI视觉/剧情创作/战斗关卡/资产资源/系统治理）× 纵向 Project Adapter（`manifest.yaml` 各工程一份）二维解耦。
- 远程访问（Phase 4）**已决策延后**：紧迫度极低，需要时一步扩展，记入 `backlog.json` 的 `platform` 模块。

### 8.3 本地化应用交付（消除「调端口」痛点）
- 工作室打包为本地 exe（`PyInstaller onefile`），端口**自动顺延**（8765 被占试 8766…+20），用户**永不需手动调端口**。
- 安全红线：绑 127.0.0.1、路径白名单 `_is_valid_id`、ZIP 逐条目校验、Origin 防护、`security_selftest` 15 断言。
- 更新交付 SOP：清旧进程 → `--clean` 重打包 → 同步全部副本（6 处+）→ curl 验证 md5。
