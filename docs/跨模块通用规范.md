# 跨模块通用规范（落地对照 + 铁律）

> 本文件锚定《武侠单机游戏业务模块详细设计规范》第四部分（跨模块通用规范）的**已落地实现**与**强制铁律**。
> 配套代码已通过 Godot 4.3 headless 校验，零 Parse/Compile 错误。

## 1. 模块注册与启动流程（§4.1）

**落地方式**（对齐规范意图，但按本项目"无废代码"纪律做了裁剪）：

| 规范原设计 | 本项目落地 | 文件 |
|---|---|---|
| `Bootstrap` 有序初始化序列 | 同设计：按依赖顺序执行步骤并广播 `bootstrap_*` 生命周期信号 | `scenes/bootstrap/Bootstrap.gd` |
| `GameServices` 静态 16 服务容器 | **未做**：`GameManager` 已承担"服务容器"同角色（持有 player_state + 4 服务），重复建容器会造空引用 | `autoload/GameManager.gd` |
| `InputManager / LocalizationManager / UIManager / SceneManager / DebugTools` 步骤 | **延后到 Phase 2**：这些系统尚未实现，强行登记会造空引用、破坏已跑通切片 | 待 Phase 2 追加步骤 |

**铁律**：
- 启动序列只调用**已存在**的模块步骤；新增系统后在 `_build_init_sequence()` 追加，严禁引用未实现模块。
- 切场景必须用 `call_deferred`，禁止在 `_ready` 链中直接 `change_scene`（父节点 busy 时报错）。
- 全局类（带 `class_name`）通过全局名引用；**autoload 脚本本身不写与单例同名的 `class_name`**（与单例冲突，已多次踩坑）。

## 2. 错误处理规范（§4.2）

**错误分级**（枚举 `core/enums/error_enums.gd` → `GameErrorLevel.{INFO,WARN,ERROR,FATAL}`）：

| 级别 | 处理 | 触发示例 |
|---|---|---|
| FATAL | `ErrorHandler` 弹窗 + 退出 | 配置加载失败、核心资源缺失 |
| ERROR | 记录日志 + `notification_show` 通知 | 存档损坏、物品 ID 不存在 |
| WARN | 仅日志 | 字段缺失用默认值、信号重复连接 |
| INFO | 仅日志 | 存档成功、场景切换 |

**四种处理模式**（规范 §4.2.2）均已在代码中践行：
1. 返回结果对象（业务操作）→ 当前服务层多用信号/布尔返回，结果对象模式在 Phase 2 厚化。
2. 断言 `assert()`（开发期检查）→ 在关键前置校验使用。
3. `push_error` + 状态标记（Godot 无异常）→ `GameLogger.error/fatal`、`SaveManager` 均用。
4. 容错降级（玩家体验优先）→ `ConfigManager.get_*` 缺失返回空、UI 显示"未知"。

**全局兜底**：`autoload/error_handler.gd` 监听 `EventBus.game_error`，分级处理；`GameLogger.fatal()` 广播 FATAL。

## 3. 日志规范（§4.3）

**统一工具**：`core/utils/game_logger.gd`（`GameLogger`），控制台 + `user://logs/game.log` 双输出，5 文件轮转（10MB/个）。

**铁律**：
- 禁止裸 `print()`，一律 `GameLogger.debug/info/warn/error/fatal(module, msg)`。
- 日志必须带**模块名**（如 `"Inventory"`、`"Bootstrap"`）。
- 禁止在每帧循环里打日志（性能红线）。
- 调试信息用 `Level.DEBUG`，发布构建可由 `_current_level` 门控。

## 4. 配置管理规范（§4.4）

**当前落地**：`autoload/ConfigManager.gd` 启动时同步加载各 JSON 配置，提供 `get_ability/get_item/get_enemy/get_battle/get_quest/get_npc/get_dialog` 等查询；新增 `is_loaded()` 供启动序列查询。

**计划延后**（避免破坏已跑通切片，Phase 2 再重构）：
- 配置清单 `_manifest.json` + 版本号 + 按 manifest 顺序加载；
- `ItemData / AbilityData / QuestData / NPCData / EnemyData / SceneData` Resource 类与索引；
- 配置校验 `validate_all()`（引用完整性、缺失告警）。

**铁律**：所有数值写在 `data/configs/*.json`，绝不硬编码进代码；路径集中在 `ConfigManager` 常量，禁止散落。

## 5. 对象池规范（§4.5）

**落地**：`core/utils/object_pool.gd`（`ObjectPool`）+ `core/utils/pool_manager.gd`（Autoload `PoolManager`）。

**必须使用对象池的场景**（Phase 2 战斗/UI 接入时）：伤害飘字、战斗特效、投射物、掉落物、对话气泡、通知提示、粒子。

## 6. 性能监控规范（§4.6）

**落地**：`tools/performance_monitor.gd`（Autoload `PerformanceMonitor`，**仅调试构建启用**，发布版 `queue_free`）。提供帧率/卡顿计数/模块计时（`start_timer`/`end_timer`）/内存。

**性能红线（强制执行）**：

| 指标 | 红线 |
|---|---|
| 帧率 | ≥30fps（目标 60） |
| 单帧耗时 | ≤33ms |
| 场景切换 | <3s；启动 <5s |
| 内存 | PC <2GB |
| 存档读写 | <500ms |
| UI 响应 | 点击到反馈 <100ms |

## 7. 单机补丁/热更新规范（§4.7）

**落地**：`core/patch_manager.gd`（Autoload `PatchManager`）—— 启动扫描 `patches/patch_xxx/` 目录，加载 `patch.pck` 覆盖主包资源，做 `min_game_version` 校验，记录已应用补丁到 `user://patch_history.json`，可选触发存档迁移。

**结构**：`patches/patch_001/{patch.pck, manifest.json, migrate.lua?}`；`manifest.json` 含 `patch_id/version/min_game_version/files/save_migration`。
