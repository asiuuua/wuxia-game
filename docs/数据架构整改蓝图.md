# 数据架构整改蓝图

> 版本：v1.0　日期：2026-09-04　
> 承接《数据架构》文档思想：「数据定义与运行时状态分离」「全局数据与区域数据划分」「单一事实来源（SSOT）」「统一存档机制」，对现有系统进行全面摸底与整改规划。
> 面向人群：先给项目经理/架构确认路线，再动手。每阶段改完都要过双闸门（GATE1 零脚本错误 + GATE2 单测全绿）。

---

## 一、整改核心思想（一页看懂）

一把钥匙解释四件事：

| 你要解决的困惑 | 底层思想 | 大白话 |
|---|---|---|
| 哪些是"设定"，哪些是"进度"？ | **数据定义 vs 运行时状态分离** | "角色的长相"是设定、一辈子不变；"他有没有复活、好感度多少"是进度、会变、要存档 |
| 数据该放哪个文件？ | **全局 vs 区域划分** | 全天下的人都认识的规则放全局；只属于新手村的人放新手村文件夹 |
| 同一份东西会不会改乱了？ | **单一事实来源（SSOT）** | 每样东西只在一处"定义真身"，别处只认它的 ID，不各抄一份 |
| 存档到底存什么？ | **统一存档机制** | 凡是"会变的进度"登记进存档管理器；"不变的设定"永远不写进存档，读档时直接读表 |

**整改总目标**：让"加一个新内容 / 导入一张新数据表"变成傻瓜级操作——往对的地方塞一个 JSON，游戏就能读到，NPC/任务/战斗/物品/对话全部按规则对齐。

## 二、现状摸底结果

### 2.1 数据文件全景（盘点完毕）

`data/configs/` 下现有两类配置表：

**A. 全局表**（全游戏通用，`ConfigManager.gd` 启动时整表加载）：

| 目录/文件 | 存放内容 | 数据性质 |
|---|---|---|
| `abilities/skills.json` | 技能定义 | 纯定义（配置） |
| `items/`（武器/药品/装备/材料） | 物品定义 | 纯定义（配置） |
| `npcs/enemies.json` | 敌人模板 | 纯定义（配置） |
| `npcs/npc_stats.json` | NPC 属性模板 | 纯定义（配置） |
| `npcs/dialogs/` | 台词剧本（分片+索引） | 纯定义（配置），索引懒加载 |
| `quests/quests.json` | 任务定义 | 纯定义（配置） |
| `scenes/battles.json` | 战斗配置 | 纯定义（配置） |
| `combat/attribute_table.json` | 数值换算表 | 纯定义（配置） |
| `alchemy/forge/shop/sect/bond` | 各系统配置表 | 纯定义（配置） |
| `world/`、`ui/`、`difficulty/`、`player.json` | 环境/UI/难度/玩家模板 | 纯定义（配置） |

**B. 区域表**（按区域分文件夹，本次 NPC 迁移后的主战场）：

```
regions/
├── _map_index.json          ← 区域总索引（新增区域在这里登记）
├── newbie_village/
│   ├── index.json           ← 区域点名册（列出本区所有实体 ID）
│   ├── npcs.json            ← 【已迁移】本区 NPC（10+ 个）
│   ├── quests.json / items.json / battles.json / enemies.json
│   └── dialogs/*.json       ← 本区台词
└── misty_town/ …（同上结构）
```

### 2.2 摸底发现的遗留问题（重要）

| # | 问题 | 位置 | 影响 | 是否本次处理 |
|---|---|---|---|---|
| 1 | **游戏 NPC 主表仍指向全局 `town_npcs.json`** | `ConfigManager.gd` 第 28 行 `NPC_FILES` | 迁移后全局表已清空，游戏可能读不到 NPC 或读到旧备份 | ✅ 阶段一核心 |
| 2 | NPC 编辑工具/脚本仍写全局表 | 磁盘 ``tools/desktop_studio/studio_core.py`` 已改区域感知，但项目内 `addons/content_studio/npc_panel.gd`、`tools/story_import/convert.py`、`gen_icons.py`、`gen_placeholder_portraits.py` 仍指向旧全局表 | 工具链各干各的，容易读写错地方 | ✅ 阶段一/二 |

| 6 | 区域 index 点名册与实际表存在部分 ID 对不上 | `newbie_village/index.json` | 目录快照失真 | ✅ 阶段二对账 |

## 三、数据字典总表（核心交付物）

> 这张表是"每样数据放哪、谁来读、要不要存档"的唯一答案。每条记录 = 一个数据类型。

| 数据块 | 定义层（在哪定义） | 状态层（会变的进度） | 作用域：全局/区域 | 是否存档 | 唯一真源 | 备注 |
|---|---|---|---|---|---|---|
| **NPC 演员表** | `regions/<rid>/npcs.json` | 无（NPC 状态在 GameState） | 区域 | 否（设定） | 区域表 | 用 `scene` 字段归区 |
| NPC 世界态（生死/阵营/好感） | — | `GameState._unit_runtime` | 全局 | ✅ | GameState | **待定**：好感是否上收统一 |
| NPC 属性模板 | `npcs/npc_stats.json` | — | 全局 | 否 | 全局表 | |
| **物品定义** | `items/`（武器/药品/装备/材料） | — | 全局 | 否 | 全局表 | SSOT，别处只引用 ID |
| 玩家背包 | — | `InventoryService` | 玩家 | ✅ | 服务层 | 存物品 ID+数量（装备待补实例） |
| 装备实例状态 | — | 待补（EquipmentService） | 玩家 | ⚠️缺 | 需整改 | **阶段三补** |
| **任务定义** | `quests/quests.json`（+ 区域 quests.json） | — | 全局+区域 | 否 | 各表 | |
| 任务进行态 | — | `QuestService` | 玩家 | ✅ | 服务层 | |
| **战斗配置** | `scenes/battles.json` + `regions/<rid>/battles.json` | — | 全局+区域 | 否 | 各表 | |
| 战斗结果 | — | `GameState`（NPC 生死快照） | 全局 | ✅ | GameState | |
| **台词剧本** | `npcs/dialogs/` + `regions/<rid>/dialogs/` | — | 全局+区域 | 否 | 各表 | 索引懒加载 |
| 对话阶段 flag | — | `GameState._global_flags` | 全局 | ✅ | GameState | |
| 敌人模板 | `npcs/enemies.json` | — | 全局 | 否 | 全局表 | |
| 技能/状态 | `abilities/skills.json` | — | 全局 | 否 | 全局表 | |
| 门派/锻造/炼药/商店 | `sect/forge/alchemy/shop` | 门派声望等 | 全局 | 派系 ✅ | 服务层已登记 | |
| 结缘/结拜/师徒 | `bond/` | 关系进度 | 全局 | ✅ | 服务层已登记 | |
| 世界开关/难度/阶段 | — | `GameState` 各字段 | 全局 | ✅ | GameState | 章节进度唯一真源 |
| 安全点/抵押物 | — | `GameState` | 全局 | ✅ | GameState | |

**读表铁则**：
1. **定义层永不入档**——读档是"把状态层吐回给服务"，出生地/配色/台词这些设定直接从表读，不写进存档文件。
2. **每样东西只有一个真源**——NPC 长相对区域表，玩家背包对服务层，"是谁、站哪"问 GameState。
3. **区域特色能下沉就下沉**——只属于某区域的任务/战斗/NPC 优先放 `regions/<rid>/`，全局表只留全游戏共用。

## 四、整改路线图（分 5 阶段，每阶段过双闸门）

### 阶段一：收口 NPC 单一真源（最高优先 · 已部分完成）
- **目标**：让游戏运行时以"区域表"为 NPC 唯一来源，全局 `town_npcs.json` 退居备份。
- **动作**：
  1. `ConfigManager.gd` 的 `NPC_FILES` 改为聚合 `regions/**/npcs.json`（扫描 `_map_index.json` + 区域目录）。
  2. 提供 `get_npc(id)` 统一走区域聚合结果；`_npcs` 构建时合并各区域。
  3. 清理项目内指向 `town_npcs.json` 的死引用（`addons/content_studio/npc_panel.gd`、`tools/*.py`），改为区域感知或标记废弃。
  4. `town_npcs.json` 移入 `data/configs/npcs/_deprecated/` 作为历史备份（**保留不删**）。
- **风险**：低，主要是路径聚合逻辑，需 GATE2 的 icon_wiring 等契约测试加固。

### 阶段二：区域数据对账与盘点册校正
- **目标**：让"区域点名册（index.json）"与各分片表完全一致，消灭 ID 对不上。
- **动作**：
  1. 写校验脚本：比对 `index.json` 列出的 ID 与各表实际 ID，输出差异。
  2. 处理 `newbie_village/index.json` 中的幽灵/重复 ID（如 `npc_village_chief` 无名字、与 `nv_npc_chief` 疑似并存）。
  3. 明确 `misty_town` 区域表归属，补全其 index 点名册。
- **风险**：中，涉及数据合并去重，需小心不误删（历史教训：误删 JSON 会导致 GATE2 退化）。

### 阶段三：状态层补齐与去重
- **目标**：让"会变的进度"全部有唯一存档真源。
- **动作**：
  1. 盘点并补齐装备实例状态存档（阶段建议：在 InventoryService 内为"已强化/已变更的装备"存一份索引）。
  2. 收敛 NPC 好感度：评估把好感从 `GameState._unit_runtime` 与 Bond 关系表合并为单一来源，给出结论（或保留但明确归属）。
  3. 复检 `GameManager._register_saveables()`，确保新增状态对象都登记。
- **风险**：中高，涉及存档格式可能变更，需**旧档兼容**（SaveManager 已有版本号+备份机制）。

### 阶段四：工具链区域感知收尾
- **目标**：让内容工作室（桌面端＋项目内 addons）读写统一走区域表。
- **动作**：改造 `addons/content_studio/npc_panel.gd` 等残留工具，与 `studio_core.py` 保持一致的区域感知逻辑；废弃脚本标注"已迁移"。
- **风险**：低，工具层，不碰游戏运行时。

### 阶段五：导入能力与扩展就绪
- **目标**：为"大规模内容/数据导入"铺路。
- **动作**：提供"按区域批量校验 + 一键导入"规范模板，把 `tools/story_import/` 改造成区域感知的流水线。
- **风险**：低。

> 说明：阶段一+二为**必做**（直击当前遗留问题）；阶段三涉及状态层需**用户确认方案后**再动；阶段四+五为完善项。

## 五、本次先行确认的必做整改（阶段一二能立竿见影）

为避免"蓝图空谈"，先挑两件低风险、见效快的动起来：

1. **改 `ConfigManager.gd` NPC 加载**为区域聚合 → 游戏即刻读到迁移后的 NPC。
2. **全局 `town_npcs.json` 降级为备份**，清理死引用，还数据一个唯一真源。

这几步改完即过双闸门，验证游戏能正常读出新手村 NPC。

## 六、风险与红线

- 🚫 **不删任何现有 JSON**：迁移一律保留备份（`.bak` / `_deprecated/`）。
- 🚫 **不碰 `preset_*.json`** 战斗预设与战斗/背包游戏逻辑主权。
- 🚫 **不擅自改存档格式**：涉及字段变更须先出兼容方案。
- ✅ **每阶段结尾跑双闸门**：GATE1 `godot --headless --path "D:/武侠游戏" --quit` 零错误；GATE2 `res://tests/unit/run_all.tscn` 全绿。
- ✅ **改前查 change_log 确认非回归**，改后登记。
- ✅ **提交走 commit_queue 入队**，不自行 git 提交。
