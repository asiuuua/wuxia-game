## 二、文档 GDScript 语法硬伤（必须改，否则编译失败）

### 2.1 `implements ISaveable` 非法

GDScript 4.x **没有 `implements` 关键字**。文档所有 runtime state 类都写了：

```gdscript
class_name FishingState
extends RefCounted
implements ISaveable   # ❌ 编译错误
```

正确写法（本工程现有 `PlayerState`/`CombatState`/`QuestState` 等都是这么写的）：

```gdscript
class_name FishingState
extends ISaveable   # ✅ 直接继承 ISaveable（RefCounted 已是 ISaveable 的父类）
```

> 注意：本工程 `ISaveable` 是 `extends RefCounted` 的接口类，`FishingState` 等应 `extends ISaveable`，不要 `extends RefCounted` 再 `implements`。

### 2.2 `Resource` + `@export` 与我工程"数据全走 JSON"纪律冲突

文档用 `class_name FishData extends Resource` + `@export` 把**数值直接写在 Resource 资产**里。本工程纪律（你定的"数值全写 JSON、Resource 仅作 schema 占位"）是：
- 静态数据 → **JSON**（由 `ConfigManager` 加载，如 `weapons.json`）
- `Resource`（如 `item_data.gd`）仅作字段类型/schema 定义，数值在 JSON

**决策建议**：四大系统的静态配置（鱼/鱼竿/鱼饵/配方/材料/打造台/钓鱼点/NPC关系/成长配置）**统一走 JSON**，复用现有 `ConfigManager` 加载体系。Resource 类仅保留类型定义（可选，也可纯 Dictionary 驱动）。这样不引入第二套数据管道，维持"数据驱动"铁律。

> 运行时状态（`FishingState`/`BondState`/`CraftingState`/`ChildData`/`PregnancyState` 等）保持 `RefCounted`/`ISaveable` + `serialize()/deserialize()` 模式（本工程已有 `player_state` 范式），**不**用 `@export`。

### 2.3 其它小修正

- 文档 `CraftLogEntry.deserialize` 里 `e.success = data.get("s", 0)` 应为 `bool`（`data.get("s", false)`），且 `e.success = data.get("s", 0)` 写成 `0` 是笔误——落地时按 `bool` 处理。
- 文档多处 `GameServices.player` 等聚合访问器需按第三节重映射到 `GameManager`。

## 三、命名对齐：文档 API → 本工程 API

文档假设了一个 `GameServices` 聚合门面，本工程用 `GameManager` 聚合各 service 实例。逐条映射：

| 文档写法 | 本工程对应 | 备注 |
|---|---|---|
| `GameServices.player.xxx` | `GameManager.player_state.xxx` | 属性在 `player_state.gd`：`strength/constitution/agility/wisdom/luck/focus/level/silver/hp/max_hp` 等 |
| `GameServices.player.age` | `GameManager.player_state` **暂无 `age` 字段** | 生育系统需给 `PlayerState` 加 `age: int` |
| `GameServices.player.spend_money(cost, Currency.SILVER)` | `GameManager.player_state.silver -= cost`（或补 `spend_money()` 方法） | 本工程 `silver` 是 `int`，无 `Currency` 枚举 |
| `GameServices.inventory.add_item(...)` | `GameManager.inventory_service.add_item(...)` | |
| `GameServices.inventory.remove_item_by_id(...)` | `GameManager.inventory_service.remove_item_by_id(...)` | 已存在 |
| `GameServices.inventory.remove_item_by_instance(...)` | `GameManager.inventory_service.remove_instance(...)` | 本工程方法名是 `remove_instance` |
| `GameServices.player.luck` | `GameManager.player_state.luck` | 已有 |
| `QuestService.is_quest_completed(id)` | `GameManager.quest_service` **需补 `is_completed(id)`** | 现有 `QuestService` 无此方法 |
| `AbilityService.learn_ability(ability_id, player, false)` | `GameManager.ability_service.learn(ability_id)` | 签名不同，需调整 |
| `ConfigManager.get_fish/get_relation_data/get_passive_bonus/get_affix_pool_for_category/get_hidden_recipes/get_child_growth_config` | 需为 `ConfigManager` **新增对应访问器** | 加载 JSON 后提供 |
| `EventBus.achievement_check` | 需确认 `EventBus` 已补此信号 | 之前补过部分信号，落地时核对 |
| `LootService.roll_loot(table)` | 需建 `LootService` | P2，M1 可占位 |
| `SceneManager.change_scene(scene)` | 用现有场景切换（如 `GameManager` 的进场景逻辑） | 不新建 SceneManager |
| `CompanionService.*` | 需建 `CompanionService` | P2，配偶/孩子出战时才需 |

## 四、数据驱动落地方案（JSON 配置清单）

每个系统需要新建的 JSON（放在 `data/configs/` 对应子目录，由 `ConfigManager` 加载）：

**钓鱼** `data/configs/fishing/`
- `fish.json`（鱼类，对应 `FishData` 字段，去掉 Resource 包装）
- `rods.json`（鱼竿，对应 `FishingRodData`）
- `baits.json`（鱼饵）
- `spots.json`（钓鱼点 + 鱼群表）

**打造** `data/configs/crafting/`
- `recipes.json`（配方，对应 `CraftingRecipe`）
- `crafting_materials.json`（材料引用，实际复用 `items.json` 的物品 id）
- `stations.json`（打造台）

**结缘** `data/configs/bond/`
- `relations.json`（NPC 关系数据，对应 `CharacterRelationData`）
- `affection_events.json`（好感度事件，可选内联进 relations）

**生育** `data/configs/child/`
- `growth_config.json`（成长配置，对应 `ChildGrowthConfig`）
- `child_events.json`（成长事件）

> `ConfigManager` 需为每类配置加 `XXX_FILES` 常量 + `_load_xxx()` + `get_xxx()` 访问器（复用 `abilities`/`items` 的范式，参考已落地的 `recipes` 加载）。

## 五、建议实现顺序（按依赖与独立性，遵循"先小后大、不造空壳"）

```
阶段A：基础设施补全（跨系统前置，单独排期，不混进系统切片）
  ├─ WeatherTimeService（时间/天气/季节全局状态，autoload）
  ├─ TimeService（游戏内天数推进，autoload 或并入 GameManager）
  └─ 给 PlayerState 补 age / spend_money / 队友槽位占位

阶段B：四大系统切片（每个系统独立 M1 最小闭环，按独立性排序）
  1. 钓鱼（最独立，不依赖结缘/生育/队友）→ 先做
  2. 打造（仅依赖 InventoryService + ConfigManager）→ 其次
  3. 结缘（依赖 NPC 对话系统 + QuestService）→ 第三
  4. 生育（强依赖结缘 + 时间系统 + 队友）→ 最后

阶段C：二次基础设施（按需）
  ├─ LootService（钓鱼特殊事件 / 打造产出）
  └─ CompanionService（配偶/孩子出战）

阶段D：各系统 M2-M5 内容填充（按原设计文档逐阶段推进）
```

### 每个系统 M1 最小切片范围

**钓鱼 M1（建议第一个做）**
- 枚举：`fishing_enums.gd`（6 个枚举）
- 配置 JSON：`fish.json` / `rods.json` / `baits.json` / `spots.json`
- `ConfigManager`：4 类加载 + 访问器
- `FishingService`（extends ISaveable）：状态机 `IDLE→CASTING→WAITING→BITING→FIGHTING→CAUGHT` 简化版（咬钩/收杆用计时器替代全 QTE，M2 再补张力 QTE）
- `EventBus`：补钓鱼信号（已规划，落地时补）
- `GameManager`：实例化 + 注册存档 + 新游戏重置
- UI：最简钓鱼界面（钓鱼点列表 + 开始/收杆按钮 + 鱼篓展示）
- 测试：状态机转换 + 钓获入库 + 存档往返
- **时间/天气条件 M1 暂简化为"固定窗口"或读取 `WeatherTimeService` 占位值**，M2 再完整接入

**打造 M1**
- 枚举：`crafting_enums.gd`（5 个枚举 + `ItemAffix` 类）
- 配置 JSON：`recipes.json` / `stations.json`
- `CraftingService`（extends ISaveable）：选配方→检查材料/技能/台→消耗→产出（成功/失败）+ 品质判定（M2 补随机词条/小游戏）
- UI：最简打造界面（配方列表 + 材料状态 + 打造按钮）
- 测试：材料消耗 + 产出 + 品质 + 存档

**结缘 M1**
- 枚举：`bond_enums.gd`（8 个枚举）
- 配置 JSON：`relations.json`
- `BondService`（extends ISaveable）：好感度等级 + 送礼反应 + 好感度事件触发
- UI：NPC 关系面板（好感度条 + 送礼按钮）
- **结缘/婚礼完整流程因依赖 NPC 对话系统触发，M1 先做到"好感度+送礼+事件"，婚礼流程留 M2**
- 测试：好感度等级边界 + 送礼反应 + 事件触发

**生育 M1**
- 枚举：`child_enums.gd`（3 个枚举）+ `ChildGrowthConfig` 资源/JSON
- 配置 JSON：`growth_config.json`
- `ChildService`（extends ISaveable）：`try_conceive`（需先结婚，M1 可临时放开或接 BondService 占位）→ 孕期更新 → 分娩 → 婴儿 + 基础成长
- 测试：怀孕概率 + 阶段转换 + 属性继承 + 存档
- **强依赖结缘**，建议结缘 M1-M2 完成后再做，或 M1 提供"测试用配偶"绕过结婚前置

## 六、落地纪律红线（沿用既有工程规范）

1. **数据全 JSON**：不把数值写进 `@export` Resource，统一 `ConfigManager` 加载。
2. **运行时状态 extends ISaveable**：不用 `implements`；`serialize/deserialize` 模式对齐 `player_state`。
3. **typed array 八字真言**：从 JSON/普通 Array（Variant 来源）收集数据时，要么 `assign()`、要么保持 untyped、要么循环内 `var x: T = arr[i]` 局部类型化——不一边 untyped 来源、一边 typed 返回（已踩过坑，见 `MEMORY.md`）。
4. **业务层不持有 Node**：Service 全 `extends ISaveable`/`RefCounted`，跨模块只走 `EventBus`。
5. **先小后大、不造空壳**：每系统先做 M1 最小可验证闭环，F5 可见效果再扩。
6. **autoload 不写 class_name**：与单例名冲突（已踩过坑）。
7. **Godot 4.7 headless 校验零错误**为每轮交付红线。
